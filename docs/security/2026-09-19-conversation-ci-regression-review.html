P1: Binding evidence can cross a counterparty email boundary

src/components/portal/pro-unified-inbox.tsx:197 authorizes the native display key using a global set containing only native binding plus owner/property/role. The returned display key instead uses the native row's email. The set producer at line 701 does not bind the declaring email to that evidence.

Concrete source-level counterexample: email A declares K1 for owner M/property P/role resident. A second email B has the same M/P/role and no native binding. Native K1 reports email B. The global set accepts K1 from A, but the helper places native K1 into B's display group. In src/lib/unified-inbox-merge.ts:127, B's group has no explicit bindings, so the entire bucket is accepted. B's pane can then render, acknowledge and reply through native K1 even though B never declared K1. Exact binding and person identity have been checked separately, allowing the wrong relationship between them.

Correction: carry normalized counterparty email with accepted binding evidence, and require one coherent binding/email/owner/property/role match before granting the shared person key. Do not simply disable the generic merge helper's no-binding behavior or rely on downstream selection to repair an already accepted member. Preserve authenticated resident-user-id aliases already supported by the native contract; an alias must remain attached to its proven person, never serve as an email-substitution bridge.

P2: New cross-key folding does not require complete owner and role proof

src/components/portal/pro-unified-inbox.tsx:171 treats every non-null inboxThreadRelationshipKey as a proven full relationship. That existing helper (src/lib/portal-inbox-storage.ts:456) requires only propertyId; owner and role can both be empty. The native relationship helper also permits empty owner and role. Two same-email, same-property rows bound to different native keys and missing owner/role now receive the same display key, whereas before their distinct bindings partitioned the display. This contradicts the handoff's promise that unknown identity remains isolated and that folding requires proven owner/property/role.

Correction: require nonempty, nonconflicting owner, property and role evidence for the new cross-key display folding and native acceptance. Prefer a narrow display-proof check; avoid broad changes to storage compatibility semantics without separate review. Provenance can supply fields, but absence must not count as matching proof.
