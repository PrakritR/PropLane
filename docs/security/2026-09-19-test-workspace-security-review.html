Reachable trigger: sign in as a newly invited classified account and POST a valid {"kind":"card","returnUrl":"https://prop-lane.space/resident/payments"} to /api/stripe/resident-payment-methods. S2 - P1: Google Calendar capture is SMS-context-only

Anchors: src/lib/google-calendar/sync.server.ts:56 and :761. Upsert/delete capture consults only captureSmsTestDelivery. Outside an SMS test turn it returns false, and line 767 invokes the real Google deletion API. No durable workspace checks appear in the Google Calendar provider module or connect/callback route.

Reachable trigger: a classified manager follows /api/portal/google-calendar/connect and completes its signed OAuth callback, which exchanges/persists a real connection. Then DELETE /api/portal/google-calendar/events?eventId=... authenticates the manager and calls deleteProplaneGoogleCalendarEvent. Without SMS ALS, the real Google DELETE executes. Ordinary availability sync also reaches unguarded provider operations; delayed/retry work lacks SMS request context. Hiding the settings affordance does not prevent these requests.

Correction: apply durable owner classification before OAuth exchange, connection/watch work and every read/write/delete provider boundary. Reuse workspace effect capture for applicable simulated operations. Refuse real connection setup for classified accounts; also guard already-created connections and delayed cleanup, so fixing setup alone cannot leave an escape.

Acceptance: active/suspended/expired/flag-off test managers, with and without pre-existing connections, must cause zero Google token/event/watch requests across direct routes, ordinary portal turns, availability sync, and delayed cleanup. Use provider spies; do not test by deleting a real event. Normal connected manager remains unchanged.

S3 - P1: suspension, expiry and flag-off do not revoke ordinary data APIs

Anchors: src/lib/portal-record-api.ts:89 and src/app/api/portal-service-requests/route.ts:23; suspension writer at src/app/api/admin/test-workspaces/route.ts:199. The operator PATCH changes membership state only. Layout and selected assistant gates check classification, but ordinary API session helpers and shared portal access helpers do not. Database provenance triggers classify rows and reject incompatible relationships; they do not reject operations based on access state. The service-role API query bypasses RLS.

Reachable trigger: create a private manager/resident record, retain the account session, suspend its member through the operator API, and GET /api/portal-service-requests. The route still authenticates, derives the ordinary role and queries the caller's records. Expiry and flag-off have the same gap. A layout denial is not applied to this API request. This is a confirmed continued read-access path; other API writes need coverage in the correction inventory rather than assuming that all writes are blocked by the banner.

Correction: add a fail-closed access decision at the authenticated business API boundaries and shared request context used by generic record routes, including independent service/request handlers. Preserve classification after denial. Audit direct authenticated PostgREST and storage access separately and enforce revoked membership there where it remains reachable; an HTTP-route-only fix cannot establish the whole contract. Keep the operator management/auth recovery paths deliberately separate.

Acceptance: keep a real valid session while changing membership to suspended/expired or disabling the flag. Assert denied record reads/writes across generic routes, service requests, manager/resident APIs, ordinary assistant and direct PostgREST/storage. Re-enable access and assert same workspace classification/data; normal account controls remain usable. Verify no endpoint falls back to public/customer behavior on lookup failure.
