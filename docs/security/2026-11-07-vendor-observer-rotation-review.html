Findings

1. High: repeated session checks can reuse the initial zero-session snapshot

scripts/security/signup-fixture-observer-rotate.mjs:90, call sites 140 and 167. Apply begins a transaction, reads pg_stat_activity, performs metadata and filesystem work plus external GitHub reads, then queries activity again in the same transaction. No pg_stat_clear_snapshot() occurs. PostgreSQL caches activity information within a transaction, so an observer connection established after the initial read can be absent from the supposed final check. The root attestation remains necessary, but cannot substitute for the expressly required fresh database observation. See PostgreSQL statistics snapshot documentation.

Correction: execute select pg_catalog.pg_stat_clear_snapshot() as a separate statement immediately before every activity inventory, retaining the complete-visibility and all-state exact-role checks. Keep a fresh inventory at the last pre-commit and pre-publication decision points. Do not terminate sessions or change role privileges.

Regression: model activity caching in a focused fake: first observation is zero, a new observer appears during the GitHub check, and the second observation refreshes only after the explicit clear. Assert refusal before ALTER/COMMIT/publication. A test that simply returns a fresh count on every mocked query does not exercise this failure.

2. High: the recovery directory itself is not durably linked before mutation

scripts/security/signup-fixture-observer-rotate.mjs:51, especially line 54. rotationStore creates a new operation directory. Subsequent writes fsync each file and the operation directory, but never fsync the existing parent directory that contains the new operation-directory entry. A crash after password commit can therefore lose that entry despite the nested files having been fsynced, defeating the promised retained-credential recovery. This is a durability gap, not evidence that data has already been lost. The containing-directory requirement is documented in fsync(2).

Correction: after exclusive creation and private-path validation, fsync the new operation directory and its already-private parent before any DB mutation. Fail closed if either sync fails. Preserve the existing exclusive file creation, file fsync, directory fsync and readable-byte verification. The root-created private parent must itself already be durable.

Regression: track filesystem synchronization ordering and inject parent-directory fsync failure. Assert no ALTER, no commit attempt and no secret publication. A normal temporary-directory readback proves readability, not crash durability.

3. Medium: the short quiescence lease may expire before irreversible boundaries

scripts/security/signup-fixture-observer-rotate.mjs:167 and 180-185. The lease is validated before a GitHub inventory that can consume 30 seconds. On publication it precedes two such calls, and the last database session check precedes all of them. A lease with little time remaining can pass, then expire before password commit or publication. A scheduled-consumer exclusion window can consequently end before the protected action.

Correction: finish the potentially slow GitHub metadata reads, refresh the DB activity snapshot and require zero sessions, then validate the local lease immediately before mutation/commit and again immediately before secret publication. Require sufficient remaining lease duration for the bounded publication call, or define and enforce a longer consumer exclusion window that covers it. Recheck after any blocking durability work before COMMIT. Root still must serialize consumers; point-in-time polling cannot prevent a new unmanaged consumer.

Regression: advance an injected clock during GitHub reads and durability writes. An expired lease must prevent the subsequent mutation/commit/publication. Also make a session appear during the final GitHub reads and require the fresh final DB observation to reject it.
