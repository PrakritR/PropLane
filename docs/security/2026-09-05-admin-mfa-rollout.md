# Admin application MFA — staged implementation

Status: local implementation, not deployed and no account enrolled by this agent. The production inspection previously found no verified application MFA factors. This document does not assert that production MFA is active.

The new `/auth/mfa` page uses Supabase's existing TOTP enrollment and challenge APIs. Setup starts only on an explicit click. Already enrolled accounts verify an existing factor; an AAL2 session can add a backup authenticator. The flow never removes a factor, creates a password-only bypass, or sends a setup key/code to application APIs, logs or analytics. The existing auth card, buttons and native `/auth/` path are reused. QR/secret/OTP containers carry PostHog's installed SDK `ph-no-capture` replay block and `ph-mask` text mask. Codes and setup secrets live only in component state, are cleared on session change/success, and late responses are discarded. Factor mutations run on an owner-pinned nonpersistent client so an old in-flight verification cannot directly replace a new browser login.

`ADMIN_MFA_POLICY` is server-only: `off` preserves the prior behavior; `enrolled` requires AAL2 for admins with a currently verified factor; `required` requires a verified factor and AAL2 for every admin. A typo fails closed. Admin detection includes role membership, legacy profile role and primary-admin fallback. Manager/resident/vendor accounts without admin privileges retain existing behavior.

Middleware covers every API path and every existing protected portal path. This includes shared APIs that independently recognize admin roles, rather than protecting only `/api/admin`. Both cookie and valid Bearer identities are evaluated because routes differ in precedence. JWT assurance uses the explicit-token SDK overload, which validates that token with `getUser`; it never trusts a client-provided AAL or header. Role/assurance outages return generic 503; required API step-up returns private/no-store 403 with `MFA_REQUIRED`; portal pages redirect to enrollment/verification. Sign-out and authentication recovery pages remain reachable. Return paths exclude external URLs and query strings.

Rollout sequence:

1. Deploy with `off`, confirm a dedicated staging admin can enroll, verify, sign out, sign back in, and use a second authenticator. Check mobile scrolling and native/WebView access; verify the final live PostHog replay blocks the setup container.
2. Enable `enrolled`; account owners explicitly enroll production admins themselves and add a separately held backup factor. Prove an AAL1 session cannot read/write a privileged shared API, then prove the same session works after verification.
3. Rehearse recovery using a synthetic staging account. If all factors are lost, an independently authorized provider operator verifies identity through the organization's recovery process, resets only that account's factors, revokes old sessions, and requires re-enrollment. Do not use email/password reset as MFA recovery or disable policy globally. Store backup access to the provider organization separately from the app's own MFA device.
4. Only after owner enrollment and recovery evidence, set `required` and repeat the negative AAL1 API test. Recheck all admin definitions, including the primary-admin fallback. This is the point at which mandatory app MFA can be claimed.

Scope limits: this gates Supabase-authenticated app requests. Provider organization/dashboard MFA, machine API keys/OAuth clients, SMS identity, direct browser database RLS, and custom service credentials are separate controls. Auth's own factor-enrollment and verification rate limits remain provider-controlled. `enrolled` deliberately permits unenrolled accounts and is an intermediate rollout state. A new public server-rendered privileged surface outside the protected prefixes must join the gate. No production enrollment, auth setting, deployment or external write was performed here.

Local validation: six focused suites passed, **47 tests**, including policy modes, primary/legacy admins, role/assurance failure, mixed cookie/Bearer identities, API and page enforcement, unchanged anonymous webhooks, sign-out, real form enrollment/challenge, masked secret containers, delayed responses after account switch and isolated mutation-client owner checks. Existing admin-role and platform-parity suites are included. Full TypeScript no-emit checking passed with incremental output disabled; focused ESLint and `git diff --check` passed. No real provider enrollment, production build, browser screenshot or live replay inspection is claimed by these checks. The release owner reviews and validates the isolated patch before integration.
