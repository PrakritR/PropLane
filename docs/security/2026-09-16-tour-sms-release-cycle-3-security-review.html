H1 - inquiry singleton remains writable through generic upsert

Exact evidence: src/app/api/portal-schedule-records/route.ts:106 includes id.eq.axis_admin_partner_inquiries_v1 in the non-admin scope for every non-vendor role, including residents. The POST branch at src/lib/portal-record-api.ts:204-226 handles any non-delete action as an upsert, checks the existing row only against that scope, and therefore accepts the existing singleton. At src/lib/portal-record-api.ts:241-258, the configured atomicWrite is called, but the schedule route's implementation at route.ts:137-196 immediately returns {handled:false} for every id other than axis_admin_planned_events_v1. The generic upsert at portal-record-api.ts:258 then persists the caller's full row_data. authorizeDelete at route.ts:197-207 protects the same inquiry id only for DELETE/deleteIds; it does not protect upsert.

An authenticated resident, unrelated manager, or admin can send {action:"upsert",row:{id:"axis_admin_partner_inquiries_v1",recordType:"axis_admin_partner_inquiries_v1",payload:[…]}}. The resident/manager scope explicitly makes the existing singleton visible for the write check; atomicWrite skips it; and no dedicated inquiry authorization or merge/CAS runs. A caller can replace or erase all pending inquiry records, including prospect names, phones, emails, requested windows, and SMS consent. An admin can likewise use this generic protocol to bypass the intended dedicated lifecycle boundary. This defeats the release's protected shared snapshot and can alter the data later used by tour approval, reschedule, reminders, and prospect SMS context.

Required correction: make the inquiry singleton fail closed in generic upsert/replace for all callers, or give it a dedicated server-side authorization/atomic handler that preserves server-owned rows and validates an observed baseline. Do not rely on GET projection or DELETE authorization: the POST must reject before the generic upsert. Add real route tests for resident, unrelated manager, owner manager, vendor, and admin, including action:"upsert", replace, empty payload, and an attempted mixed operation; assert the row is unchanged and no generic upsert occurs.

Read projection and deletion checks

The new GET path does apply a server projection: route.ts:85-93 reads the schedule rows and route.ts:93 passes them to projectScheduleRecordsForViewer. The projection denies non-manager/non-admin viewers, gives owners full item data, and gives an explicitly granted co-manager only the allowlisted busy fields (src/lib/schedule-record-projection.server.ts:100-174). Ownership lookup failures narrow access at lines 74-91; the service-role read bypasses table RLS but is projected before serialization. I found no confirmed read disclosure in this bounded review. A separate correctness/availability concern remains that this custom reader applies limit(500) before projection (route.ts:85-91), so a high-volume result can omit otherwise authorized rows; this is not an authorization bypass.

DELETE/deleteIds is materially stronger: portal-record-api.ts:156-178 reads every target, calls authorizeDelete for the whole batch before mutation, and only then reaches deletes at lines 190-197. The schedule hook rejects both protected singleton ids at route.ts:197-207. Scope is also reapplied to each delete query at portal-record-api.ts:180-188. No partial-delete bypass was established from this source review.
