P1 B1: Switching the assistant endpoint retains the previous conversation

src/components/portal/axis-assistant.tsx:549; src/components/portal/axis-assistant.tsx:572; src/lib/axis-assistant/use-assistant-conversation.ts:319

Trigger and evidence
Open an ordinary portal conversation, then press Start test. The endpoint changes but the provider and its archiveKey do not. The hook only clears the archive when archiveKey changes, so the old portal session, messages, pending action and hydration flag remain. The next SMS turn submits the portal session and is rejected as an invalid session. Exit test has the inverse failure. Switching during a pending request increments conversationGeneration through endpoint-dependent cleanup, while the old finally block only clears loading/requestInFlight for its original generation, potentially leaving the new surface permanently busy.
Correction
Use a full conversation identity containing endpoint, authenticated viewer and portal workspace. Reset and generation-fence messages, session, pending action, attachments, loading/in-flight state, metadata and every archive request on identity changes. Preserve the portal tree rather than key-remounting WorkspaceProvider.
Required verification
Hook/browser tests: existing portal chat → Start test → first SMS → Exit test → portal continuation; switching listing targets; switching while send or history fetch is delayed; verify no stale transcript, pending card, attachment or stuck busy state.

P1 B4: The private client catalog is merged with cached customer listings

src/lib/demo-property-pipeline.ts:783; src/lib/demo-property-pipeline.ts:643

Trigger and evidence
Browse ordinary public listings first so extras are cached, then sign in as a private test resident. Successful private catalog loading fills privateTestWorkspaceListings but leaves public extras intact. readExtraListingsPublic explicitly combines readAllExtraListings with the private array. Resident applications, tour modal and rental wizard consume this combined list. This violates the promised private-only catalog and shows choices whose backend rejects the cross-domain application. P1 B5: Late listing responses can restore private data after logout

src/lib/demo-property-pipeline.ts:607; src/lib/demo-property-pipeline.ts:611; src/lib/demo-property-pipeline.ts:643; src/components/portal/portal-sign-out-button.tsx:35

Trigger and evidence
The private array and catalog/detail in-flight guards have no viewer/workspace identity or generation. Logout clears the array but does not cancel/invalidate outstanding requests. A private catalog or detail response that finishes afterward repopulates the array and emits a pipeline event. A following normal user can observe stale private entries until another successful public load clears them; the global in-flight guard may also return the prior user’s request. Native WebViews keep module memory alive, increasing the importance of this boundary.
Correction
Key in-flight work and caches by authenticated viewer/workspace, capture an identity generation before fetch and discard stale completions. Invalidate on all session transitions, not only this signout button. Ensure direct detail fetches cannot append across domains.
Required verification
Delay private catalog and detail responses across logout and login as another actor; finish responses in both orders and assert no stale reads/events. Cover browser back, native resume and denied/failed fetches.

Cache, rendering and performance assessment

Private server responses use private, no-store and the server public listing projection excludes classified rows by default. Those are useful boundaries but do not solve client identity and fallback defects B4/B5. Public and private responses also share the same cookie-dependent catalog URL; ordinary responses advertise public s-maxage without an explicit domain-specific cache key. Verify actual edge bypass/Vary behavior with a warmed anonymous cache before enabling production. No edge-cache leakage is claimed without deployed evidence.

The SMS capability fetch runs on every manager/resident layout mount even when the assistant is closed. Successful active resident authorization scans up to 100 applications and 500 live workspace listings, then each turn resolves capability again and separately rereads application stage. This is bounded, but unnecessary mount-time work and repeated reads should be measured; do not add process-wide authorization caching that would delay suspension. Current private catalog requests also retain the old “CDN-cached, no TTL needed” assumption even though private responses are no-store. Consider viewer/workspace-keyed short-lived coalescing after correctness fixes.

The scheduled persistence split is directionally correct: server-only transport/provenance imports are separated from client-safe display types. No new dependency was added. The new admin UI reuses PortalRecordListSurface and person rows. Several new explanatory subtexts and small controls conflict with current UI guidance; include typography, target size, loading/error states and mobile overflow in the required live craft pass. No performance benchmark, hydration, production bundle, memory profile or accessibility runtime pass was run.
