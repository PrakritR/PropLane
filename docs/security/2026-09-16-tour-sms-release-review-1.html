S1 - High / P1: A manager save claims protected events with no assigned manager

Location: src/app/api/portal-schedule-records/route.ts:74-77, interacting with supabase/migrations/20260915105500_atomic_planned_schedule_generic.sql:113-115.

The existing reconciliation function protects every stored event whose manager differs from the caller, including missing or null owners (src/lib/planned-events-write-scope.ts:25-29). Its output includes those protected events. The new atomic write consumes that reconciled output, accepts every event with a falsy managerUserId, and overwrites its owner with the caller's id. The SQL preservation predicate uses value->>'managerUserId' <> p_manager_user_id::text, which excludes null/missing owners. Together these changes replace the protected unassigned event with a caller-owned copy. On a subsequent save, the caller can edit or delete it.

This is a supported record shape: PlannedEvent.managerUserId is optional in src/lib/demo-admin-scheduling.ts:598-606. The pre-change reconciliation explicitly preserved such events. Exploitation does not require guessing another event id, selecting another manager, or manipulating the protected event in the request; an ordinary manager save imports it from the stored singleton.

  1. Store a valid planned-events singleton containing event legacy-A with no managerUserId and a separate event owned by manager M.
  2. As M, POST the planned-events singleton containing M's own event. Reconciliation adds the protected legacy-A back to the payload.
  3. The new atomic callback stamps legacy-A.managerUserId = M. The SQL replacement omits its old null-owned copy and appends the stamped copy.
  4. POST again as M omitting legacy-A, or changing its content. It is now treated as M's editable slice.

Resolution criteria: distinguish new unassigned client events from protected stored events before constructing the owned slice. Preserve stored missing/null-owned events byte-for-byte using a null-safe SQL predicate such as IS DISTINCT FROM. Ship the database correction as a new additive migration, retaining immutable migration bytes. Add route-plus-real-PostgreSQL regression coverage proving both missing and explicit null owners survive an unrelated manager save unchanged, cannot be claimed or deleted by a second save, and another manager's owned events remain unchanged. Preserve any separately authorized admin editing behavior.

S2 - Medium / P2: A canceled prospect reminder can send after the budget/credit await gap

Location: src/lib/sms/owner-sms-dispatcher.server.ts:952-973, with loadSendPolicy at lines 94-103 and supabase/migrations/20260915104500_prospect_sms_tour_reminders.sql:43-55.

The reminder-specific begin RPC validates the current attempt and sets its outbox to submitting. The dispatcher then awaits campaign budget and communication-credit reservation (lines 876-920). A new inbound revision during these waits cancels the reminder, but the cancellation trigger only blocks outbox rows in queued, deferred, or claimed. The newly added final policy call includes the new prospect_tour_followup purpose, yet loadSendPolicy checks current reminder state only for the old tour_interest_followup purpose. The new reminder can therefore pass final consent/quiet-hours policy and reach the provider despite its committed cancellation.

The contract in docs/agents/sms-system.md, “Prospect SMS scheduling and follow-up,” says a new inbound, booking, opt-out, deferral, handoff, or archive cancels the follow-up. This finding concerns the avoidable multi-await window before the final policy check; it does not require eliminating the unavoidable overlap between a final successful check and an external provider call already in flight.

  1. Create a due reminder with current burst revision R, granted scoped consent, permitted quiet hours, and sufficient budget and credit.
  2. Dispatch it and pause after begin_prospect_tour_reminder_submission succeeds, before budget/credit work completes.
  3. Commit a new inbound message for that conversation, advancing the burst to R+1. Verify the reminder becomes canceled while the outbox remains submitting.
  4. Resume the dispatcher. The final policy read sees unchanged consent and sender but never reads the canceled reminder or newer burst. The current code proceeds to sendSms.

Resolution criteria: thread the durable reminder identity into the last policy check and revalidate reminder status, burst revision, scheduling state, archive controls, and ownership before provider submission; fail closed on unavailable state. Release reserved communication credit when this final check refuses. Add a deterministic provider-sink regression pausing at this exact boundary, commit the new inbound, then assert zero provider calls and no retained communication-credit charge. Cover booking/handoff/archive invalidation at the same boundary, plus the normal eligible case.
