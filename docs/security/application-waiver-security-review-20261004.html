Security assessment

AreaEvidence and conclusion
AuthorizationThe new save path uses the existing same-origin authenticated JSON PATCH and supplies no manager/owner identity. The server authenticates through requireManagerRouteUser, resolves ownership and applications edit access before writes, then pre-validates waiver permission and collision rules. Removing client workspace filtering does not grant authority: the captured property is independently authorized on every request. References: settings-module-page.tsx:398-412; API route.ts:218-251; settings-scope.ts:78-119; manager-route-guard.server.ts:16-43.
Target retentionChanges require exactly one selected property and store its id with the edit. Flush consumes stored id/code pairs rather than the newly selected scope. Requests carry only propertyId and waiverCode. Newer edits during an in-flight request remain pending. References: settings-module-page.tsx:389-418.
DisclosureNo new public endpoints, analytics fields, persisted browser storage, URLs containing codes, or broad response projections. Pending codes live in an instance-local ref and errors are displayed using existing toast/status infrastructure. Existing owner-only portfolio code disclosure remains on the unchanged server route. References: settings-module-page.tsx:174-175,247,409,424-426; API route.ts:185-203.
Error and retry pathsHTTP failures and network rejection return false, preserve pending entries and report failure. Close awaits the registry result and stays open on false. Concurrent blur/close reuse one in-flight promise. Previously successful targets can remain committed if a later target fails; remaining failed targets retain their original ids for retry, with no success announcement for the failed batch. References: settings-module-page.tsx:396-436,469-474,531-560; pro-portal-settings-modal.tsx:206-212.
