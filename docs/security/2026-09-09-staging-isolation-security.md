# Staging isolation security review - 2026-09-09

Reviewed base/head: `26404c43290f9b38348a6f80a1f662c2a99a63d4` plus the uncommitted implementation diff, re-reviewed after addition of `sms-inbox-state.server.ts`, mailbox mutation routing, chronology corrections, and regression tests. Review is source inspection, not a deployment or production-write test. No production data or external messages were written.

## Findings

1. **Medium, resolved on re-review: a browser state save can erase concurrent SMS history.** `sms-inbox-notice.server.ts` now appends to a stable per-owner/phone row with timestamp compare-and-swap, but `POST /api/portal-inbox-threads` still upserts the browser's entire `row_data`. `pro-inbox.tsx` persists local snapshots when marking read and explicitly upserts them when archiving. Sequence: browser reads turn A, webhook appends B, browser saves its A-only snapshot. B is lost despite successful webhook CAS. Preserve server-owned SMS message/history fields on browser state changes with atomic narrow updates or a read/merge/CAS path. Resolution: the authorized SMS target now enters `updateSmsNoticeMailboxState`, which derives members from database owner/scope/phone identity, rereads each row, and compare-and-swaps only mailbox state while retaining server history. The stale-snapshot regression test passes. Deletion resolves member IDs server-side and reapplies authorization scope; client-supplied member IDs are not trusted.
2. **Low, resolved on re-review: legacy consolidation can misattribute root direction.** `collapsePersonInboxThreads` replaces `body` and `from` with the earliest message while retaining `rootOutbound` from the newest canonical row. An older inbound root merged with a newer outbound SMS notice is rendered outbound by `inboxThreadMessages`. Resolution: collapsed roots now copy `first.outbound` and `first.at`, and combined messages sort by parsed time. New notice roots retain `rootAt` independently of latest thread recency. Consolidation regression tests pass.

## Security properties verified by inspection

- Missing `AXIS_PROD_SUPABASE_REF` no longer disables known production protection. Staging git ref remains checked even with an erroneous production runtime flag. Server and service client constructors call the guard.
- Browser guard pins recognized staging hostnames to the dedicated staging database before client creation. This is defense in depth, not authorization. Opaque preview hostnames are not classified by this browser helper; server runtime guards still apply.
- Calendar loads reject mismatched project provenance and untagged staging credentials before token decryption. Saves stamp the current database ref; ordinary sync-setting patches cannot recover rejected copied credentials. Public status excludes credentials. Explicit reconnect can authorize an external calendar in staging; this is not a general ban on calendar side effects.
- Stable SMS identifiers include the recipient manager ID and normalized phone. Conflict inserts ignore duplicates; append reads and writes additionally constrain owner and scope. GET derives owner and thread type from database columns rather than trusting JSON payload metadata. No new cross-owner disclosure was identified.
- Eight failed CAS retries throw rather than silently overwrite. Caller retry/idempotency behavior outside this helper is not certified by this source review.
