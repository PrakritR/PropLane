Finding status

Medium - resident application JSON widened the authorized property set: resolved in reviewed correction

Original issue. The feature commit accepted every property ID found in application columns and row JSON. A stale or extraneous JSON ID could therefore authorize research of a different live property owned by the same manager, exposing its location fields and sending its address to Brave.

Resolution evidence. The corrected applicationPropertyId returns one ID, with assigned_property_id first and property_id second; JSON is consulted only when both columns are absent (src/lib/tools/domains/resident/property-research-application.ts:15-24). The resident status projection and research handler now use this same function (src/lib/tools/domains/resident/lease.ts and property-research.ts). Research still checks resident email, manager ID, property ID and status = live before provider access. The focused test asserts that the original property is refused after assignment and adds a case beyond the first database page. The logic closes the reported widening even when JSON conflicts with a populated authoritative column.

Residual check. The focused test does not yet contain an explicit conflicting JSON ID when a column is populated. That extra regression case would make the invariant clearer, but its absence does not reopen this finding because the corrected resolver is unambiguous. The author's test results and integration QA are separate from this read-only review.

Other security controls checked

  • Manager research retains the existing property access and workspace check. Prospect SMS resolves a live/listed owner-scoped or public-catalog listing before research. Resident research now pages its application lookup with stable ID ordering, avoiding the earlier 500-row truncation.
  • Brave receives only selected location fields and fixed-topic queries at a fixed API endpoint. The response has an 18-second timeout and 128 KB size cap. The correction scans past empty excerpts before retaining up to six usable citations; it does not expand the response cap or fetch source URLs server-side.
  • Source links are limited to HTTPS citation annotations; Luna's reply-link guard admits only verified research-source URLs or the fixed OpenStreetMap attribution. Retrieved excerpts are wrapped as untrusted content. External prose remains a model-behavior risk, with no deterministic write path found in this feature.
  • Paid attempts are capped at two per agent turn through async local storage independently of Langfuse. Cache keys include scope, property, normalized address and topic; cache hits and coalesced callers add no attempt. Direct service calls outside an agent turn still require their caller's admission control.
