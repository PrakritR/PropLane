Finding P1: historical SQL terminates the next ledger guard's dollar quote

scripts/release-conversation-schema-reconciliation.mjs:118-121 wraps the entire PL/pgSQL body in the fixed delimiter $ledger_guard$, and embeds all prior migration statements in that body through a JSON SQL string literal. After the first reconciliation, its truthful history contains that exact delimiter. The next step embeds those statements in its guard.

PostgreSQL lexes a dollar-quoted body by looking for its matching delimiter. Single quotes inside that body do not protect an occurrence of the outer delimiter. Consequently the recorded first-step SQL closes the second-step guard prematurely, producing invalid SQL. The current disposable fixture never constructs a subsequent guard from a ledger containing the first guard's actual SQL, so its successful first-step case would miss this failure.

Impact: an initial migration can commit, but the next migration cannot execute, leaving a partial release. Production encounters the same issue after its name-correction migration. Exact dry-run selection does not parse and execute this guard, so a dry-run cannot detect the failure.

Required correction: generate deterministic collision-free dollar delimiters from each complete DO body, checking that the chosen delimiter does not occur in the body. Apply that approach to every generated DO block that embeds captured strings or SQL, including history rename and function snapshots. Add a disposable PostgreSQL regression that records the first guard's actual SQL, constructs and executes the second guard from that resulting full ledger, and verifies preserved history. Include a captured historical statement containing the preferred delimiter.
