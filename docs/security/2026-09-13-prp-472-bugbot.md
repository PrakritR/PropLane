## B1 - High / P1: a matching subset clears unread for an unmatched newer source

Location: `src/lib/portal-inbox-storage.ts:981-986`, `reconcileObservedInboxReadRows`; actual caller at `src/components/portal/pro-unified-inbox.tsx:1002` loads the latest cache when each acknowledgement resolves.

The helper filters a merged row's observations down to the subset matching the old request, computes unread only for that subset, then overwrites the single unread flag covering the entire current row. It does not require every current source to match. An unread arrival in a new same-person row, or a revised existing member alongside another unchanged member, can therefore be hidden by an older acknowledgement. This violates the explicitly required protection for a newly created third same-person row. The durable CAS can correctly preserve the new row while the client still suppresses its unread badge and removes it from Status=Unread.

Deterministic reproduction from the actual function body, extracted and evaluated with dependency-free Node:

```text
current row: folder=inbox, unread=true,
  readSources=[{id:A, observation:old-A}, {id:B, observation:new-B}]
old request: [{id:A, observation:old-A}]
response map: A -> false
actual reconciled row: unread=false
expected: unread=true, preserving unseen B
```

The probe exited 0 and printed the actual before/after values. It did not import the app, run a test runner, fetch, or mutate files. A changed B observation with unchanged A follows the same branch. Missing response IDs also implicitly count as false and should not be treated as acknowledgement.

Required correction: preserve per-source unread state or decline to overwrite the aggregate when any current source is unobserved, conflicting, revised, or lacks a valid result. Add tests with at least two current source observations and a delayed acknowledgement, including a newly added member and a revised member. The existing test at `portal-inbox-read-storage-contract.test.ts:73` covers only a singleton changed observation, which produces zero matches and misses this case.

Status: unresolved; blocker communicated immediately to the parent reviewer.

## B2 - Medium / P2: the assistant collapse drops noncanonical source observations

Location: `src/lib/portal-inbox-storage.ts:1069-1077`; coverage gap at `tests/unit/portal-inbox-read-storage-contract.test.ts:32-45`.

The feature introduces response-only observations and promises to carry their union through both collapse passes, but `collapseAssistantInboxThreads` still spreads only the canonical row's metadata. When two distinct rows actually share an assistant collapse key, their message bodies merge while all noncanonical `readSources` disappear. Conflicting observations in this pass are also silently resolved by canonical selection. The person-collapse union added by this feature does not cover inputs that remain separate in the first pass, including assistant aliases without a common email, or resident-scope GETs which call assistant collapse directly.

Reproduction by source inspection: pass two `agent_notice_<same-owner-uuid>...` rows with different IDs and observations and no common counterparty email to the two collapse passes. `assistantInboxCollapseKey` groups both, `messages` contains their combined history, but the result retains only the canonical row's observation. The new test first collapses two ordinary email rows into one non-assistant row; invoking assistant collapse on that singleton never exercises its merging branch.

Required correction: union and conflict-check observations in the actual assistant merging branch as well. Add an actual multirow assistant collapse test and a conflicting-observation case. Its root attachment/body projection also still uses canonical attachments with `first.body`; that predates this change, but the new claimed two-pass attachment test does not establish coverage of it.

Status: unresolved. This is a newly incomplete transport contract, not a claim that resident observed-read writes have been enabled.
