## Passing controls and prior finding resolutions

1. **Effective identity is resolved before batch access.** `src/lib/portal-inbox-thread-scope.ts:46-80` authenticates the caller, verifies admin status separately, and substitutes an effective portal target's ID/email only through the existing effective-session boundary. `portalInboxThreadScopeFilter` at lines 14-26 grants owner, linked-owner, participant, or explicitly admin-scope rows. An admin role alone does not grant unrelated manager-scope mailboxes. The new effective-viewer test calls the real resolver with authenticated/effective-context dependencies mocked; the route suite retains the real scope predicate and tests effective-target ownership, bare-admin denial, and a mixed-owner zero-write batch. This corrects the prior test's unrestricted-admin model.

2. **Co-manager edit grants remain affirmative and owner-scoped.** The mark-read route requests `viewerAndLinkedOwnerIdsForModule(..., "inbox", "edit")` at `route.ts:154`. The actual helper normalizes accepted, assigned-property grants and evaluates the requested module/level. `tests/unit/portal-inbox-co-manager-grants.test.ts` invokes that real helper: empty permissions leave only the viewer, read permission does not confer edit, and an edit grant adds the granting owner. The route test separately verifies the helper's requested level and scoped owner outcomes. This is meaningful layered composition evidence; it is not a live co-manager database test.

3. **Complete-batch authorization precedes outcomes and writes.** `route.ts:143-160` restricts this action to the manager mailbox scope, bounds the batch to 500 unique IDs with bounded observations, filters the initial lookup through the authenticated/effective scope, and checks the full returned count and every stored scope. Missing/inaccessible/mixed-scope batches return no member state and invoke no RPC. The first query's scope check occurs after retrieval, but before mutation or source outcomes. Scope-filtered rereads at lines 176-178 retain ID and manager-scope predicates.

4. **Observation values provide concurrency checks, never authority.** `portal-inbox-read-state.server.ts:13-26` hashes canonical durable identity, timestamp, and complete JSON, with stable object ordering and preserved arrays. `route.ts:94-96` projects the actual database ID and freshly computed observations over normalized stored data. POST ignores client identity/row JSON for SQL arguments and never accepts a requested unread value. Historical `sourceThreadIds` do not create a GET observation. The hash is deliberately predictable and is not treated as a credential.

5. **Exact CAS protects newer durable content.** `route.ts:169-187` compares the original browser observation, sends authorized database identity/timestamp/JSON to the RPC, and permits at most two attempts. A reread cannot upgrade an old observation to a revised snapshot. The SQL checks exact JSONB and timestamp plus scope, owner, participant, and thread type; only boolean unread on inbox/sent rows can change. The update only clears unread and strictly advances `updated_at`. Same-timestamp body, draft, folder, or message changes defeat the old CAS. Retained route tests cover same-timestamp content changes, retry bounds, RPC failure, reread failure, and partial outcomes.

6. **Earlier confirmed outcomes survive later failures.** Each source operation, including retry reads, has its own catch at `route.ts:163-192`. An A commit followed by B RPC/reread error returns A's confirmed read result alongside B's failure under HTTP 500. The transport parser in `portal-inbox-storage.ts:984-1010` validates exact result membership/status/boolean shape and can retain complete valid partial outcomes despite non-OK HTTP status. Unknown/malformed outcomes are not represented as success. There is no folder-write or generic-upsert fallback. The original server partial-result P2 is resolved.

7. **RPC execution remains service-only.** The unchanged migration uses `SECURITY INVOKER`, `VOLATILE`, empty search path, fully qualified relations/functions, and a transactional revoke from PUBLIC/anon/authenticated followed by a service-role grant. Its SHA-256 remains `8a6007c229d637f3eb4d6091650ddb8c546a7f5dee353abcb157e4bd99f5bad6`. Root's separate RPC report records actual DEV catalog privileges, anonymous/authenticated denial, 50/150-message payload checks, invalid-precondition and concurrency probes. This reviewer did not repeat or reapply them.

8. **Response metadata is removed at durable writer boundaries.** `route.ts:24-35,257-259` strips `readSources`, `readSourcesComplete`, and `smsBindingKeys` before generic server upserts. Client upsert/replace serialization at `portal-inbox-storage.ts:434-444` and legacy replace at lines 546-556 strip the same fields, including nested optimistic state by removing the entire source field.
