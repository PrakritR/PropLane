Confirmed findings

High: stale replace can resurrect a cancelled tour

Evidence. supabase/migrations/20260915103000_prospect_sms_tour_booking.sql:238-243 cancels an event by adding canceledAt, cancelling its active reservation and changing a confirmed/rescheduled booking to cancelled. The replace branch at lines 244-274 checks only that an event with the requested id exists (lines 261-263), then replaces the complete JSON event with caller supplied p_event (line 261) and creates an active reservation (lines 266-273). The booking update at line 274 excludes canceled bookings, leaving that row canceled. Replacement neither requires an active event nor compares an expected current start/end/version.

Impact. A reschedule request built before a cancellation can run afterward, omit canceledAt, and restore the tour event and slot as active while the SMS booking row remains canceled. The current server caller, src/lib/tour-planned-change.server.ts:370, calls replace without an expected-current fence.

Required correction. Make replace fail closed for cancelled events and require an atomic expected-current version or start/end predicate supplied from the authoritative current event. Do not reactivate a booking or reservation as a side effect of a stale replace.

High: reservation-only intervals are not collision checked

Evidence. In the same replace branch, the planned-event mirror is protected by an interval predicate at lines 252-257. The reservation authority check at lines 258-260, however, compares only manager_user_id and slot_key. The subsequent upsert is likewise keyed only by (manager_user_id, slot_key) at lines 266-273.

Impact. If an active reservation remains while its planned-event mirror is absent or otherwise unavailable, a different slot key with an overlapping interval can pass. For example, an orphan 10:00-10:30 reservation and a requested 09:45-10:15 reservation have distinct keys but overlap in time. This violates the durable reservation authority expected when the mirror is unavailable.

Required correction. Check every active reservation for the same manager using starts_at < requested_end AND requested_start < ends_at, excluding the same planned event only when it is the replacement's existing reservation. Retain the slot-key check as an additional guard, not the only one.

Reviewed controls with no additional confirmed defect

ETag and 409 fence. src/lib/google-calendar/api.server.ts:969-990 reads the remote ETag, validates durable current ownership after that read, and sends PATCH with If-Match. A conditional 412 becomes a superseded write at line 998. Deterministic create 409 enters that same conditional update path at lines 943-949.

Expired-owner recovery and cancellation cleanup. src/lib/prospect-tour-booking-recovery.server.ts:249-307 claims reconciliation, registers a bounded provider write deadline before sync, and returns failed work to reconcile_current or cleanup_required. Its cleanup path at lines 196-234 rechecks the live planned event before deleting a deterministic remote event.

SMS confirmation and reminders. Confirmation recovery uses booking-keyed enqueue arbitration in src/lib/prospect-tour-booking-recovery.server.ts. Reminder registration checks scoped consent and dispatch records the outbox handoff before submission in src/lib/sms/prospect-tour-reminder.server.ts. No separate credit or duplicate-send bypass was confirmed from this read-only pass. These are bounded static observations, not runtime validation.

Review limitations

These findings are static evidence, not execution proof. This review did not re-run tests or simulate provider timing. The two High findings are nevertheless directly derivable from the mutation branch and its current caller, and should be fixed and regression-tested before release.
