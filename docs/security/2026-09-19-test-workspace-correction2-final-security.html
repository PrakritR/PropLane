C2-S1 / P1Guest checkout can choose the identity used for classification

src/app/api/stripe/checkout/route.ts:53; src/lib/stripe/manager-checkout.ts:38-61,119,162

The unauthenticated checkout route accepts body.userId. The shared helper assigns it directly to storedUserId and skips both stored email lookups when it is present. Submit a classified account email plus an unrelated normal UUID (or a UUID with no membership): classification resolves normal and price lookup and Stripe session creation execute. No forged Stripe webhook is required. The corrected pricing-oauth-continue route does not protect this shared caller. In addition, the authenticated generic checkout caller invokes ensureProvisionedManagerForPricing at line 61 before the shared classification check, so revoked pending accounts can still reach provisioning reads/writes.

Derive existing identity from authenticated context or verified stored identity; never let guest userId suppress classification of the checkout identity. Gate the generic authenticated route before provisioning. Preserve new ordinary signup.

C2-S2 / P1An unmatched credit dispute still calls Stripe before deriving an owner

src/lib/comms-billing/credit-purchase.server.ts:326-348; src/app/api/stripe/webhook/route.ts:477-489

A genuine delayed dispute for a classified account can carry a payment-intent id with no matching manager_comms_credit_purchases row (for example a household payment, or credit not yet fulfilled). The dispute branch forces inspect_charge, and the no-purchase branch invokes loadCharge at line 341. The webhook supplies stripe.charges.retrieve. Classification occurs only after this branch, for a matched credit purchase. Thus the classified provider call survives even though matched fulfillment/reversal is now guarded.

Resolve ownership through an applicable durable ledger/charge/purchase mapping before the provider fetch; preserve refund-before-fulfillment reconciliation and ordinary dispute handling without treating an unmatched purchase as permission.

C2-S4 / P1Active private calendar and resident hydration still use ordinary data scope

src/app/api/portal/co-manager-calendar/route.ts:63-67,73-95,126-138; src/lib/auth/manager-lease-scope.ts:121-149; src/app/api/portal/resident-property/route.ts:65-79,102-129

Both routes discard the active workspace returned by the new gate. Calendar authorizes ordinary ownership/co-manager grants, then selects portal_schedule_records using ordinary expectedManagerScheduleRecordIds for every caller; it never reads the private schedule namespace or compares peer provenance. An active classified owner with pre-existing ordinary schedule rows sees those rows; an accepted pre-existing cross-domain grant can expose a normal peer’s shared slots. Newly created private availability is also absent from this result. Resident-property selects all applications for the email, chooses the primary filing, and reads/fallback-scans properties without checking test_workspace_id or manager classification. A pre-existing ordinary approved application for an identity later classified remains a path to normal property data. These require stored relationships, not an arbitrary unaffiliated resource id.

Carry workspaceId into the existing namespace-aware schedule loader and validate peer/resource provenance. Constrain resident application/property selection to the actor’s durable namespace, including fallback scans. Preserve normal controls and co-manager grants.

C2-S5 / P1The new webhook owner gate breaks normal hosted and legacy checkout completion

src/lib/stripe/manager-checkout.ts:135-174; src/app/api/stripe/webhook/route.ts:92-98,234-246; src/lib/manager-purchase-from-session.ts:81-113

The public checkout route accepts embedded:false. That supported hosted path creates a real paid session but never reserves manager_purchases by session id. The new webhook checkoutOwner requires precisely that row and a nonempty user_id, and throws before recordPaidManagerCheckoutSession can use its stored legacy user/manager fallback. A normal hosted checkout therefore reaches a persistent 500 on completion and does not grant its paid plan. Embedded guest reservations without user_id and reservation failures have the same mismatch. This is a concrete normal-control regression from fail-closed integration, not a request to weaken the ownership gate.

Make checkout reservation and owner derivation consistent across hosted, embedded, guest and legacy normal flows. A verified durable owner must be available before effects, and payment completion must not depend on a reservation path the creator never executes.
