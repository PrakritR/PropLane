Security analysis

Injection and XSS. AssistantMarkdown does not install rehype-raw or use dangerouslySetInnerHTML. In the installed renderer, raw HTML nodes are converted to text. The existing focused test confirms that model output containing an <img onerror> payload and a <script> tag creates neither an image nor script element. React continues to escape ordinary text. GFM formatting adds structural elements only.

Links and navigation. URL-bearing properties pass through the package's safe default transformation. Non-allowlisted protocols are blanked. The custom anchor component adds target="_blank" and rel="noreferrer", preventing opener access in supported browsers and suppressing referrer disclosure. HTTP(S) destinations can still be untrusted, as with any assistant-authored link, but navigation requires a user click and this behavior already exists across other assistant surfaces.

Role and data boundaries. The diff changes rendering after a message has already been selected for the current thread. It adds no fetch, route, query, database call, cache, persistence path, identity input, role branch, tenant selector, or authorization decision. Manager, resident, vendor, and assistant-message classification remain in their existing callers. No cross-tenant or privilege-escalation path was introduced.

Writes and external effects. The change is client-side presentation only. It cannot invoke an assistant tool, confirm a pending action, send a message, mutate a record, or alter the server-side confirmation lifecycle. Markdown links are ordinary anchors and do not execute application writes.

Supply chain. There is no manifest or lockfile change. react-markdown 10.1.0 and remark-gfm 4.0.1 were already locked at the base commit. The reviewed change reuses the existing component, so it adds no package, install script, remote asset, runtime download, or new third-party code.
