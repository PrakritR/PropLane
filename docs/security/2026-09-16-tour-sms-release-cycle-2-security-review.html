S1 - High: authenticated users can delete the global planned-events singleton

Exact locations: src/lib/portal-record-api.ts:115 enters the delete/deleteIds branch; line 122 constructs the service-role DELETE and line 123 applies the same scope used for reads. src/app/api/portal-schedule-records/route.ts:52 through line 54 explicitly includes axis_admin_planned_events_v1 for every role other than admin/vendor. Authentication at src/lib/portal-record-api.ts:104 checks only that a user exists. The protected atomic callback starts later at line 171 and cannot intercept deletion.

A manager with no access to another portfolio, or a signed-in resident, can submit {"action":"delete","id":"axis_admin_planned_events_v1"} to POST /api/portal-schedule-records. The fixed shared id satisfies the scope irrespective of the caller's ownership. The service client removes the entire singleton, including every manager's tours, tasks, and meetings. The equivalent deleteIds request is also accepted; mixed batches execute sequentially, so checking only later ids permits partial changes.

The new reservation and booking tables do not rescue this operation. Their lifecycle changes occur inside mutate_confirmed_tour_schedule, including the per-event delete branch at supabase/migrations/20260915103000_prospect_sms_tour_booking.sql:275. Raw row deletion never calls that function. The Google cleanup trigger at supabase/migrations/20260915120100_prospect_tour_confirmation_and_google_cleanup.sql:75 and create-intent trigger at supabase/migrations/20260916100500_prospect_tour_google_create_intents.sql:232 run only after UPDATE of row_data. Therefore confirmed bookings and active reservations can remain after their calendar records disappear, and settled remote Google events have no new deletion obligation. The corrected snapshot RPC's tour and null-owner protections are completely bypassed.

Remediation: introduce an explicit schedule deletion authorization contract before any mutation. Reject generic deletion of the shared planned-events singleton, including for ordinary admin cleanup; legitimate per-event deletion must use its authorized lifecycle function. Prevalidate every id in deleteIds before deleting anything. Apply an explicit allowed-role gate to the schedule surface and preserve the existing authorized vendor availability use case. Inspect the companion inquiry singleton, which is exposed by the same scope, rather than merely removing one literal while leaving the shared-snapshot pattern unguarded.

Required regression: exercise the actual exported POST handler as unrelated manager, resident, vendor, and admin with delete, deleteIds, and a mixed batch. Assert rejection occurs before any database deletion; both singleton contents, null-owned rows, other-manager rows, reservations, bookings, and Google cleanup state remain unchanged. Separately prove an authorized per-event tour cancellation/deletion still updates all lifecycle records atomically. Existing tests/unit/portal-schedule-records-atomic-write.test.ts:8 mocks the route factory and invokes only atomicWrite, so it cannot detect this bypass.

S2 - High: the shared GET discloses other managers' prospect contact data

Exact locations: src/app/api/portal-schedule-records/route.ts:53 includes both global schedule singletons. src/lib/portal-record-api.ts:71 reads using the service-role client, lines 80 through 95 return complete row_data without a viewer-aware event projection, and line 96 returns those rows. New SMS tours store attendeeName, optional attendeeEmail, and the trusted texting number as attendeePhone at src/lib/tools/domains/tours.ts:477 and :478, alongside their property and exact tour window.

A signed-in resident or unrelated manager can call GET /api/portal-schedule-records and receive the complete planned-events payload for all portfolios, including the new prospect contacts. No event-id guessing or co-manager grant is necessary. The route has no response normalization callback and the generic GET does not filter nested events. UI filtering after receipt cannot protect this data. Table RLS is also irrelevant to this request because its query uses the service-role client. Middleware does not add an API role/ownership gate.

Remediation: authorize reads by role and project the shared JSON server-side before returning it. Managers should receive only events they own or can access under the repository's explicit property/module grants; residents should use their properly scoped tour surface, and vendors must retain only their own supported availability records. Any public availability requirement should expose an appropriate busy-slot projection without guest contacts. Keep admin-wide reads behind verified admin authority. Apply equivalent protection to the inquiry singleton and preserve the corrected write RPC's protection of rows omitted by the projected view.

Required regression: call the real exported GET handler using two unrelated managers, a resident, a vendor, an admin, and co-managers with absent/read-only grants. Seed distinct prospect contacts and assert unauthorized contacts, property metadata, and event ids never appear in returned JSON. Confirm manager task save still succeeds with its projected observed baseline and does not delete protected events.
