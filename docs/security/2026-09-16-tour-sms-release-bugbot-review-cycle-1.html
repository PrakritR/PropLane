High / P1: A changed-window create is settled before its current window reaches Google

Primary location: src/lib/google-calendar/sync.server.ts:243-265. Supporting code: supabase/migrations/20260916100500_prospect_tour_google_create_intents.sql:125-132,158-162; src/lib/prospect-tour-booking-recovery.server.ts:258-269.

After Google successfully creates the old window, lifecycle-safe ID persistence may return changed. The caller first settles the generation as cleanup_ready, which commits terminal state reconciled and enqueues cleanup. Only afterward does it reload and synchronize the live window. If the process dies or that synchronization fails, the create recovery query excludes the reconciled intent. Ordinary cleanup sees the live tour, correctly refrains from deleting it, and completes its row. Nothing in those durable rows now requires updating the stale remote window.

Deterministic reproduction sequence for the implementation agent:

  1. Create a manager/manual tour at window A and pause the Google insert after durable intent creation. Manual and manager-confirmed tours use this same intent machinery and do not have an SMS booking recovery row.
  2. Reschedule the local tour to B before the insert returns. The trigger changes the intent to reconcile_current. Its immediate reschedule sync cannot start a second create while the first intent is in flight.
  3. Let the original insert commit A. Its ID persistence returns changed; let settle(..., cleanup_ready) commit.
  4. Simulate process death before the live-event reload or recursive sync. Run expired-create recovery and cleanup repeatedly.
  5. The intent is not claimable, cleanup skips deletion because B is live, and Google remains at A indefinitely.

Related false-success path: sync.server.ts:51,218-220,229 converts denied create ownership into null. planned-tour-sync.server.ts:67-75 classifies any fulfilled promise as ok: true. A competing SMS booking recovery therefore writes calendar_sync_status = completed at prospect-tour-booking-recovery.server.ts:103-107 while the create is still unresolved. This also prevents the SMS booking sweep from reliably masking the crash gap. Reschedule callers can report calendar success without a remote update.

Resolution criteria: Preserve a claimable current-window reconciliation obligation until both remote synchronization and lifecycle-safe metadata persistence complete. A changed live event must not become terminal deletion work. Distinguish in-flight/deferred ownership from completed synchronization, and retain pending booking recovery on that outcome. Add provider-sink plus real PostgreSQL coverage for a crash immediately after the stale successful create is settled, including a manual tour and the competing SMS recovery case. Subsequent sweeps must move the deterministic event to B without deleting it; a second move to C must invalidate obsolete completion.

High / P1: Stale browser saves still erase new bookings and strand their reservations

Primary location: src/app/api/portal-schedule-records/route.ts:78-84. Supporting code: src/lib/portal-record-api.ts:135-139,165-171; supabase/migrations/20260915105500_atomic_planned_schedule_generic.sql:104-122.

The slice RPC compares against expectedEvents, but the route derives that expectation from a fresh database read performed while handling the POST, not from the browser snapshot that produced its replacement payload. Therefore the CAS protects only changes made between the route's read and RPC. A booking committed before that read is included in the expectation but absent from a stale browser payload, so the RPC successfully deletes it.

Deterministic reproduction sequence:

  1. Manager browser loads its own planned-event slice containing A.
  2. The SMS booking transaction successfully appends confirmed tour B and creates its active tour_slot_reservations row.
  3. The stale browser POSTs its edited slice containing only A. The route reads current database events A and B and passes those as expectedEvents.
  4. The RPC comparison succeeds and replaces the manager slice with A. B disappears despite the successful booking response.

The generic replacement does not update reservation or booking lifecycle. The cleanup trigger at 20260915120100_prospect_tour_confirmation_and_google_cleanup.sql:57-69 enqueues Google deletion for the removed tour, while its relational reservation stays active and booking stays confirmed. Public availability reads the JSON calendar and can advertise the slot, but the booking RPC then rejects it against the ghost reservation. Normal cancellation cannot find the missing event to release it.

Resolution criteria: Require an actual client-observed version/snapshot, use per-event operations, or preserve server-owned tours on generic calendar saves. The server must not manufacture its optimistic concurrency expectation from its own latest read. Generic event removal/replacement must atomically maintain the same reservation, booking, and Google lifecycle invariants as the confirmed-tour mutation path. Add route-level and real PostgreSQL regressions for booking B both before the route read and after the route read. A stale save must return a conflict or preserve B, and deliberate authorized deletion must release the reservation and close the booking in the same transaction.

Reviewed safeguards and limits

The canceled-create path retains a durable tombstone after its first post-expiry 404; later sweeps can remove a delayed create. Expired reconciling claims are reclaimable. The trigger ignores metadata-only ID persistence while invalidating real window changes. Deterministic create conflicts patch the submitted body after 409, and ordinary cleanup skips a live rescheduled event. These safeguards are present in source and covered by supplied tests, but this reviewer did not execute those tests. The terminal-settlement gap above remains outside the covered canceled-create scenario.

Manual and SMS append RPCs share the advisory lock and inspect both current planned events and reservations. The generic slice route remains an escape from their lifecycle guarantees. Reminder claim, dedupe, newer-inbound invalidation, and final submission checks were inspected; no additional reminder finding is asserted in this report. Review does not certify deployed cron execution, provider behavior, or browser QA.
