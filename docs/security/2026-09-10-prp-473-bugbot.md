## Findings

### P1: Non-SMS origin is lost before planned-tour lifecycle authorization

Changed location: `src/lib/tour-notification-delivery.server.ts:525-527`.

The new `undefined` compatibility branch treats a planned event created today as a legacy SMS-eligible inquiry because the provenance is dropped twice: `confirmTourInquiry` constructs its planned event with `smsConsent` but without `smsOrigin` (`src/lib/tour-inquiry-confirm.server.ts:279-305`), and `inquiryFromPlannedEvent` independently constructs the notification payload without `smsOrigin` (`src/lib/tour-planned-change.server.ts:47-59`). A new voice/email/web request with `smsConsent:false` is correctly stamped `smsOrigin:"non_sms"` on create and correctly denied conversation evidence while pending. After manager confirmation, reschedule or cancellation admits the same recipient's historic conversation grant and sends SMS. That defeats the deliberate origin isolation introduced by this change and required by the plan.

Carry server-owned provenance through both inquiry-to-event and event-to-notification projections, with behavioral coverage for create -> confirm -> planned reschedule/cancel on voice/email requests and unchecked web requests. Tests that inspect only `createTourInquiry` arguments do not exercise the loss.

### P1: START-derived tour grants bypass a subsequent source-conversation revoke

Changed location: `src/lib/sms/tour-sms-eligibility.server.ts:112-129`.

The materialization branch accepts `manager_conversation` grants whose source is `twilio_start` and preserves that source when writing the derived tour-purpose grant (lines 150-166). On a later send, however, the existing-purpose branch rechecks the source conversation only for `recipient_initiated_inbound`. A derived `twilio_start` grant is accepted directly even when the current source conversation is revoked. This is the same revoke-after-derived-grant failure that the new test covers for the other source. Global STOP still blocks; the defect concerns a scoped conversation revoke with global suppression clear.

Preserve/read derivation evidence and revalidate every conversation-derived grant, including a START-restored source. Direct purpose restoration and conversation-derived restoration may need distinct treatment; source alone currently loses that distinction.

Independent hermetic execution of the actual transpiled resolver with an existing `tour_rescheduled/granted/twilio_start` event and newer `manager_conversation/revoked` event returned `eligible:true, provenance:"twilio_start"`; the DB stub recorded zero current-conversation reads. Only imported consent primitives and DB responses were substituted. No provider or database was contacted.

### P2: Deployment invalidates pending SMS proposals created by the existing version

Changed location: `src/lib/tour-reschedule-sms-reply.server.ts:265-269`, also lines 206-210, 300-304, 227-230, and 364-368.

Every YES match now requires the newly introduced `guestRescheduleReply.smsEligibility === "eligible"`. Proposals persisted by the base implementation never have that field, even when `smsConsent:true` and all existing owner, phone-pair, generation, and window checks pass. A recipient answering a real pre-deployment reschedule SMS is told the update is stale and their confirmation is not saved. Retrying the same notification does not repair it: proposal recording returns success immediately for the existing generation/version (lines 143-148), without adding the new evidence.

Add a safely revalidated compatibility path for old actionable proposals or a CAS upgrade that preserves their original generation and work-number snapshot. Do not infer eligibility solely from the absent field.

Independent hermetic execution of the actual transpiled reply module against a pre-change proposal returned `kind:"stale"` for YES. Repeating `recordTourRescheduleSmsProposal` with its identical generation returned `true`, performed zero row writes, and left `smsEligibility` absent. The existing test named `rechecks authorization and the exact window inside the CAS` also supplies an old-shaped proposal without this field; it now rejects before reaching the intended CAS race and therefore no longer validates that behavior.
