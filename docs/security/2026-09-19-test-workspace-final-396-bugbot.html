Findings

P2, medium, original finding closed in the scoped addendum: a failed SMS turn can leave the previous turn's delivery evidence presented as current

Trigger: complete one successful SMS test turn that reports captured or refused effects, then issue another turn in the same selected listing and session that returns a non-2xx response or throws a network error.

Evidence: use-assistant-conversation.ts clears the ordinary error and tool state when a send begins, but does not clear lastSmsTestTurn. It updates that value only in the success branch. The non-2xx branch restores attachments and sets an error without clearing SMS metadata; the catch path also leaves it intact. assistant-sms-test-control.tsx considers metadata current whenever its target and session still match, then continues to render the prior effects under the unqualified heading “Test delivery evidence.”

Impact: a tester can see an error for the newest request while the control still displays “Captured” evidence from the preceding successful request. This can misattribute an earlier email or SMS capture to the failed turn and weaken the release evidence the feature is intended to provide.

Correction: clear the current SMS-turn metadata when a new request begins, or associate metadata with a client turn/request id and render it only beside that completed turn. Add a focused success-then-failure test for the same target and session.

P3, low, original finding closed by the scoped one-file follow-up: asynchronous attachment preparation is not invalidated when SMS mode becomes text-only

Trigger: begin processing an image or PDF in ordinary assistant mode, then activate SMS test mode before prepareChatAttachmentsFromFiles resolves.

Evidence: assistant-chat-composer.tsx checks allowAttachments before the await, but does not recheck a generation or current-mode ref after the await. The stale closure can therefore call onAttachmentsChange or report an attachment error after SMS mode has become active. The passive cleanup effect normally removes the late attachment, and the SMS route independently rejects non-empty attachment payloads.

Impact: this is fail-closed on the server, but it can briefly repopulate stale state or turn a valid SMS text attempt into a 400 response if submission interleaves before cleanup. It can also surface an irrelevant attachment error in SMS mode.

Correction: increment an attachment-preparation generation when allowAttachments changes and discard prepared results from older generations. Cover the deferred-preparation mode switch in a client unit test.

P3, low, retained: envelope validation has a local lstat/read race

Evidence: decrypt-local-qa-build.mjs validates manifest.json with lstat, then opens it independently through readFile. A same-user process with write access to the task-owned artifact directory could replace the file between those operations. This finding was already recorded in the fresh encrypted-artifact review and is unchanged by the runtime-alias refinement.

Impact: the envelope remains bounded to 4 KiB, exact-schema checked, SHA-bound, and its values feed AES-GCM authentication, so this does not create an authentication bypass. It is a local robustness gap in a task-private workflow.

Correction: open once with O_NOFOLLOW, validate the opened handle, read at most 4097 bytes from that handle, and compare the opened identity rather than doing a path-based second read.
