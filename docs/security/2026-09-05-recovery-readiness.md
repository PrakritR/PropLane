# Production encryption maintenance and recovery readiness

Date: 2026-09-05. Source review and synthetic verification; this report does not assert that production backfills, strict cutover, or a production restore have completed. Production deployment/configuration evidence belongs in the rollout report.

## Reviewed operator implementation

- `scripts/security/production-database.mjs`: a separate, fixed production project (`qahnczmilgptcedaqype`) helper. CLI 2.116.0 dry-run login output stays in memory. Exact project-bound CLI identity, endpoint, port 5432 and database are checked; TLS requires certificate and hostname verification. Nonproduction helpers remain unchanged.
- `scripts/security/production-schema.mjs`: only five SHA-256-pinned security migrations, explicit apply/target confirmation, exact migration history, metadata prerequisites, and postconditions in one transaction. Untracked objects or drift stop execution. Preserves existing profile row grants while removing dangerous grants. Independently reviewed; no blocker found within this fixed migration scope.
- `scripts/security/production-backfills.ts`: one of `applicant`, `cosigner`, `calendar`, `document`; dry run by default. Apply requires `--apply --confirm-project=qahnczmilgptcedaqype --backup-dir=/absolute/private/directory`. No arbitrary database, SQL, table or object arguments. Requires exact name and source statements for all five migration-history entries before inventory/backfill. Uses the existing pure transformations and resumable document migration helper.
- `scripts/security/production-backup.ts`: AES-256-GCM archive using the existing versioned keyring and a separate backup-purpose context. Ciphertext-only exclusive mode-0600 file inside an operator-owned mode-0700 directory; file/directory fsync and authentication of the persisted archive before mutation. Database snapshots include four fixed application/co-signer/calendar/alias tables. Document runs additionally include bytes, paths, MIME types and SHA-256 hashes for objects in current application folders. Paths and row data appear only inside the encrypted archive.
- `scripts/security/production-verify-backup.ts`: offline decrypt/authentication and object-checksum verification; prints only counts and the encrypted archive checksum. It never restores rows or contacts a provider.

Fixed limits are 10,000 rows per table, 1,000 objects total, fewer than 1,000 entries in each application folder, 15 MB plus framing per object, 32 MiB of downloaded object bytes total, and 64 MiB serialized snapshot content. Exceeding limits stops the run; increasing them requires another review. Aggregate database size is checked before retrieving complete rows. These limits deliberately make this a bounded maintenance tool, not a general backup system.

Database apply snapshots the affected rows while holding `FOR UPDATE` locks in the same repeatable-read transaction as transformation and commit. Concurrent inserts are left for another run; conflicting updates may safely force a retry. Document runs back up their inventory before any migration, check that each legacy source still matches its backed-up hash, then retain existing per-object locking, verified upload, alias commit and original-removal ordering. New objects require another inventory pass. This depends on the application's immutable object-path contract; it does not impose or claim a global write pause. A failed document run can have committed earlier objects and must be resumed, not treated as wholly rolled back.

## Execution sequence

Load production runtime credentials and all required production encryption-key versions through the operator's private secret mechanism. Never echo environment files or keys. Use the bundled public CA via `SUPABASE_DB_SSL_CA_FILE`. Serialize CLI-backed operations because issuing another ephemeral login may interfere with an active connection; prior contention was suspected, not proven.

1. Dedicated staging QA must sign off, and production must run the reviewed encryption-compatible release before backfilling. Verify effective production secrets and TLS enforcement separately.
2. Run `node scripts/security/production-schema.mjs` for metadata-only dry run; review the aggregate plan. Apply only through the explicitly authorized command `node scripts/security/production-schema.mjs --apply --confirm-project=qahnczmilgptcedaqype`. Re-run dry run and require five matching histories and valid boundaries.
3. For each kind, sequentially run `npx tsx --conditions=react-server scripts/security/production-backfills.ts KIND`. These dry runs read sensitive data privately and validate existing ciphertext; only aggregate results are printed. They perform no DB/Storage writes, though the login service creates ephemeral credentials.
4. For each reviewed inventory, run the same command with `--apply --confirm-project=qahnczmilgptcedaqype --backup-dir=/absolute/private/directory`. Retain each reported archive/checksum in protected backup storage. The runner authenticates its persisted backup before mutations. It does not verify independent organizational key escrow.
5. Re-run all four dry runs. Require zero changed rows/plaintext fields and zero legacy document candidates, cleanup pending, or deleted-parent discrepancies. Check zero counts against the inventory scope; do not interpret an empty table as a successful sample decryption.
6. Verify independently recovered keys can authenticate the saved archives with `npx tsx --conditions=react-server scripts/security/production-verify-backup.ts /absolute/archive.json.enc`. Keep output aggregate-only. A successful archive authentication is not a database/object restore drill.
7. After inventory and authorized application read/write checks pass, enable the four strict read flags in the effective production deployment: `APPLICANT_IDENTITY_REQUIRE_ENCRYPTED_READS=true`, `COSIGNER_IDENTITY_REQUIRE_ENCRYPTED_READS=true`, `DATA_ENCRYPTION_REQUIRE_ENCRYPTED_READS=true`, and `DATA_ENCRYPTION_REQUIRE_ENCRYPTED_DOCUMENT_READS=true`. Recheck authorized reads, uploads and OAuth paths against that exact release. Do not rollback to code unable to read ciphertext.

An applicant with no nonempty protected fields may intentionally have no envelope. Co-signer metadata may exist while all protected fields are empty. Neither case demonstrates recovery of a real encrypted value. Document inventory covers current application folders, including unreferenced files in those folders, but not orphaned application folders or other buckets. A zero-candidate result does not prove all Storage objects are encrypted.

## Key recovery and restore verification still required

- Store every referenced `DATA_ENCRYPTION_KEYS_JSON` key version in an independent, access-controlled recovery location separate from database/object backups. Preserve the active-key ID and archive versions. Keep historical keys until every live ciphertext and retained backup that needs them has expired or been migrated. A secret copied to another file on the same laptop is not independent recovery.
- Inventory `FINANCIALS_TIN_ENCRYPTION_KEY` separately (`src/lib/reports/tin-crypto.ts`); its existing format is not the versioned application keyring. Recovery of the new keyring does not recover TIN ciphertext without that other key.
- Run an isolated restore drill with synthetic application, co-signer, calendar and document fixtures. Restore exact primary IDs, origin metadata, storage paths and aliases; authenticated encryption binds to them. Verify decryption after loading keys from the independent recovery source, wrong/missing-key failure, ciphertext tamper rejection, and old-key recovery after rotating to a new active key. Keep external email/SMS/OAuth calls disabled.
- Then define and test a controlled production-backup recovery procedure in an isolated recovery environment, with access approved for that data. Never place the production key in shared staging merely to make a clone readable. The new tool verifies archives but intentionally offers no general production restore/write command.
- Verify actual provider backup availability, retention, Storage-object coverage and restoration procedure for the current plan; no provider control-plane backup verification was performed here. Record tested recovery time and acceptable data-loss window after the drill. Do not promise either beforehand.
