## Findings

### SEC-470-1 - Medium / P2: an obsolete SMS authorization failure can permanently block the new viewer's entire inbox

Locations: `src/components/portal/pro-unified-inbox.tsx:315`, `:318`, `:326`, `:374`, `:380`.

`loadSms` mutates `smsPollHaltedRef` and `smsPollHalted` on 401/403 immediately after `fetch`, before checking the captured viewer epoch or request generation. Its initial early return then makes every later call resolve `false`. Neither the viewer-change effect at line 240 nor the initial loader resets the latch. The new initial readiness condition requires `smsOk`, so the previous SMS-only polling halt now also prevents successfully loaded email conversations and contacts from being displayed.

Concrete sequence with SMS enabled and the component retained across a session change: A's SMS request is in flight; A changes to B; A's response returns 401 before B's initial request starts, or A was already halted when B signs in. B's email and application requests succeed, but its SMS loader returns `false` without requesting B's data. Initial state becomes `error`. Clicking Retry repeats that result indefinitely until a remount. A stale 401 arriving while B has an outstanding request can likewise poison subsequent retries/polling even if that outstanding request succeeds.

Required correction: reject stale responses before any status-driven mutation, retain the post-JSON guard, and scope/reset the halt latch to the current viewer/session. Preserve auth-failure polling suppression within the same rejected session. Add deferred-response coverage for old A 401 and 403, already-halted A changing to B, and successful B loading/retry. The current A-B-A SMS test only resolves successful JSON and does not cover this status branch.

Resolution: unresolved in the reviewed diff.

### SEC-470-2 - Medium: pre-existing empty saved SMS contacts can survive account replacement

Locations: `src/components/portal/pro-unified-inbox.tsx:226`, `:240`, `:333`, `:345`, `:351`, `:568`.

This is an existing state-isolation gap, not a newly introduced disclosure. The new readiness/epoch guards do not close it. The viewer-change effect advances an epoch but retains `smsResidents`. A successful B response merges every old current row with a saved contact name, no messages, and no matching server key into B's rows as `pendingOptimistic`. The condition does not establish that the contact is an unsaved contact belonging to B; it also matches already-loaded A contacts. Once B's sources succeed, the readiness gate displays those retained rows. With normal unfiltered Communication, `allSmsItems` maps the retained contact into its display name/subtitle/phone context.

Concrete sequence: A successfully loads a saved empty SMS contact; the same mounted component changes to B; B successfully receives an empty SMS list. A's contact remains in the merged list. This discloses contact metadata, not message bodies in the demonstrated path. It requires an account change without component remount and SMS enabled. The existing deferred A-B-A test covers an old response arriving late, not old data already accepted into React state.

Recommended correction: clear viewer-owned SMS state on account changes and bind optimistic contact retention to the viewer that created it. Add a test that first displays A's empty named contact, switches to B, completes all B sources, and asserts A's contact is absent. Avoid relying only on guarding late fetches.

Resolution: unresolved existing limitation; reported separately from the regression above.

## Checks without new findings

- The inbox storage generation and captured viewer cache key are checked before `notePortalResponse`, after JSON, and in rejection handling. The promise identity check in `finally` protects a newer same-key request from an older request's cleanup. These address stale success, stale auth failure, and A-B-A cache publication.

Successful server timestamps are distinct from local mutations. Existing scope semantics, including the single application cache's treatment of `selfScope`, were not changed by this patch.
