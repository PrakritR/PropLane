## Security and behavior reviewed

- Email onboarding creates an unconfirmed account with an unknown password, sends a browser-independent `token_hash` link, and binds the finalizer to the verified Auth subject and exact server-owned handoff. The first-confirmation Auth trigger retires a password planted before mailbox proof, including direct GoTrue verification. Confirmed users are not rotated. Application setup locks the exact application and requires its original token, live recipient, and confirmed Auth mailbox. Other same-email applications are not adopted.
- Tour return uses a hashed, expiring capability minted from a trusted inquiry. A service-only preclaim precedes Auth token generation; a compare-and-set binds the returned digest to that handoff. A verified subject and eligible inquiry must match at finish. Same-token retry is idempotent; a different subject cannot claim the link. Concurrent generic starts still have Auth's newest-token-wins behavior; the recent-handoff cooldown avoids an unnecessary sequential mint.
- Paid manager provisioning claims only the exact verified Checkout purchase and preserves a live `cs_` reservation until asynchronous payment completes. A read-only legacy entitlement can route an existing stored manager role after confirmed Auth mailbox proof; it never claims an unbound purchase or grants a role. An unauthenticated `axis_intent` row cannot block legitimate free onboarding. Provider read errors fail closed. Email search alone is not purchase ownership authority.
- Manager, resident, vendor, and admin APIs use stored `profile_roles`, exact Auth subjects, scoped grants, and explicit admin oversight. User metadata and legacy `profiles.role` no longer grant API capabilities. Exact subject-owned applications, charges, leases, tours, services, and move-in forms remain available without a confirmed email; email-only historical inheritance requires mailbox proof. Legacy unbound service rows remain manager records and cannot be reassigned by address reuse. The managed read-only SQL function now honors stored admin role rather than matching profile email.
- New resident service/work-order rows stamp immutable `resident_user_id` from the trusted actor. Vendor direct PostgREST SELECT on those tables was removed. The route must preserve an assigned vendor's intended job/contact details and an offered vendor's general area, without raw Auth identifiers or resident financial fields.
- The public onboarding start applies IP and normalized-recipient limits before account or mail work, generic responses, and a 16 KiB incremental UTF-8 byte cap. Missing/false `Content-Length`, oversized multibyte input, malformed UTF-8, and reader failure return before Auth or provider calls. The sender-health endpoint performs read-only exact-domain verification behind `CRON_SECRET`; HTTP 200 alone is not a verified sender result.
- Move-in forms use an exact service-only subject claim synchronized with the form writer. The 144900 recovery hooks let the same subject recover without deleting forms. The initial hosted failure before that migration and the successful corrected run are separate evidence. No historical email-only form adoption was added.
