- Manager, resident, vendor, and admin APIs use stored `profile_roles`, exact Auth subjects, scoped grants, and explicit admin oversight. User metadata and legacy `profiles.role` no longer grant API capabilities. Exact subject-owned applications, charges, leases, tours, services, and move-in forms remain available without a confirmed email; email-only historical inheritance requires mailbox proof. The route must preserve an assigned vendor's intended job/contact details and an offered vendor's general area, without raw Auth identifiers or resident financial fields.

Missing/false `Content-Length`, oversized multibyte input, malformed UTF-8, and reader failure return before Auth or provider calls. ## Deliberate limitation: a pre-release row with no bound subject stays manager-only

**There is no backfill, and this release ships no one-shot script for one.** A draft
`bind-existing-resident-subjects-20261030.sql` was written in an earlier fix round and then
**retracted by the release owner**: the production rows that carry no `resident_user_id` are
placeholder and demo accounts that never signed in, so there is no resident to hand them to. The
peer PROD inventory bounds it at 12 work orders (nine import/demo placeholders, three internal
test-account items).

So the standing rule for pre-release data is:

- A `portal_work_order_records` / `portal_service_request_records` row with `resident_user_id` null,
  and a `manager_application_records` row with no `row_data.residentUserId`, stay **manager-only**.
  The manager keeps full access to every one of them — nothing is hidden from the workspace that
  owns it; only the resident-scoped reads skip them.
- **Nothing is bound from an email.** An address is not proof of control, which is the whole point of
  this release, and 20261030144600's `sync_resident_service_subject` trigger refuses any null →
  non-null assignment after insert. That trigger is **never disabled** — not by a migration, not by a
  script, not by application code.
- A resident who proves their mailbox through the email-proof setup is bound going forward
  (`bind_resident_setup_subject`), and a manager-filed service for a resident already bound to that
  manager + house is bound at INSERT. Neither path reaches backwards.

If a specific pre-release row ever does need a subject, it is an owner-authorized, individually
reviewed operation against named ids — not a sweep, and not something this release performs.
