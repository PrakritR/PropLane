High: a late original PATCH can undo completed current-window recovery

Location: src/lib/google-calendar/sync.server.ts:303, :311, :344; supabase/migrations/20260916101000_prospect_tour_google_changed_window_reconciliation.sql:36.

The correction releases a stale successful create into immediately claimable reconcile_current, clears its lease, and sets provider_deadline_at=now(). The original request nevertheless starts its own recursive current-window update. That recursive call supplies the deterministic remote ID and does not acquire a reconciliation claim. A sweeper can therefore update the same Google event concurrently. The local expected-window CAS protects the database after the remote write; it does not order or fence those remote writes.

StepOriginal requestSchedule / recovery
1Create A is in flight.Move the live local tour A to B.
2Create A returns; persist-ID CAS rejects A. Settlement exposes a reclaimable intent. Recursive PATCH B starts and is paused before the sink applies it.Intent is reconcile_current with an expired deadline.
3PATCH B remains pending.Move B to C. Sweep claims the intent, loads C, PATCHes C, persists its ID, and completes the claim as settled.
4Release PATCH B so it overwrites C remotely. Its persist-ID CAS rejects B as changed. Recursive allowReconcile=false throws.Database stays C. Intent remains terminal settled. Google is now B.

This does not require an expired provider request or a crash. The overlap can occur within normal request deadlines. Use a manual or manager-approved tour with no prospect-booking row to avoid relying on an unrelated booking recovery effect. The reschedule to C can also complete its own current sync before the paused B update is released.

Why existing guards do not recover: the recursive invocation has its own createGeneration=null and takes the existing-ID update path (sync.server.ts:48-56). Its changed result throws at lines 344-348 without a durable requeue. The outer invocation never reaches its final current-window settlement at lines 328-336. Sweeper completion at prospect-tour-booking-recovery.server.ts:331-340 legitimately settled before the late write. Claim SQL selects only nonterminal states (20260916100500_prospect_tour_google_create_intents.sql:159-161). Google PATCH has no conditional version header (api.server.ts:682-692).

Correction: give every external current-event write durable, exclusive ownership and prevent an unclaimed original follow-up from running beside a sweeper. Handle late/stale successful writes by durably restoring the obligation to reconcile the current window, even if a newer worker already settled it. Design the recovery for expired-lease writers as well; a database claim alone does not fence an already issued remote request. Do not terminally settle while a known older write can still change the sink.

Required deterministic test: run the real synchronization and recovery functions against PostgreSQL RPCs and a controllable provider sink. Pause PATCH B before applying its body; complete C, its ID CAS and claim settlement; then apply and release B. Assert eventual remote window C, local C, and that the intent is either still recoverable until convergence or terminal only after convergence. Repeat with a recovery worker whose lease is replaced, then with a second sweep. No real Google calls. The expired-worker variant follows the same un-fenced external-write structure; it was not separately executed here.

Coverage gap: prospect-tour-google-id-persistence.test.ts:131 and :180 mock RPC results and immediate provider completion. prospect-tour-booking.test.ts:1484 proves claimability and exact-window settlement separately, manually resetting intent state at line 1511; it does not place two provider writes around a completed settlement. Existing late-create tests concern canceled-event tombstones, not this live-event overwrite.

Medium: conflict recovery can loop forever through real task projection

Location: src/lib/demo-admin-scheduling.ts:322-326, :393, :755-761; src/lib/manager-tasks.ts:404-408.

Every failed planned-event POST triggers a forced schedule GET. Every successful GET dynamically calls the real task reapplication function. When any manager task cache exists, that function calls replaceManagerTaskPlannedEvents, which unconditionally schedules another POST, even if its projection did not change. A persistent 409 or 503 with healthy GETs therefore produces POST failure → GET success → task reapply → POST failure indefinitely. Forced GETs bypass both TTL and in-flight checks at lines 349-356. Promise serialization limits ordering, not the total number of requests.

The caller is ordinary portal usage: fetchManagerTasks fills the task cache and applies it to the calendar (manager-tasks.ts:439-441). A missing schedule RPC returns a persistent error through the route. A second concrete case is a missing singleton with nonempty task cache: successful GET rows:[] never records an observed empty baseline or clears optimistic planned data, so a rejected first write leaves subsequent retries comparing local nonempty events to an empty server slice. This consumes repeated authenticated reads/writes and can leave the calendar appearing locally saved without durable persistence.

Correction: bound and coalesce conflict refresh, make server refresh/task projection avoid re-emitting unchanged writes, and stop automatic retry after persistent failure. Track a successful observation of an absent singleton explicitly; optimistic values must not become an acknowledged server baseline merely because a prior write failed. Surface an actionable failure to the task/calendar caller. Preserve tour lifecycle protection and per-manager CAS.

Required test: import the real scheduling and manager-task modules, seed task cache via its public fetch path, return healthy schedule GETs and persistent POST 409/503 responses, and use a capped fake transport to detect excess requests deterministically. Assert a bounded request count, no detached retry loop, and observable failure. Also cover GET with absent singleton, no-op projection, two queued local saves where the first conflicts, and recovery after a later successful reload. The current baseline unit test explicitly mocks manager-tasks at line 10, removing the callback that closes this loop.

What the correction does protect

The snapshot RPC now compares the supplied browser slice and preserves server-owned tour rows, other managers' rows, and null/missing-owner rows using NULL-safe comparisons. Admin non-tour writes have a separate explicit branch. These address the previous upsert-path lost-tour and ownership findings. Production manual tour creation uses its dedicated route; inquiry acceptance routes tours through the dedicated accept endpoint. Those facts do not establish that the entire generic record protocol is safe: the parallel security reviewer owns the raw singleton read/delete issues.
