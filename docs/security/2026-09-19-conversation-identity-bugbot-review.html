B35: explicit resident Unread filter retains a read routed row

Severity: Medium. Resolution: open. Location: src/components/portal/resident-communication.tsx:659-670, with route selection effects at :746-750 and :817-837.

Trigger: open an already-read resident conversation so it has an active thread route, then apply Unread from the actual status filter. The merged result admits row.unread || row.key === selectedKey without establishing that the row was admitted as unread in the current filter context. Although the list-segment effect clears the selection, subsequent route effects in that same flush select the routed row again from the retained merged result. The read conversation therefore remains in Unread and stays open. Search/context changes can similarly reuse a selection without the bounded admission used by the manager implementation.

Fix: retain a just-read selection only after it was visibly admitted as unread in the same viewer, status/folder and search context. Resolve identity through accepted members so representative changes are safe. Clear a resolved route when an explicit presentation change excludes it, while preserving genuinely pending deep links. Mirror the manager admission contract rather than using selection alone as proof. Add a resident behavioral test that opens a read route, applies Unread, and requires both row/pane removal and route clearing; retain coverage for an actually unread row becoming read while open.
