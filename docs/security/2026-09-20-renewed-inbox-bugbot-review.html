P2: failed manager reply restores an obsolete approval draft

src/components/portal/pro-inbox.tsx:1004, especially 1012-1019.

Start sending with active draft A. Before the request fails, a cache event updates the same thread's active draft or its metadata without changing the message count. The cache listener publishes that current row. When delivery is refused, rollback filters out the optimistic reply and uses equal message counts as proof that nothing else changed. It then replaces the current aiDraft with captured A, while leaving the current queue and resolved IDs in place. The UI can therefore offer an obsolete or already resolved A beside the newer queue. The optimistic append no longer changes the draft at all, so there is no draft contribution for this rollback to restore. The same count heuristic also restores a newer unread-only change to the old value.

Required correction: remove restoration of draft state from reply rollback. Reconcile only fields this particular optimistic reply changed, preserving newer cache fields, and do nothing to a row whose optimistic message has already been replaced by an authoritative cache snapshot. Add a deferred refusal test that publishes a newer active draft/metadata and unread value without adding a message, then asserts rendered draft state and storage. Do not assert only against the fixture array.

P2: thread navigation prevents reconciliation of a successfully delivered reply

src/components/portal/pro-inbox.tsx:1161, src/components/portal/resident-inbox-panel.tsx:1156, src/components/portal/vendor-inbox-panel.tsx:798.

Start approving draft A in X with B/C queued, then open Y while the send is pending. When delivery succeeds, the new conversation-generation check returns before the current-cache merge, before advanceInboxAiDraft, and before the final refresh. Returning to X leaves A unconsumed even though its message was delivered; approving again can send A twice. The send route does not perform this client-owned draft advancement. The equivalent resident/vendor return also skips their accepted-reply bookkeeping and refresh. The X-to-Y-to-X generation fix correctly protects newer composer text, but applying that lifetime to the delivered outcome discards necessary reconciliation for the initiating conversation.

Required correction: use the initiating viewer/session ownership to authorize current-cache reconciliation for the original source thread, even after navigation. Preserve conversation and attempt ownership for composer clearing, busy state, errors and other active-thread UI effects. Consume only the approved draft identity once, using current storage. Add deferred all-role send/navigation tests that verify the delivered source-thread result survives while the newly selected composer stays intact, and a manager approval test that proves A is resolved and B/C retained after X-to-Y and X-to-Y-to-X.
