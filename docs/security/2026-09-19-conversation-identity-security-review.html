S1 - High - resident relay history remains authorized by phone alone

src/lib/manager-sms-messages.server.ts:1321-1388 reads active resident relay bindings by verified phone, fetches messages for every bound thread, and appends each message to the returned flat messages array before checking counterparty_user_id === residentUserId. The later check protects only the new named-conversation array. The resident endpoint uses a service-role client, so RLS does not independently eliminate another resident's turns. A resident controlling a shared or recycled verified number can receive the other resident's still-active relay history. The new unknown SMS timeline explicitly retains and renders those rejected grouping members. Hiding the SMS UI does not protect the callable API.

Required fix: resolve relay threads first, admit only records whose exact counterparty user ID matches the authenticated resident, then query/return messages only from those thread IDs. Missing identity or failed authorization reads must not return flat fallback history. Preserve the flat feed only for authorized turns. Regression cases should include a shared verified phone with different counterpart user IDs, a null-counterparty legacy thread, and a failed thread lookup; assert both payload arrays exclude unauthorized bodies. Status: unresolved; coordinator notified.

S2 - Medium - stored identity metadata is still client-writable

src/app/api/portal-inbox-threads/route.ts:310-382 and src/lib/portal-inbox-thread-upsert.ts preserve client-provided managerUserId, propertyId, counterpartyRole, smsConversationKey, and identityProvenance in ordinary person rows. New send/folding code describes these as server-stamped provenance, but a caller can create an owned source row or overwrite an authorized ordinary row with those claims and then select that row in send. Recipient-scope checks still constrain the actual recipient, so this review did not establish arbitrary-recipient delivery or reading another owner's content from this issue alone. It does permit false relationship metadata to propagate into recipient copies and weakens the integrity of the new partition contract.

Recommended correction: exclude protected identity fields from client upserts, preserve authoritative existing values on ordinary-row updates, and derive any new relationship from server records. Add a route-level forged-provenance regression. Status: unresolved hardening finding; Medium alone does not block this repository's Critical/High gate.
