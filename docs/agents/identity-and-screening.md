# Identity and applicant screening

Captain decision (Nov 12, 2026). Applications, leases and tours stay FREE. Two optional checks sit beside them, each its own per-listing setting, and the manager chooses which of them an applicant completes **before the application form opens** (§ Before applying).

## The two checks

| Check | Provider | Who pays | Where it runs |
| --- | --- | --- | --- |
| Verify ID (government ID + live selfie) | Checkr's `identity_verification` add-on, **$2.95** (`checkr/packages.ts`), or Persona's standalone flow when `RESIDENT_IDENTITY_PROVIDER=persona` and its keys exist | The applicant, inside the same Checkout as the order (Checkr); Persona is not billed here | Before the application opens: `POST /api/screening/preapply/checkout` (Checkr) or `/resident/profile#verification` (Persona) |
| Applicant background check | Checkr **Starter** ($24.99: criminal, sex-offender, global watchlist) | The applicant, through PropLane Stripe Checkout, total shown before they confirm | Before the application opens: `POST /api/screening/preapply/checkout`; after it, `POST /api/screening/applicant-checkout` for an application that was submitted before the requirement existed |

Checkr has no ID-only product, so a listing with only "Verify ID" on still orders Starter + the add-on (the cheapest orderable). The per-check fee model is the existing one: package and add-on prices come from the Checkr catalog (`checkrPackageCatalog` / `checkrAddOnCatalog`, env overridable); the applicant pays the order total.

**Upgrade.** A manager can upgrade a specific applicant to Essential ($34.99) or Complete ($44.99) from the existing manager screening checkout. The charge is the package DIFFERENCE only (`checkrUpgradeCostCents`), billed to the manager, because today's screening settings make the manager the payer of a manager-initiated order. The upgrade replaces exactly the completed applicant-paid check (`upgrade_from_package` is re-verified at order time), and the ID result is carried over (`carriedIdentity`), never re-bought. Checkr itself bills the full new order to PropLane's Checkr account; the difference is what the customer pays.

## Settings

`applicantScreening` namespace (`{ idCheck, backgroundCheck, idUnlock }`), property override then workspace row then default: **both OFF for every workspace until the manager turns them on** (captain, Nov 12), `idUnlock` `clear`. Resolver `resolveApplicantScreeningSettings`; route `/api/portal/applicant-screening-settings`; UI is one multi-select **Before applying** (Verify ID, Background check: either, both or none) plus, with Verify ID on, an **Application opens once** dropdown (ID is verified | Check is ordered), in Settings > Automations > Screening, following the scope bar (a listing's own choice beats the workspace's). No settings migration.

## Provider switch

`RESIDENT_IDENTITY_PROVIDER`: unset or `checkr` (default), `persona` (the existing inquiry flow, only with its keys), anything else resolves to `null` and fails closed. `RESIDENT_IDENTITY_ENABLED=true` is the master switch for the ID check. `applicantIdCheckAvailable()` is the one answer; a listing that turned Verify ID on while it is false shows **"ID check unavailable"**, creates no Checkout session and never marks anyone verified. "Verified" is derived only from Checkr's re-fetched report (`applicationIdentityVerified`: complete + add-on ordered + `identity_verification.status === "clear"`), drawn as a plain glyph fact, never a pill.

**Stripe Identity is NOT a provider.** Its activation terms bar using it "to determine eligibility for any purpose covered by the US Fair Credit Reporting Act (FCRA)", and tenant screening is such a purpose. `RESIDENT_IDENTITY_PROVIDER=stripe` is refused. If it is ever added it may back only non-eligibility fraud/trust checks, never applications, screening or lease decisions.

**No ID evidence is stored.** The application row keeps the product status and reasons only (`parseCheckrReportSnapshot`); images and document numbers stay at Checkr.

## FCRA authorization

The applicant card shows the standalone disclosure and an explicit authorization checkbox before the Pay button works. The server refuses (`authorization_required`) without `authorize: true` and the current `FCRA_DISCLOSURE_VERSION`; the authorization (version + timestamp) goes into the Stripe session metadata and onto `backgroundCheck.authorization`. The disclosure wording in `applicant-screening.ts` needs counsel review before live rollout.

The same authorization and disclosure apply to the pre-apply order (`/api/screening/preapply/checkout` refuses with `authorization_required` exactly like the post-application route).

## Before applying (pre-apply requirements)

What the applicant completes BEFORE the application form opens, the manager's choice per listing: Verify ID, Background check, either, both or none. The pure rules are `screening/preapply.ts` (plan + progress), the I/O is `screening/preapply.server.ts`, the screen is `ResidentPreApplyGate` (wraps the wizard at its three portal mounts: `resident-application-workspace.tsx`, `resident-applications-panel.tsx` x2).

- **One step list**, Verify ID -> Background check -> Application, a status per step (To do, In progress/Ordered, Done, Needs review, Unavailable). Coming back later lands on the next unsatisfied step (`next`); a pending check polls every 8 s and on tab focus. A signed-in resident account is required (existing rule): a signed-out submit for a listing that requires anything is refused (`preApplyGuestGate`).
- **Checkr** (default): the ID add-on only exists inside an order, so "Verify ID first" is ONE payment for Starter + ID (`$27.94`; Starter alone `$24.99` for a background-check-only listing). The applicant authorizes the FCRA disclosure, pays through embedded Checkout (`purpose=application_screening`, `preapply=1`, no `application_id`), the webhook / `checkout-verify` places the Checkr order (`fulfillPreApplyFromSession`, idempotent on the session id, refunds a provider failure or a second payment for what a live order already covers) and Checkr's applicant invite goes to the applicant's email. The order is created from the account's name and email with NO SSN or date of birth (none is collected before the application). The application opens when the ID product returns clear (`idUnlock: "clear"`, default) or as soon as the order is placed (`"order"`). An ID that comes back `consider` is "Needs review": the form stays shut and the manager is the only one who can move it (no retry button yet). The background-check step is satisfied as soon as the order is placed: the applicant is never held for days waiting on the report.
- **Persona** (`RESIDENT_IDENTITY_PROVIDER=persona` with all three keys): Verify ID is Persona's standalone inquiry (`/resident/profile#verification`), satisfied by the account's approved `resident_identity_subjects` row; no background order is needed for it. A background check on top is still the same Starter order WITHOUT the ID add-on. Stripe Identity is never used.
- **Environment**: `RESIDENT_IDENTITY_ENABLED` off means no ID requirement is enforced in that environment (the same rule as the Persona baseline gate); enabled with an unknown provider, Persona without its keys, or Checkr without its key is **"ID check unavailable"** and refuses (fail closed). A background check requirement is dropped when Checkr itself is not configured (nobody could meet it).
- **Server enforcement**: `prepareResidentSelfWrite` calls `preApplySubmitGate` when an application is SUBMITTED (a draft is never refused): unsatisfied -> `403 { blocked: "preapply", step, steps }`; an unreadable requirement -> `503` (fails closed). A satisfied check is stamped on the application (`backgroundCheck`, `backgroundCheckStatus`) and the order trail (`screening_orders.application_id`, `applicant_preapply_checks.application_id`) is pointed at it, so the manager's screening panel shows it like any other check. `backgroundCheck` is now server-owned on an applicant's own write (kept from the stored row, never from the body).
- **Persistence**: `applicant_preapply_checks` (one row per applicant x listing: the order and report state, the authorization, the session id) and `application_adverse_actions`, both service-role only (RLS on, no policy), migration `20261112140000_preapply_checks_and_adverse_action.sql`, classified in `account-purge-manifest.ts`. The Checkr webhook updates the pre-apply record by order id first (`applyPreApplyCheckReport`), then the application row as before.
- **Known gaps**: a Persona deployment still runs the older global baseline gate (`resolveBaselineResidentIdentity`) for every applicant whatever the listing chose; the Checkr applicant-invite behaviour for an SSN-less order is unverified against live Checkr (confirm in Checkr's sandbox before turning Verify ID on in production).

## Adverse action (FCRA)

When a manager declines an application for which a completed Checkr report exists, they must answer **"Is this decision based in whole or part on the background check?"** (`useAdverseActionDecline`, asked from the Applications list/record and the Residents tab's Decline; `declineApplicationWithUndo` takes a `confirm`).

- **No**: recorded (`stage: not_based`, an audit row), then the normal decline with the normal generic notice. Nothing else is sent.
- **Yes**: the **pre-adverse** notice goes out now (resident email + inbox; a text link only where the application was made by text, `noticeChannelFor`): a copy of the report through `GET /api/screening/adverse-action/report` (signed-in applicant only, never a Checkr URL, only once the manager recorded a report-based decision), the CFPB "Summary of Your Rights Under the FCRA" link, Checkr's name/address/phone, the right to dispute and to a second free copy. The application stays Pending; `final_due_at` is stored, **five business days** later (`addBusinessDays`: weekends and US federal holidays skipped, the time of day kept). After the window the manager's **Send final notice and decline** (Finalize) sends the **final** notice (same elements plus that Checkr did not make the decision and cannot give the reasons), then the decline is saved. **Withdraw notice** cancels a pending one (the applicant is told no adverse decision was made) and a fresh answer may follow. Before the due date Finalize is refused (`waiting_period`). There is no cron: finalizing is the manager's decision, never automatic; the panel shows "Pre-adverse notice sent <date> - Final notice available <date>".
- **Checkr's Adverse Action API is not used** (`checkr/client.ts` has no such call): PropLane sends both notices through the action-event bus as **system notices** (`application_pre_adverse_action`, `application_final_adverse_action`; not muted, templated or held as a draft by workspace settings), idempotent on the record id. A notice that reaches nobody is not recorded as sent (the record is withdrawn and the manager can retry).
- **Server enforcement**: `adverseActionDeclineBlocker` in `POST /api/manager-applications` refuses (`409 blocked: adverse_action`) any move to Declined for an application with a completed report until the answer for THAT report is `not_based` or `finalized`; an unreadable state refuses (`503`). The decline of an application with no completed report is unchanged. Authority is re-derived (owner, admin, or a co-manager with `applications` edit); the audit trail is `audit_log` (`adverse_action_not_based`, `_pre_adverse_sent`, `_final_sent`, `_canceled`).
- **COUNSEL REVIEW REQUIRED before live rollout**: every sentence in `preAdverseNotice` / `finalAdverseNotice` (`screening/adverse-action.ts`, version `ADVERSE_ACTION_NOTICE_VERSION`), the five-business-day period and its holiday list, the CFPB summary URL, and Checkr's contact details (`checkrAgencyContact`, overridable with `CHECKR_CRA_NAME` / `CHECKR_CRA_ADDRESS` / `CHECKR_CRA_PHONE`; the defaults must be verified). Not built: a conditional approval (approve with added conditions) has the same `action_kind: "condition"` support in the routes and tables but no screen asks the question yet; the normal automated "not approved" notice still goes out when the decline is saved, in addition to the final notice.

## End-to-end path

0. (Pre-apply, the default now.) Applicant opens Apply for a listing, the gate shows the steps, they authorize and pay, the Checkr order is placed by the webhook and the form opens when the requirement is met; at submit the check is stamped on the application. Steps 1-3 below are the post-application route, which remains for an application that was submitted before the requirement existed.
1. Applicant opens their application (resident portal status screen), sees the itemized total and disclosure, authorizes.
2. `applicant-checkout` re-derives the application's owner, the listing's settings and the price, and creates an embedded Checkout (`purpose=application_screening`, `payer=applicant`).
3. The Stripe webhook (`checkout.session.completed`) calls `runScreeningFromStripeSession` -> `runBackgroundCheck` (idempotent on the session id; `checkout-verify` is the same path for the return trip). Failure after payment refunds, except a provider error that a retry can fix.
4. Checkr creates applicant, property and order; `POST /api/webhooks/screening/checkr` (`Tenant-Signature`, 5 minute replay window, live + test secrets) re-fetches the order and applies Checkr's status. Any `report.*` / `order.*` event is handled; redelivery changes nothing. The route is host-independent, so proplane.ai and axis-seattle-housing.com both work (the legacy redirect never touches `/api/**` or a non-GET).
5. The manager sees the result and the Verified fact on the application's screening panel; the PDF streams through `/api/screening/background-check/document` (authenticated, never a Checkr URL, never stored). The applicant sees progress and Verified only, not the report.

## Production steps

- Env: `RESIDENT_IDENTITY_ENABLED=true` (omit `RESIDENT_IDENTITY_PROVIDER`), `CHECKR_API_KEY`, `CHECKR_WEBHOOK_SECRET` (already set).
- Checkr dashboard: point the webhook at `https://proplane.ai/api/webhooks/screening/checkr` and subscribe to report and order events; the signing secret is `CHECKR_WEBHOOK_SECRET`.
- Stripe: no new events (the existing `checkout.session.completed` handler covers `application_screening`).

- Migration `20261112140000_preapply_checks_and_adverse_action.sql` (additive, idempotent). Dev: `supabase db query --linked -f supabase/migrations/20261112140000_preapply_checks_and_adverse_action.sql`; it rides the `/promote staging` and `production` rungs like any dev-only migration. Not applied to staging or production by this work.
- Env for the pre-apply Checkr path: the same `RESIDENT_IDENTITY_ENABLED=true`, `CHECKR_API_KEY`, `CHECKR_WEBHOOK_SECRET`; optional `CHECKR_CRA_NAME` / `CHECKR_CRA_ADDRESS` / `CHECKR_CRA_PHONE` once counsel confirms them.
- Before turning Verify ID on for a listing in production: place one pre-apply order against Checkr's sandbox and confirm the applicant receives Checkr's ID-verification invite with no SSN/DOB on the order.
