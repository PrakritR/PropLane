Internal research brief

Integrating PropLane’s messaging AI into Airbnb, VRBO, and PadSplit

This is a partner-and-policy problem first, not a model problem. The existing leasing SMS bot cannot be pointed at these inboxes as-is.

Researched 31 Aug 2026 · PropLane / AXIS-2 codebase + live platform docs

Verdict

VRBO

Most open official door

Expedia Connectivity Partner Program is accepting software providers. Lodging Supply GraphQL already has retrieve-thread and AddMessage. Certification usually includes listings, rates, and reservations, not messaging alone.

Airbnb

API exists, program is closed

Homes API has messages and webhooks, but Airbnb is not taking new partner applications. Invitation-only. Practical 2026 path is Hospitable / Guesty / Hostaway as middleware.

PadSplit

No public messaging API

Messenger is web/app only. Threads auto-close after 24 hours. PadPulse sync is unaffiliated. Do not scrape. Path is BD, or keep AI on PropLane channels after the member is on our platform.

Do not ship the current leasing bot into OTA threads. Its system prompt requires PropLane apply/tour links. Airbnb (and VRBO) scan for off-platform contact and payment. That is a ban path, not a feature.

What we already have

The “messaging AI bot” is not one widget. It is several channel adapters around one agent loop: runAgentTurn in src/lib/agent/loop.ts. Each surface has its own context resolver, tool registry, and delivery path. That is the right shape to copy.

SurfaceTriggerRegistryReply delivery
Leasing SMS Twilio inbound on a manager work number leasingSmsAgentRegistry deliverLeasingSmsReply → Twilio
Resident SMS Same webhook, only if phone is verified and belongs to that manager Resident tools deliverResidentSmsReply
Resident Communication assistant In-app inbox, labeled PropLane Assistant Resident tools; writes only proposed Inbox thread write
Vendor SMS Inbound webhook, one work order vendorWorkOrderAgentRegistry Twilio

Leasing SMS path (closest analog to guest chat)

  1. Webhook proves the message is real (x-twilio-signature).
  2. claim_sms_inbound makes retries idempotent.
  3. Identity is resolved before the model runs: work-number owner = manager; From phone = prospect or resident.
  4. runLeasingSmsAgentTurn loads history from agent_sessions / agent_messages, calls tools, traces in Langfuse.
  5. The model never sends. Code sends. The only inline write is escalate_to_manager.
  6. Threads key as owner:role:person_ref, not “this phone pair.”

Leasing tools today

  • list_live_listings / get_listing_details — live PropLane catalog
  • build_prospect_links / get_site_links — apply, tour, listing, portal URLs on prop-lane.space
  • escalate_to_manager

The system prompt requires those PropLane links on every useful reply. This is a conversion bot for our own listings, not an OTA inbox bot.

Existing Airbnb code is calendar only. src/lib/channel-calendar/ imports https://www.airbnb.com/calendar/ical/… URLs. iCal has no messages, no guest identity, no send path. VRBO and PadSplit have no code at all.

The integration shape (same for all three)

Do not fork a second agent. Add a channel adapter that looks like /api/twilio/inbound.

OTA webhook / poll → verify signature → durable claim (MessageSid analog) → map listing/reservation → PropLane manager + property → pick surface (inquiry vs in-stay) → runAgentTurn (channel-specific prompt + tools) → send via that platform’s message API → log into Communication under a new conversation_key

Identity has to grow past phones:

conversation_key = <manager_id>:<role>:<channel>:<thread_or_reservation_id>

Roles stay prospect | applicant | resident. An Airbnb inquiry is a prospect. A confirmed stay is closer to the resident SMS agent. PadSplit messenger opening at booking/move-in is mostly in-stay.

Hard rule from this codebase. Landlord id and listing ownership come from the mapping table and the webhook, never from guest text.

Airbnb

Not self-serve Homes API is real Off-platform links banned pre-booking

Official API

Airbnb’s Homes API (docs at developer.withairbnb.com) is the real supply-side API: listings, availability, reservations, guest messages, webhooks. Messaging is reservation-thread scoped (list/send), OAuth 2.0, scopes like messages:read / messages:write. Webhooks include message.created.

Access is not a signup. As of 2026:

  • No public developer portal you can self-serve.
  • Hospitable and Elfsight both report Airbnb is not taking new API/partnership requests; partner managers invite companies based on supply volume, security review, and support capacity.
  • Preferred Software Partners (as of 24 Aug 2026): about 40 companies, Preferred / Preferred+.
  • Partners must pass data-security + API-quality review and implement mandatory API features within six months of each release. Messaging-only is usually not enough; they expect calendar, rates, reservations.

Reconstructed Activities Messages pattern (not Homes, same shape):

GET/POST https://api.airbnb.com/v2/reservations/{reservation_id}/messages
body: { "message": "..." }   maxLength 5000

Homes inquiry threads are a separate resource in partner docs. Hospitable’s public API still splits inquiry vs reservation send endpoints.

Policy conflict with our current bot

Airbnb scans every message for phone numbers, emails, personal sites, and off-platform payment. Pre-booking contact sharing is forbidden. PMS-sent automated messages get the same scan.

Our leasing prompt telling the model to always include a prop-lane.space apply/tour link, plus build_prospect_links prefilling a phone, is exactly what their filter is built to catch. Post-booking, some contact sharing is allowed, still on-platform first.

What this would look like in our code

  • Mapping table: PropLane property_id / room ↔ Airbnb listing id (today we only store an iCal URL).
  • /api/webhooks/airbnb mirroring Twilio: signature, claim, no double-reply.
  • A new registry, not leasingSmsAgentRegistry. Strip build_prospect_links and get_site_links for pre-booking. Ground answers on the Airbnb listing/reservation payload plus our listing facts. Escalate anything about exceptions, refunds, or “text me at …”.
  • Dual-mode: inquiry → leasing-like Q&A with no off-platform links; confirmed reservation → resident-like tools (check-in, house rules) still without leaking phones until policy allows.
  • Communication: new channel so Airbnb threads do not merge with SMS.

Practical paths

PathReality
Direct Homes API Unlikely until Airbnb invites PropLane. Need real STR supply, PCI/security review, full channel-manager surface.
Ride an existing partner Hospitable, Guesty, Hostaway already have Airbnb+VRBO messaging. Hospitable: POST /v2/reservations/{uuid}/messages, inquiry send when reservation_id is null, OAuth message:write (approval-gated). Guesty: reservation.messageReceived / messageSent webhooks.
Scraping / unofficial inbox tools Breaks, ToS risk, Airbnb revokes. Do not do this.
Keep iCal + SMS after the guest is on PropLane Already possible. Does not put the bot in the Airbnb inbox.

If the goal is “our bot answers Airbnb guests this year,” the honest route is vendor on Hospitable/Guesty, not pretending we will get Homes API access.

VRBO (Expedia Group)

Software partners can apply GraphQL messaging is live Usually not messaging-only

Two Expedia APIs (do not mix them up)

APIAudienceMessaging
Rapid API (supply_source=vrbo) Demand partners booking VRBO inventory Not compatible with Property Message Center. Email/phone on the booking only.
Lodging Supply GraphQL (Connectivity Partner Program) PMS / channel managers pushing your listings to VRBO/Expedia Yes. This is the one we want.

Supply messaging

Live in EG Connectivity Hub, official Node SDK:

  • PropertyMessageThreads — threads for a property (propertyId + filters)
  • MessageThread / Message — fetch by id
  • AddMessage — messageThreadId + AddMessageThreadMessageInput
  • SetMessageThreadSpamStatus

Hostaway’s production notes (they are a VRBO Elite partner):

  • API messages show in both the PMS inbox and VRBO’s inbox.
  • Plain text only: no HTML, no attachments.
  • Thread can lag minutes after inquiry/reservation create; send too early and it fails.
  • Incoming relies on VRBO webhooks.
  • Expedia-sourced VRBO bookings (expediaIntegrated) often cannot use the VRBO messaging API and fall back to email proxy.

Partner program (2026)

  1. Software provider contacts Expedia connectivity (Connectivity Hub).
  2. PCI + license agreement.
  3. Consult, build, sandbox, soft launch, go live.
  4. Individual properties cannot connect directly.
  5. Email historically used: vrboconnectivity@expediagroup.com / connectivitypartner@expediagroup.com.
  6. Tiers: Integrated → Preferred → Elite. Messaging is a real capability, not a secret add-on.

Expedia’s Rapid “Property Message Center” is a different product (hotels / Rapid bookings). VRBO Rapid bookings still do not use it.

What this would look like in our code

  • Same adapter pattern as Twilio, GraphQL instead of REST.
  • New vrbo-inbox-agent.server.ts + /api/webhooks/vrbo (or poll PropertyMessageThreads if webhooks are delayed in certification).
  • Official SDK: ExpediaGroup/lodging-connectivity-nodejs-sdk SupplyClient.
  • Mapping: PropLane property/room ↔ Expedia/VRBO propertyId.
  • Reply cap: plain text, no markdown (our SMS prompt already does this).
  • Same off-platform filter: do not ship apply URLs in inquiry threads.
  • Certification is usually listings + rates + availability + reservations + messaging. That is a product decision: become a channel manager for those houses, or only message listings already connected through someone else.

VRBO is the right first official partnership if we want a first-party API. Timeline is months, not a sprint.

PadSplit

0 public APIs Messenger is product-native 24h thread auto-close

APIs.io (scored 27 Aug 2026) lists PadSplit as 0 APIs, no developer program, agent-readiness 0.

What hosts actually get (PadSplit Help, updated 13 Apr 2026):

  • PadSplit Messenger (web + iOS/Android).
  • Thread opens when a member requests a booking or has a move-in date (instant book).
  • Inactive threads auto-close after 24 hours. Member is pushed to maintenance tickets / support. Host can reopen.
  • Host features: mute, notification prefs, close/open chat, pre-written move-in messages (app only).
  • Maintenance, billing, and safety are supposed to leave messenger for other PadSplit channels.

June 2026: PadSplit’s first external API work is outbound listing distribution to Furnished Finder (supply APIs Furnished Finder owns). That is inventory, not messenger. Hosts were told “no action required.”

PadPulse advertises bi-directional PadSplit auto-sync including messages. Their own terms say they are not affiliated with PadSplit. That almost always means a private/session integration. Replicating it (browser login, scraping Messenger) would violate PadSplit ToS and our security bar. Do not build that.

If PadSplit ever opened a partner API

  • Closest existing surface: resident SMS agent, not leasing. Messenger is post-request / post-move-in.
  • 24-hour auto-close means: reply in seconds, no “wait for the manager to confirm in the portal” for the first answer. Use the SMS posture (readOnly + allowlisted escalate), not the Communication-tab proposal card.
  • Do not route maintenance/payment into the bot as if they were PropLane work orders unless PadSplit’s ticket APIs exist.
  • conversation_key would use PadSplit member/thread id. Phone may not be visible.

Until they open an API

  1. Business development with PadSplit (they just proved they will do partner APIs for distribution). Ask specifically for a host messenger webhook + send.
  2. After a member is on PropLane (lease/account), our existing SMS/inbox bots already cover them. PadSplit Messenger stays native.
  3. Use PadSplit’s own move-in auto-messages for dumb templates; keep the AI on PropLane channels.

How this collides with PropLane invariants

These are not optional polish. They decide whether a channel adapter is safe.

1. Off-platform conversion vs OTA lock-in

The leasing bot’s job is to move people onto PropLane URLs. Airbnb/VRBO’s job is to keep the guest on their platform until (and often after) booking. One prompt cannot serve both. You need channel: "sms" | "airbnb" | "vrbo" | "padsplit" in context and a prompt/tool allowlist per channel.

2. Facts stay tool-grounded

OTA messages will mention wifi, lock codes, fees, “the other listing.” Those must come from tools or the reservation payload. Do not let the model invent check-in instructions. Reuse publicListingProjection. Do not dump row_data.

3. Untrusted guest text

Guest body never changes identity, never triggers an unconfirmed write. OTA webhooks must resolve manager from our listing map.

4. Conversation identity

Do not key OTA threads on guest phone even if the payload includes one. Two guests can share a number. Airbnb identity is the reservation/thread. PadSplit identity is the member.

5. Communication inbox

One conversation inbox, no folder tabs. OTA threads should appear as another conversation in Communication, with channel in the subtitle, not a new “Airbnb” tab.

6. Observability

Stamp channel on Langfuse the way leasing SMS already stamps channel: "sms". Reuse event names; add a channel property. Do not invent a parallel taxonomy.

7. Web + native

A unified inbox change is a portal nav/inbox change. Keep web-native parity. The native app is the same WebView.

8. We are not a channel manager today

Airbnb iCal is one-way occupancy. Becoming an Airbnb/VRBO connectivity partner usually means two-way calendar, rates, content, reservations, then messaging. That is a much larger product than “wire the SMS bot to their inbox.”

Recommended strategy

Do not try to “integrate the existing leasing SMS bot” as-is. The prompt, tools, and identity model would violate Airbnb/VRBO policy on day one.

If the goal is “AI replies in the guest’s Airbnb/VRBO thread”

  1. Near term (engineering, no partner wait): treat Hospitable or Guesty as the channel. Manager already connected to Airbnb/VRBO → OAuth PropLane as a messaging vendor → webhook in, runAgentTurn, send body back. One adapter covers both Airbnb and VRBO. Cost: those managers must live in that PMS; we take their API ToS and latency.
  2. Official VRBO: start Expedia Connectivity Partner intake now. Messaging GraphQL is documented and shipping. Expect full supply integration, PCI, sandbox certification.
  3. Official Airbnb: relationship + supply story, not a GitHub PR. Keep the adapter interface so a future Homes API drops in next to the Hospitable adapter. Do not scrape.
  4. PadSplit: talk to them. No API to implement until they offer one. Do not copy PadPulse’s unofficial sync.

If the goal is “managers stop missing OTA messages” without becoming a PMS

Ship Communication as a unified human inbox first (pull via Hospitable/Guesty), with AI drafts behind the existing confirm gate — same as resident inbox proposals — rather than auto-send. Auto-send on OTAs is how people get policy-banned.

PadSplit vs the other two

Airbnb and VRBO are short-term guest threads tied to a reservation. PadSplit is co-living member ops with a 24h thread TTL and a platform that wants maintenance/billing off messenger. Same agent core, different registry, different SLA.

What to build first (when leaving research)

A channel-agnostic inbox worker, then one adapter:

  • src/lib/channel-inbox/types.ts — Channel = airbnb | vrbo | padsplit | sms
  • src/lib/channel-inbox/identity.ts — extend buildConversationKey with channel + external thread id
  • src/lib/channel-inbox/compliance.ts — block phones, emails, prop-lane.space apply links, payment asks on pre-stay OTA
  • src/lib/agent/channel-inbox-agent.server.ts — copy runLeasingSmsAgentTurn (session, rate cap, history, readOnly, escalate allowlist, Langfuse)
  • src/app/api/webhooks/<partner>/route.ts — copy Twilio claim/replay
  • Mapping: extend channel-calendar beyond iCal, or a new channel_listing_connections table

Hospitable as the first partner would let you prove the agent loop on real Airbnb+VRBO threads without waiting on Airbnb’s invite.
