P2 I1: final selected-line policy checks for the same credit twice

Candidate src/lib/sms/owner-sms-dispatcher.server.ts:1026 calls reserveCommsCredit with policy.workspaceId and the message cost. The task's expanded condition at :1064 then invokes loadSendPolicy for every row carrying selected_work_line_id. That function again calls evaluateManagerCommsBillingGate for the full cost at :191. The gate rejects when the wallet's remaining credit is below that cost (src/lib/comms-billing/eligibility.server.ts:27).

The reservation is already a debit, not merely a held flag: supabase/migrations/20260924170000_comms_credit_per_workspace.sql:256 subtracts the reserved amount from the workspace wallet. A wallet starting with exactly one message cost therefore passes the first gate and reservation, reaches zero, fails the final gate with comms_billing_allowance_exhausted, then the dispatcher blocks and refunds the message. The same failure applies whenever starting available credit is at least one cost but less than two. Main previously used this final-policy branch only for tour purposes; the SMS durability change expands the behavior to selected-line manual messages. This is a deterministic source-path finding, not a claim that a paid or production send was executed.

Required behavior: the final provider-boundary check must recognize the exact already-reserved cost while retaining current billing pause, line/owner, provider identity, suppression and consent checks. It must not require a second unreserved message cost or broadly bypass billing. Add behavioral coverage for a nondefault selected workspace with exactly one message cost, a genuinely insufficient wallet before reservation, and billing paused or line revoked after reservation. The successful path should reserve once and submit once from the selected number; rejected paths must release the existing reservation correctly.
