# PRP-450 implementation plan

## Decision and dependency gate

PRP-450 should extend the existing confirmation-gated listing-draft tools, then enable edits of pending/live records only after one canonical server listing mutation contract owns normalization and downstream charge reconciliation. Do not add a broad `update_listing` tool that directly patches `manager_property_records` JSON.

Two prerequisites are mandatory under `AGENTS.md`:

1. **Server listing normalization:** move the wizard's authoritative `ManagerListingSubmissionV1` normalization, legacy-field derivation, lifecycle validation, owner/co-manager authorization, quota checks, and persistence behind one server-only function or RPC used by both `POST /api/property-records` and agent handlers. It must update the correct lifecycle container (`row_data.submission` for drafts/review records and `property_data.listingSubmission` for published records), preserve unrelated fields/media, reject stale writes with an `updated_at`/version CAS, and never change status as an incidental field edit.
2. **Approval charge generation:** the server approval path must derive rent, deposits, move-in fees, utilities, and lease terms from the persisted normalized listing and reconcile charges atomically/idempotently. Until that is the sole approval money path, the agent must not edit these fields on a listing that can feed approval charges.

The current `create_listing_draft` / `update_listing_draft` implementation is useful preparation but incomplete: its schema covers only listing-level rent, deposit, and application fee; it sets only the first room's rent; it omits move-in fee, utilities, lease-term choices, and named-room batch updates. `update_room_rent` is single-room and writes record JSON itself. Success follows a database update, but the portal still needs an authoritative refresh signal.

## Ownership and overlap

Prakrit's PRP-429 property-draft work and PRP-430 wizard work own the submission shape, autosave/baseline behavior, form validation, and UI refresh contract. Do not concurrently edit `src/components/portal/pro-add-listing-form.tsx`, `src/lib/manager-listing-submission.ts`, `src/lib/manager-listing-draft-autosave.ts`, `src/lib/manager-property-save-target.ts`, or the wizard tests. Rebase PRP-450 after their contracts stabilize and consume their exported server-safe schema/helpers.

The prerequisite owner should extract the shared mutation into a neutral server module such as `src/lib/manager-property-mutation.server.ts` and make `src/app/api/property-records/route.ts` call it; PRP-450 should call that module rather than duplicate its rules.

## Safe parallel preparation

Before the prerequisites land, a separate lane may:

- Define a strict patch DTO for draft intent with an explicit `propertyId`, optional named-room selector (`roomNames` or `allRooms`), and typed values for monthly rent, security deposit, move-in fee, utilities amount/payment model, allowed lease terms, and applicable listing-level fields. Money inputs are numeric dollars at the tool boundary and convert once through the canonical normalizer.
- Add a pure function that applies this DTO to a normalized submission, requires every named room to resolve exactly, rejects ambiguous/missing names and empty batches, preserves stable room ids/media/unmentioned fields, and returns a field-by-field before/after summary plus whether anything changed.
- Extend `get_property_details` only with the safe fields needed to disambiguate the request. Do not return private access instructions, payment handles, documents, or unrestricted row JSON.
- Draft preview tests for all-room and named-room changes, explicit zero fees, utility models, lease terms, no-op requests, ambiguous rooms, malformed amounts, and foreign property ids. These are pure/read-only preparations and must not register a new write tool yet.

## Sequential implementation after prerequisites

1. Land and verify the shared server mutation contract and approval charge reconciliation first.
2. Rebase after PRP-429/430. Replace direct JSON writes in `upsertManagerListingDraft` and `update_room_rent` with the shared mutation. Keep create as `status = draft`; publishing remains out of scope.
3. Expand `update_listing_draft` or add one narrowly named `update_listing_fields` write tool. Prefer one batch tool so “all four rooms” creates one preview and one confirmation. Preview re-reads the owned record, resolves the exact rooms, applies the pure patch, and shows every changed room/field. A no-op throws instead of proposing success.
4. Handler re-authorizes ownership/co-manager `properties:edit`, re-reads the current version, reapplies the same validated patch, writes the audit row first, invokes the canonical mutation with CAS, and records success only after persisted data is reread and equals the expected normalized projection. On conflict or partial failure it throws and clears the retryable audit dedupe key. Never infer owner id from model input.
5. Return `propertyId`, new version/`updatedAt`, lifecycle status, and changed fields. The confirmed action response must trigger the existing property snapshot refresh/coalesced store event so the open Pricing step shows server data immediately. Do not mutate wizard state optimistically before persistence.
6. Register the tool only on the manager portal registry. Manager SMS remains `readOnly: true`; leasing/resident/vendor registries never receive it. Keep publication and application approval unavailable.

## Acceptance and security tests

- One confirmed proposal sets rent `$1,500`, deposit `$500`, move-in fee `$250`, and utilities `$175` on all four rooms; persisted normalized data and a fresh property snapshot show all values without manual reload.
- Named-room subsets update only exact matches; duplicate/ambiguous/missing names reject the whole batch and write nothing.
- Explicit zero clears an allowed fee without being treated as absent. Invalid negative/non-finite values and unsupported lease terms fail schema/domain validation.
- Preview and handler both reject foreign properties and ungranted co-manager access. A record moved, deleted, published, or changed after preview fails the CAS and does not overwrite newer data.
- A database/normalization/charge-reconciliation/readback failure never returns “Updated,” never marks the pending action executed, and leaves the prior listing and charges intact.
- Repeating the same confirmation is idempotent; a changed request is not swallowed by the prior dedupe key.
- Draft edits preserve status, ids, photos, room metadata, and unrelated wizard fields. Published-record tests remain disabled until both prerequisites are proven.
- Approval integration tests derive charges from the newly persisted room values exactly once and prove deposit, move-in fee, and utilities semantics, including included-in-rent utilities and explicit zero.
- Registry tests prove the write is manager-portal-only and absent from manager SMS/read-only and every other role.
- Real dev QA: edit a seeded non-locked listing through the manager assistant, inspect the confirmation card, confirm once, verify Pricing immediately and after reload, then run approval/charge checks only on disposable dev data. Never use the locked Brooklyn listings or `/demo` as evidence.
