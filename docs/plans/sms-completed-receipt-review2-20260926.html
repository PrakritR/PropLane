Completed receipt integration: changes still required

Fresh independent Astra review 2, 26 September 2026, after correction cycle 1. Scope is the new completed-receipt migration, backfill, source adapter, receipt retry hydration, burst hydration and five focused test files. The broader SMS feature and the separately owned operations runners are not reopened. No delegation or feature-cycle restart occurred.

Disposition: do not approve these frozen files for apply or release. The main holder/workspace and NULL-safety corrections are sound, but five scoped issues remain. Three are reproduced against the actual JavaScript functions in memory; two follow from the additive importer's source-selection delta. This review changed only this HTML report. Findings and minimal corrections

F1 · P1 · Existing-turn acknowledgment still accepts a conflicting conversation identity

inbound-pipeline.server.ts, lines 194-225. The conversation read selects only owner, role, user and line. It never reads or compares identity_kind, identity_key or counterparty_phone. Two phone-based prospect conversations have the same role and null user. A turn with the correct SID, owner, original body/wire/time and line, but attached to the other phone's conversation, is therefore acknowledged as complete. This bypasses the stricter canonical identity checks in the existing projection RPC.

Observed: invoking the extracted, TypeScript-transpiled hydrateReceiptRetry with an exact original and a conversation whose phone/key names another synthetic sender returned null (the successful acknowledgment path). The recovery caller then marks success at lines 353-364. A separate case with source_ref={table:'sms_inbound_receipts',id:'SM-unrelated'} also returned null: the live-source branch checks namespace and event ID but ignores contradictory provenance. Historical log references do get their row/SID/holder check.

Correction: derive the expected complete identity once and validate it before acknowledgment. Validate recognized live provenance as well as namespace/SID. Preserve legitimate live/backfill bindings to receipts, exact ingress or exact transport rows; do not require every live source to be a receipt reference. Reject a contradictory reference or an unproved binding. Add wrong phone/key/kind and wrong source-row cases, alongside valid receipt, ingress and log bindings. All failures must leave the retry failed without provider/model work.

F2 · P2 · “Exact” timestamp checks admit different PostgreSQL instants

inbound-pipeline.server.ts, lines 154 and 211; backfill-sms-projection.mjs, line 181. These comparisons use Date.parse, which drops fractional precision after milliseconds. The synthetic receipt instant 2026-09-25T12:00:00.123456+00:00 and conflicting instant 2026-09-25T12:00:00.123789+00:00 compare equal despite differing by 333 microseconds.

Observed: the actual retry function acknowledged that conflicting existing turn. It also accepted the differently timed queued event as an exact classification binding. The imported eventMatchesStored returned true for the conflicting time, so the backfill can count an incorrect projection as already mapped without reaching SQL's exact timestamptz comparison. The body and timestamp returned by the resolver are retained unchanged; the defect is validation, not SQL timestamp storage. The backfill comparison predates this correction, but exact-time acceptance is explicitly in this review's scope, and the new enrichment boundary uses the same lossy comparison.

Correction: compare canonical instants without losing PostgreSQL microseconds, either with a bounded exact parser/normalizer or a database comparison. Equivalent timezone/fraction formatting must still compare equal. Apply this to the scoped original/enrichment/acknowledgment checks; use the same exact comparison for related backfill marker checks at lines 779 and 788 when claiming exact notice binding. Add equal-instant/different-format positives and one-microsecond negatives. Do not round stored originals or introduce a tolerance.

F3 · P2 · Role-only queued enrichment escapes the pending-payload fence

inbound-pipeline.server.ts, lines 159-170 and 219-228. The source/status restriction runs only when prior.counterpartyUserId is truthy. With a completed cleared receipt, a durable log classified unknown, and an exact queued event classified resident with no user, the restriction is skipped and the fallback expression adopts the queued role.

Observed: the actual function returned a new resident event with null user for that completed durable-log fixture. No independently classified resident source existed. This contradicts the correction report's pending-present-payload enrichment boundary and the plan's requirement that unknown remains unresolved. Known source role conflicts and completed null-user restoration with a queued user ID correctly fail.

Correction: apply the pending, present-payload, exact authorized-producer binding to role enrichment as well as user enrichment. A completed unknown log must remain unknown or explicitly unresolved, unless a separately authorized durable classification proves otherwise. Retain the successful classified-pending path and the rejection of deleted/null-user restoration. Add role-only pending positive, completed unknown negative and role/user conflict cases.

F4 · P2 · Historical importer discards the resolver's proven line ID

20260926150000_sms_completed_receipt_originals.sql, lines 96-115, 181-190 and 284-306. The resolver proves one epoch held by the receipt holder in the canonical workspace and returns workLineId. The importer copies body/wire/time but not that ID. Its later legacy query uses a broader holder-or-workspace predicate and falls back to a synthetic line whenever the candidate count is not one.

Static counterexample: receipt holder A has the proven line L1 in owner B's workspace. A second released row L2 has the same receiver and an overlapping recorded epoch, is held by C, and is also in B's workspace. The released-row schema permits this historical ambiguity. The resolver counts L1 only and succeeds; the importer counts both and creates a synthetic line. JavaScript backfill instead rejects the same source because its selected line cannot equal L1. Thus direct import can succeed with a different line identity from the shared authority, rather than fail closed. This is a deterministic branch trace, not a claimed PostgreSQL reproduction or a claim that these rows currently exist.

Correction: for resolver-backed originals, require the importer's resolved line to equal the returned proof and reject ambiguous/conflicting resolution before any insert. Keep legacy synthetic handling for sources that genuinely have no resolver line proof. Add the cross-holder overlapping-epoch case to root's rollback-only SQL fixtures and assert no projection rows. Also retain ordinary same-owner and real co-manager positives.

F5 · P2 · Co-manager correction rewrites unrelated retained log identity

20260926150000_sms_completed_receipt_originals.sql, lines 195-220 and 315-324. The new log source block unconditionally rebuilds v_key and v_legacy_key for every receipt-backed inbound log, including a same-owner non-prospect log without ingress. Migration 180 retained that source row's stored conversation_key (or its source-row fallback). This exceeds the necessary co-manager canonicalization.

Concrete retained-history case: a resident log's sender account is deleted, so its matched_sender_user_id becomes NULL under the existing ON DELETE SET NULL foreign key, while its stored conversation key remains unchanged. With no proven work-line epoch, migration 180 retains that opaque historical key on the synthetic conversation. The replacement constructs an owner/role/phone key instead; replay of the same historical source then raises historical source identity changed after projection at line 324 even though its bytes, wire, role and canonical receipt time agree. A source with a NULL legacy key similarly loses the old source-row fallback. This is static evidence from the exact importer delta and schema, not a report of an observed production row.

Correction: preserve the original log key/fallback when receipt holder and canonical owner are unchanged and no ingress canonicalization is required. Rebuild only the specifically proven canonical prospect/co-manager identity. Do not restore a deleted user ID as a live identity. Root should exercise same-owner non-prospect imports with an unplaced retained key, deleted/null user and NULL-key fallback, plus the existing co-manager preferred-ingress case. Preserve existing historical rows and idempotent replay.

What remains correctly bounded

The resolver preserves full original text from the retained payload or unique inbound log, and uses the exact receipt timestamp rather than log insertion or queue time. Prospect ingress must equal PostgreSQL left(btrim(original, ECMAScript whitespace set), 2000); there is no fuzzy normalization or truncation of the returned original. The explicit trim set includes FEFF and Unicode line terminators and PostgreSQL counts astral characters as codepoints. Burst hydration uses conversation channel sms and per-ingress transport twilio, resolves serially before model work, and refuses a changed receiver or retired Claw source.

The importer comparison against immutable migration 180 has only three insertion hunks: its resolver variable and the two inbound source blocks. The downstream owner lock, provider lock, deletion tombstones, source/provider comparison, aliases and service-only ACL are otherwise identical. The resolver is read-only SECURITY DEFINER with fixed search path and no client execution grant. Retry hydration itself calls neither provider nor model. Existing delete/replay serialization remains in the projection/import RPCs; this review found no new path that removes a tombstone or resurrects a deleted event.

The receipt inventory narrowing is accepted in this scope. The supplied census records 359 production completed receipts with NULL payloads, including 53 with no match in the five listed source surfaces. Metadata-only receipts are not originals and are not restored. Ingress, inbound-log and receipt-backed manager-log feeds still require source authority. The exact 18 currently visible owner-notice originals remain a separate provider-proven restoration, not an exclusion category. No truthful byte-exact marker is inferred for trimmed or ID-only notice entries.

The user's additional staging/production audit reports zero inbound manager logs with a matching receipt but no inbound log. That supplied evidence addresses the current inventory concern for the added manager-log guard; this reviewer did not repeat the audit. The two staging retryable NULL-payload receipts with inbound logs remain under the release owner's separate synthetic-provenance investigation before staging backfill. No resolver relaxation is justified by those fixtures.
