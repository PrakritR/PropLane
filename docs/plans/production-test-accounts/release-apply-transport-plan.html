TLS, role and transaction execution

  1. Read the fixed CA bytes and verify their SHA before opening a socket. Use explicit pg fields, never an opaque connection string: ssl.ca is the pinned certificate; ssl.servername is the validated host; ssl.rejectUnauthorized is true. Require the resulting socket to be TLS-authorized with hostname verification, and verify pg_stat_ssl for pg_backend_pid(). This is verify-full semantics; no fallback to insecure TLS, sslmode=require, rejectUnauthorized=false or an ambient CA override.
  2. Connect with 15-second connection timeout and attach the driver error listener before connection. Set explicit session role postgres and read back current_user/current_role, database postgres, UTF8 encoding, session_replication_role=origin and recovery bypass off. Reject a role or session-state mismatch. Use session SET ROLE postgres before the already framed bundle so the transport need not remove or insert bytes around its BEGIN. Session role lifetime is limited to this dedicated connection.
  3. Run preflight evidence in a bounded read-only transaction and close it before apply. Confirm target, full ledger, table/catalog state, final backup file hashes and baseline invitation beforeimage against the reviewed artifact. Verify backups are regular private files belonging to the expected target folder and the final manifest status identifies completed combined rehearsal. The final manifest must bind the generator/transport revisions, SQL bundle, catalog and beforeimage, not just claim a human-readable target.
  4. Set the session attestations proplane.release_project_ref and proplane.release_backup_sha256 through parameterized set_config calls, only after the independent target and backup checks. They are assertions supplied by transport, not independent database identity evidence. Also enforce origin mode in transport for both phases; baseline's own in-transaction assertion remains authoritative defense in depth.
  5. Send the exact generated SQL as one ordered operation on the dedicated connection. Its own BEGIN, local 5-second lock timeout, 120-second statement timeout, 180-second idle transaction timeout, advisory/table locks, beforeconditions and postconditions remain intact. Apply a bounded client wall-clock deadline (initial proposal: 210 seconds) as well. On timeout, actively close/destroy only this owned connection, rather than leaving a Promise.race loser executing. Rehearsal must establish whether that deadline is sufficient; change it only with reviewed evidence.
  6. Keep asynchronous connection errors and commit acknowledgement separate. On a confirmed SQL error before commit, attempt bounded ROLLBACK, then close. On lost connection or missing commit acknowledgement, never retry the write blindly. Open a new independently verified read-only connection and classify the exact ledger/schema as baseline, completely installed or unexpected. Report ambiguous/unexpected state as failure and halt the ladder. Never claim success merely because the write promise resolved without checking readback.
  7. After acknowledged commit, verify from a fresh TLS connection: full historical ledger unchanged, exact new entries/statements fingerprints, required schema and effective grants, baseline unchanged invitation full-row digest, and feature restrictive policy/storage/RPC postconditions. Print only target, phase, hashes, sanitized result, counts and exit code. No raw SQL, historical statements, customer rows or driver context.
