Staging test-workspace fixture plan

Use a bounded staging bootstrap for identities, then the deployed product for business rows. The existing broad DEV seed is not safe to aim at staging. The admin invitation route deliberately sends its auth invitation through Resend and is therefore excluded from provider-free fixture creation. Bootstrap one synthetic normal admin operator and four classified identities with the staging service API, preserving the route's banned-until-durable ordering; then create business rows through their real portal routes.

Provisioning sequence

  1. Take one certificate-verified read-only staging snapshot and assert the feature schema is present, the target is exact, and no intended fixture email or id already exists. Reuse an existing fixture only if every identity, workspace and provenance field matches; otherwise stop on collision.
  2. Create the synthetic normal operator with the staging service role, then insert its minimal profile and admin role in one bounded, recorded operation. Read back that it is admin, normal-classified and absent from membership. Set the branch-scoped feature flag and exact UUID allowlist, then deploy the candidate.
  3. Sign in as the operator and use the admin Test accounts UI/API to create both empty workspaces. Provision the four classified auth identities with a fixed staging-only service script: create banned user; insert profile and profile_roles; insert membership and matching test_workspace_member_fixture_created audit row; read back the exact workspace/role/state/expiry; then unban. On any failure leave the user banned and stop. The script must never generate or deliver an auth link.
  4. Sign in as Manager A to create the listing and co-manager link through normal product routes. Accept the co-manager invitation as Co-manager A and verify the assigned property plus explicit module levels. Use Manager B only as an isolation control.
  5. Write a redacted fixture manifest containing target, deployment SHA, auth UUIDs, workspace ids, membership ids, property id, co-manager link id, expiration, and row/effect counts. Hash it and retain the full credential file privately.

Pre-QA refusal checks

  • The operator is normal and cannot appear in any classified workspace.
  • Every classified profile, manager/application/property/link/schedule row carries exactly its workspace id; no row has customer provenance or crosses A/B.
  • The Workspace A listing is absent from anonymous and normal-account public catalogs, visible to the intended active Workspace A actors, and absent from Manager B.
  • Co-manager A can use only the assigned property and granted module levels. An ungranted module and Workspace B property both refuse.
  • Fixture audit evidence exists without an auth invitation or real provider call. Provider ids, remote-message ids and external calendar/payment identifiers remain absent. Exercise the real admin invitation delivery separately only if an explicitly controlled Resend acceptance test is authorized.
  • Suspending one member with an existing session denies business access while durable classification remains. Reactivation restores only the same workspace.

Ownership and cleanup

Root owns the staging configuration, service-role bootstrap, browser sessions and validation slot. Keep fixture rows for the duration of staging QA so failures are reproducible. At release close, disable the feature flag or remove the operator UUID as required by the rollout decision; do not delete membership rows merely to make identities appear normal. Any cleanup must use the product/account deletion contract and preserve durable classification and audit evidence.

This plan authorizes no production identity, seed or provider call. The production operator account remains a user decision. Never copy staging credentials, UUID allowlists or fixture rows to production.
