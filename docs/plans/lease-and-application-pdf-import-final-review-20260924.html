Findings

F1 · P1 · Reviewed reusable converted leases cannot be sent

After the dedicated template confirmation returns 200 and creates a valid placement receipt, sending the same lease returns 409: “Review the imported lease before sending it for signature.” The generic uploaded-source guard treats any stored imported-converted mode as requiring uploadedLeaseParse and uploadedLeaseReviewReceipt. Reusable template placements have templateImportReview and templatePlacementReview instead. They fail before reaching the dedicated template guard. This blocks the approved reusable-template happy path.

src/app/api/portal-lease-pipeline/route.ts:1015, src/app/api/portal-lease-pipeline/route.ts:1041, src/app/api/portal-lease-pipeline/route.ts:1067

Evidence and required outcome: Independent mocked real-route probe: confirmation 200; subsequent send 409 with the uploaded-source review error. Separate artifact-specific obligations need to be enforced without classifying template placements as uploaded lease rows.

F2 · P1 · Application comparison still approves an unseen newer draft

Application PUT accepts only property, template and source hash. It fingerprints whichever draft exists when the request arrives and clears unresolvedCount. A same-source edit saved before the request is therefore approved by a stale comparison. The updated_at conditional write only catches a later race. The editor also sends no viewed draft fingerprint or expected persisted revision. This is the application half of correction C3, still unresolved.

src/app/api/portal/application-template-import/route.ts:61, src/app/api/portal/application-template-import/route.ts:72, src/components/portal/pro-application-questions-editor-modal.tsx:599

Evidence and required outcome: Independent mocked real-route probe: replace the viewed draft with a new required question, submit the old comparison, receive 200 and a receipt for the new fingerprint. Confirmation must compare the actual viewed revision and draft before issuing a receipt.

F3 · P1 · Published co-signer submissions bypass mandatory phone validation

The co-signer endpoint requires nonempty name and email, then validates custom questions only. Phone is normalized to an empty string and stored. A request for a published co-signer template with no phone succeeds. The new integration therefore does not satisfy the approved requirement that name, phone and email remain mandatory on forged submissions. The underlying endpoint predates this feature, but closing this contract was an explicit acceptance criterion.

src/app/api/public/cosigner-submissions/route.ts:38, src/app/api/public/cosigner-submissions/route.ts:70, src/app/api/public/cosigner-submissions/route.ts:84

Evidence and required outcome: Independent mocked real-route probe: published version 1 submission returns 200 and stores phone="". Use the same required identity and configured built-in validation policy on the server.

F4 · P2 · Published question metadata still differs from live forms

The co-signer flow loads the publication and custom questions, but keeps fixed built-in labels and required rules. For example, disabling or making date of birth optional in the editor does not remove its unconditional live validation. Custom fields from every section are collected in step 4, so configured order and section do not match the manager preview. Standard forms also keep fixed household labels, and the editor permits moves between same-section built-ins while property/household rendering remains structural. These are product discrepancies, beyond a missing browser check.

src/app/(public)/rent/apply/cosigner-flow.tsx:251, src/app/(public)/rent/apply/cosigner-flow.tsx:732, src/components/marketing/rental-wizard-steps.tsx:450, src/components/portal/pro-application-questions-editor-modal.tsx:655

Evidence and required outcome: Source review and the execution handoff agree on remaining parity gaps. Either implement the saved metadata consistently or prevent unsupported edits before publication; preserve mandatory identity and typed placement constraints.

F5 · P2 · Optional group question disables dependent validity checks

When “Group application” is optional, validation returns immediately even if the applicant answered Yes. Group size and group-leader checks are skipped. A selected group with groupSize="0" passes that step under optional policy, while the same answer is rejected when the field is required. Optionality must govern missing answers; it must not suppress checks on a chosen group. This is a concrete remaining C8 defect.

src/lib/rental-application/validate.ts:173, src/lib/rental-application/validate.ts:179

Evidence and required outcome: Independent pure-function probe confirmed an empty error object for the optional case and groupSize error for the required case. The full table-driven built-in policy requested in correction 2 is still absent.

F6 · P2 · Inactive variant pins and answers do not survive reload

Per-variant state is held only in a module Map. A reload clears that map; only one active public resume ID is persisted. Returning to the previously inactive variant uses the empty map, creates a new application ID, and clears its custom answers and template pin rather than retrieving that target’s saved row. The server-row lookup immediately above applies only to property changes. Same-page switching improved, but C9’s reload and return contract remains incomplete.

Evidence and required outcome: Source-confirmed restoration gap; the focused draft test covers only the live module. Full browser reproduction after reload remains outstanding. Restore each authorized target’s persisted row/pin without putting answers or PII in browser storage.
