High findings

H1 - Inquiry upsert bypasses the protected singleton boundary

src/app/api/portal-schedule-records/route.ts:105 allows the shared inquiry id through the non-vendor authenticated write scope. At :137, the atomic writer handles only the planned-events id. src/lib/portal-record-api.ts:218 treats that visibility scope as write authority, and :258 performs an unrestricted service-role upsert. The new authorizeDelete hook is never consulted by upsert or replace.

An authenticated resident or unrelated manager can post {"action":"upsert","row":{"id":"axis_admin_partner_inquiries_v1","payload":[]}} to erase every manager's pending inquiries. A forged payload can also replace trusted inquiry fields. The raw-write exposure existed before this release and remains unresolved in the corrected authorization boundary.

The new read projection adds an ordinary-user data-loss path: src/lib/demo-admin-scheduling.ts:815 saves a public inquiry, then :822 calls insertPartnerInquiryLocally. That helper at :1232 rewrites the whole inquiry singleton from the viewer's partial cache through writeJson. A signed-in resident receives no shared inquiry rows under the new projection, so a legitimate submission can overwrite the global singleton with only that prospect's inquiry. Existing standalone mirrors do not repair the lost authoritative singleton used by confirmation.

Required resolution: prohibit generic inquiry snapshot writes or replace them with a server-authorized per-inquiry mutation that preserves hidden rows. Local insertion after successful public creation must not persist a partial global snapshot. Cover resident/unrelated-manager upsert and replace, plus a real signed-in public booking with two owners' existing inquiries. DELETE-only tests are insufficient.

H2 - A stale reschedule can revive a canceled tour

src/lib/tour-planned-change.server.ts:333 reads the active tour, then :370 submits a replacement without an expected lifecycle/window version. In supabase/migrations/20260915103000_prospect_sms_tour_booking.sql:243, replacement requires only that the id still exists. At :261 it replaces the stored event wholesale; :266 restores an active reservation. The booking-status update at :274 excludes canceled bookings, so an SMS booking remains canceled while its event and reservation become active.

Sequence: reschedule reads active A; cancel commits and notifies the guest; delayed reschedule commits the old event object with the new window and no canceledAt. The canceled tour and reservation become active again, with inconsistent booking status. The new Google provider fence cannot protect a local lifecycle that has already been reopened.

Required resolution: the atomic replacement must reject canceled/deleted or changed expected lifecycle/window state, under the same transaction lock. Exercise cancel-versus-reschedule and two overlapping reschedules through the real TypeScript caller and PostgreSQL, including notifications and Google recovery. Use additive correction SQL; do not edit the applied migration.
