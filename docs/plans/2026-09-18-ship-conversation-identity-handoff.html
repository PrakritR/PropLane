Implemented behavior

Resident manager identity and unified history

  • The resident inbox route repairs an empty historical manager email/name only after verifying the stored managerUserId and propertyId against the authoritative manager_property_records ownership row, then resolving that manager's profile. This recovery is independent of the SMS UI flag and does not overwrite conflicting stored email.
  • Persisted inbox rows now retain manager, property, role, and SMS conversation identity metadata. Person-thread collapse keeps assistant threads separate even if malformed data shares an email.
  • Resident SMS payloads now include verified, per-manager conversations while preserving the legacy flat message list for compatibility. Messages without a proven manager/property binding remain in an isolated generic SMS history.
  • The resident Communication surface binds email and SMS only through an exact verified manager/property conversation key, keeps two managers separate, deduplicates legacy flat SMS, preserves historical deep links, shows channel labels, and renders the exact selected SMS turns alongside email messages.
  • Resident archive state for SMS is local and viewer-scoped. Merged archive/restore operates on each source member. Destructive SMS deletion stays hidden because the existing manager delete route does not authorize residents.
  • Resident read acknowledgement now marks every selected email source row through the resident-authorized route. SMS inbound read state continues to use local opened-message state.

Prospect and application continuity

  • Application lifecycle SMS resolution runs for submitted and subsequent events. A unique existing prospect/applicant conversation is reused; ambiguity and unavailable sender identity fail closed. Approval still requires an existing match.
  • Application-submitted manager notifications resolve the SMS conversation independently for each recipient using that manager's own conversations plus the exact applicant phone and work number. A co-manager cannot borrow the owner's conversation key.
  • Portal inbox delivery accepts narrow thread identity metadata and persists it on both create and append paths so later resident reconciliation has durable provenance.

Tour continuity

  • Tour request and removal delivery preserves proven manager/property provenance even when profile lookup fails; a missing email stays isolated until server recovery instead of degrading to an untraceable generic row.
  • Tour messages use deterministic ids derived from lifecycle/window plus subject and body. Exact retries deduplicate, while changed reconfirmation or cancellation content appends as a new event.
