Finding

P2 / Medium: the new Text line picker cannot select a line with the keyboard

Changed location: src/components/portal/pro-resident-detail-inbox.tsx:1045-1057. The native select is replaced by FieldSingleSelect. Its accessible trigger name is correct, but its selection mechanism currently requires a pointer-down/pointer-up pair.

Evidence: checkbox-multi-select.tsx:455-459 calls onChange only through useFieldSelectListboxPointerPick; option buttons at lines 473-501 have no click or keyboard selection handler. field-select-listbox-pick.ts:43-99 registers only pointerdown, pointerup and pointercancel. field-select-menu.tsx:788-819 handles Escape, not keyboard selection. Native Enter/Space button activation produces a click, which does not take this pointer-only selection path.

Impact: with two bound projections, selection starts at null. A keyboard user can activate the Text line trigger but cannot choose either projection, so the existing smsAvailable and composer guards leave an SMS-only reply unavailable. The previous native select supported keyboard selection. This is an adoption regression on the reviewed surface even though the underlying shared-control limitation predates this delta.

Required correction: retain the shared picker while providing keyboard/assistive activation through its selection mechanism, preserving disabled-option checks and avoiding duplicate pointer activation. Add a focused keyboard interaction assertion using the real picker that selects the second projection and retains the exact projection-two send assertion. Review any shared-control correction as a separate bounded delta. The current integration adjustment at manager-unified-inbox-read-integration.test.tsx:257-265 exercises only pointer events, so its reported pass cannot detect this regression.

This finding is based on the complete event-handler path in source; no browser reproduction or new test execution was performed under this review's restrictions.
