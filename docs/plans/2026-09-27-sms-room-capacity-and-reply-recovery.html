SMS room capacity and reply recovery

Plan, 27 September 2026. Worktree branch agent/akhil-sms-listing-prod-20260926; starting commit eb627814b1fa265304cee97e3f2fe5e591b04ebc.

Observed failure

  • The public Milpitas listing has three rooms; Room 3 has occupancyCapacity: 2. The public projection preserves this field, but summarizeRooms drops it before get_listing_details reaches either SMS agent. A 05:38 UTC leasing reply consequently claimed each renter gets a private room.
  • At 05:39 UTC the texter asked whether every room has its own resident and whether the house holds no more than three people. Langfuse trace b2a4dfa1-8e92-4df9-90c1-b37fb95ac3bd shows the model called suppress_redundant_reply with repeated_question. Its handler checked only that an earlier outbound SMS was delivered, then silenced the new question.
  • Twilio confirms work number 4084596787 is active and SMS capable. Four earlier incoming texts received error 11200 with HTTP 502 from the production webhook. Some Vercel inbound requests took 10–15 seconds; this is a separate transport reliability concern. Subsequent inbound traffic and replies succeeded, so the latest silence is specifically the suppression decision.

Implementation

  1. In the common prospect-safe room summary, return normalized room resident capacity and physical bed count as distinct fields. Return a deterministic listing-level maximum resident count from the published rooms if every included room is countable. Preserve anonymous occupancy verification boundaries: capacity is a published maximum, while open spaces are unknown if the occupancy read fails. Clarify this in prospect and resident SMS instructions so the agent answers occupancy questions without inferring one resident per bedroom or conflating bed count with capacity.
  2. Make reply suppression fail closed for new questions. Pass the trusted current inbound text into the leasing tool context. Permit suppression only for a narrowly recognized standalone acknowledgment to a confirmed recently delivered reply. Remove the model's semantic repeated_question silence path; an extra reply to a repeated question is safer than losing a clarification. Ensure a rejected suppression call returns a tool error so the agent can answer.
  3. Inspect the webhook 502 samples against Vercel timing and existing durable receipt/queue recovery. Make a focused transport change only if a reproducible application failure is found. Otherwise document the evidence and leave transport architecture intact.

Acceptance and validation

  • A capacity-two room is returned as allowing two residents to both prospect and verified resident SMS tools. The listing result distinguishes three bedrooms from total possible residents; no model arithmetic or identity disclosure.
  • An explicit question following a delivered answer cannot invoke a successful silence action. A standalone “thanks” can still be quiet. Unknown or failed delivery never authorizes silence.
  • Focused unit tests cover the tool payload, missing/malformed capacity, occupancy lookup failure, and suppression boundaries. An integration harness feeds the actual tool result into the model-facing SMS turn. Test with real nonproduction listing data and inspect the resulting Langfuse-style trace. Run bounded repository validation, security review, staging QA, and the release ladder if the continuing ship authorization applies.
  • Read-only Twilio and Vercel evidence identifies which failures were webhook 502 versus model suppression. Do not text the real contact, edit a locked live listing, or write production data.
