Why a transaction is not necessarily a transaction block

The PostgreSQL 17 transaction implementation distinguishes these states. IsTransactionBlock (4927 onward in the downloaded file) returns false for TBLOCK_DEFAULT and TBLOCK_STARTED. CheckTransactionBlock (3680 onward) permits an established transaction block, a subtransaction, or a non-top-level function context; otherwise it raises the exact warning/error observed. In the query dispatcher, simple multi-statement Query explicitly calls BeginImplicitTransactionBlock, whereas extended Parse starts a transaction command and keeps it open until Sync without that block transition. This explains why top-level block-only commands can fail even when multiple extended statements share a transaction.

PostgreSQL's extended-query contract says Sync closes a transaction that is not inside BEGIN/COMMIT and rolls it back after an error. Thus the observed log is consistent with the one-Sync implementation. It is insufficient evidence to blame per-statement commits or Supavisor rewriting. PostgreSQL 18 documentation has additional pipeline-block wording, so it must not be substituted for the actual target version. Root should confirm the server version in retained inventory.
