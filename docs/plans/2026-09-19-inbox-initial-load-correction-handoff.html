Diagnosis

usePortalSession can return a server-provided viewer and ready=true before its asynchronous browser session initializes the module-level cache viewer. applySession later sets the cache viewer before publishing the hook snapshot. That identity transition purges the inbox cache and makes an in-flight initial HTTP result stale. The component's viewer and ready dependencies can remain unchanged. Both resident and manager initial-list handlers previously returned on that stale status, leaving the list loading indefinitely.

Implementation

  • src/lib/communication-initial-load.ts observes one initial request's cache identity. Initial null-to-intended-viewer hydration is allowed. A different non-null viewer at entry, or any intervening switch away from the intended viewer, invalidates the request permanently, including A-B-A changes that do not produce a component rerender. The helper observes identity and never assigns the shared cache viewer.
  • Resident inbox and manager inbox/application loaders retry a stale result once through their existing normal coalesced loader. Retry requires the same component generation and epoch, a noninvalidated request observer, and a cache viewer matching the intended viewer. No force bypass is introduced. Successful sources and SMS are not restarted by stale recovery.
  • A repeated stale result or invalidated cache authority becomes the existing Retry error state. A completion from an obsolete component generation is ignored. Every enabled source must still succeed before membership is revealed, including manager application/contact rows and enabled SMS.
  • Existing SMS authorization-stop and explicit user Retry behavior are retained. The request observer is detached on completion, replacement, dependency cleanup and unmount. Unexpected thrown loader failures also produce the existing error state for the current request.
  • Demo's synthetic identity remains separate from authenticated cache identity. It does not trigger automatic stale retries.
