Remaining findings

P1: successful replies still overwrite newer cache state from a stale React ref

src/components/portal/pro-inbox.tsx:1146-1163, resident-inbox-panel.tsx:1132-1151, vendor-inbox-panel.tsx:795-812.

All three success paths read localRef.current, whose update is a passive effect, then pass that entire array to upsertPersistedInboxRows. The storage helper synchronously replaces the shared cache with allRows before its single-row POST. A cache event can commit a new inbound message and sibling row, queue a React update, and be followed by send completion before the passive ref update. The success handler then drops the sibling from cache and upserts a target row lacking the new message. An ownership token does not prevent this same-viewer lost update. Merge the delivered message into the latest authorized storage snapshot at the actual commit boundary. This is the precise current-cache requirement left open from correction 2.

P2: manager reply advances the approval queue twice

src/components/portal/pro-inbox.tsx:979-984,1146-1154; helper src/lib/portal-inbox-storage.ts:935.

The optimistic reply calls advanceInboxAiDraft. After an ordinary network wait, localRef contains that already-advanced draft, and success calls the same helper again. With active draft A and queued drafts B/C, approving A promotes B locally and then persists C, losing B without approval. The failure rollback restores A but does not restore the queue or resolved-draft IDs already changed by the optimistic advance. This existing reply behavior remains inside the explicitly audited AI approval/queue contract; the new failed-generation queue test does not exercise it. Advance exactly once for a successful operation, and reconcile any optimistic contribution without consuming another queued draft.

P2: conversation ownership checks do not invalidate old attempts, and some completion branches omit them

src/components/portal/resident-inbox-panel.tsx:1619-1679,1696-1727; pro-inbox.tsx:1481-1514,1823-1929; vendor-inbox-panel.tsx:1038-1082.

The viewer generation changes only with viewer identity. Comparing the current expanded ID to a captured ID cannot detect a same-viewer thread X-to-Y-to-X transition. Start a send in X, visit Y, return to X and type a new draft, then resolve the old send: its completion passes both checks and clears the new X text and attachments. A conversation/attempt generation is needed for completion effects. Separately, resident AI catch/finally and manager contact-save catch/finally check only viewer ownership: an old X rejection can show an error or clear a new Y operation's busy state. These branches remain present in the final frozen source. Manager thread-switch busy resets were added during handoff and are not reported as missing.

P2: archive/restore rollback overwrites a newer unread value

src/components/portal/resident-inbox-panel.tsx:689-695,726-732, with the same pattern in pro-inbox.tsx:760-767,795-802 and vendor-inbox-panel.tsx:471-478,508-515.

The rollback checks folder and previousFolder, then unconditionally restores unread: target.unread. Archive an originally read thread, receive a newer event that leaves it archived but makes it unread, then fail the archive upsert: the new message survives but its unread flag is reset to false. The changed field must be reconciled against its own optimistic value, not merely the folder pair. Current archive coverage adds body/preview data but does not change unread, so it misses this case.

P2: resident viewer reset omits pending bulk and SMS configuration state

src/components/portal/resident-inbox-panel.tsx:317-332,1265-1288,1973-1979.

Likewise smsConfigured is not cleared on viewer change, leaving A's true value active for B until B's request finishes. Vendor explicitly resets this value. Reset these viewer-owned fields at transition. The bulk controls are the legacy schedule-panel surface, so this finding does not claim they are the normal embedded production navigation.
