R1 · P2 · Required co-signer upload questions cannot be completed

The editor permits custom file and photos questions, including required ones. The co-signer renderer handles checkbox and select controls, then renders every other type as an ordinary input. A required upload therefore becomes a text box. Both the live step validator and public submit route use the shared attachment validator, which requires serialized attachment metadata; typing a filename cannot satisfy it. The full manager preview shares this broken control. Multi-select questions also fall through to an ordinary text input.

Evidence: co-signer renderer, lines 799-808; attachment validation; custom type picker.

Independent focused probe on Node 22.23.0, exit 0: rendered the actual CosignerApplyFlow through React server rendering with a required household file question, then called the actual shared validator with paystub.pdf.

Fix: use the shared typed question controls with appropriate authorized attachment handling, or visibly prevent unsupported co-signer question types from being authored/imported/published. Handle existing unsupported drafts explicitly. Add behavioral coverage for each permitted custom type through preview, live form and submission; include required uploads and multi-select encoding. Do not weaken server validation to accept a filename as an attachment.

R2 · P2 · Unsupported built-in choices are still editable

The new restrictions fix built-in type, label and order controls selectively, but the dropdown option editor remains active for built-ins. For example, a manager can save the Number of occupants choices as 6 and 7. The applicant renderer always constructs choices 1 through 5. The saved configuration and manager field preview therefore describe choices that the live application never offers. Household and history choice controls also use typed fixed alternatives.

Evidence: unrestricted option editor; patch guard handles label and required only; fixed occupancy choices.

Independent Node 22.23.0 probe, exit 0: the actual patchListingApplicationField and resolver preserve ["6","7"], and rendering ApplicationQuestionFields exposes the edited 6 value. The live fixed 1-5 list is confirmed in source. The server-rendered closed custom dropdown does not expose its choices, so the probe alone is not claimed as an interactive browser comparison.

Fix: visibly lock choices for typed built-ins whose allowed values are structural, or implement compatible config-driven rendering and validation. Prevent unsupported stored choice overrides from promising a different form. Add a test that attempts a built-in option edit and checks the accepted policy in the actual applicant control.

R3 · P2 · Switching properties still discards a saved draft's pin and answers

F6 restores inactive stay types for one property after reload, but the property-change branch does not preserve a target row it finds. It spreads the saved target application, then spreads the previous form over it, and explicitly clears customFieldAnswers, applicationTemplateId and applicationTemplateVersion. The helper has already selected the existing target row's ID. The pin effect can then select the current publication, and autosave can persist that result into the resumed target row. Returning to property B with a v1 draft after v2 publication loses B's answers and pin.

Evidence: saved row overwritten and fields cleared, lines 1349-1363; helper selects saved target ID; unpinned draft selects current publication; autosave.

Independent focused Node 22.23.0 probe, exit 0: extracted and transpiled the actual patchForm callback, injected surrounding state/IO functions, and supplied a resolved B draft at v1 with an answer. Calling the real callback with {propertyId: "property-B"} returned B with an empty answer list and no template ID/version. This is a source-isolated callback probe, not real browser or database evidence.

Fix: resolve and restore the complete authorized property/variant target before choosing an ID or allowing autosave. Keep the saved publication and answers when resuming; clear them only for a genuinely new target. Also invalidate outstanding variant restore requests on property changes: the current async completion checks only its axis ID and can overwrite a newer property selection. Add property A/B return, publication advance, reload and delayed-response tests, including failure/retry without autosave or cross-target writes.
