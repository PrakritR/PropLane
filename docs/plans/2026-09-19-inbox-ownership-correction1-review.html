P1: archive, restore and permanent-delete continuations still cross viewer boundaries

Archive and restore capture A's array, await the upsert, and on failure stage the entire captured array without checking ownership. Switch to B and hydrate B before the failed response: A replaces B in shared cache and presentation. Even within one viewer, this discards newer rows/messages. The correction handoff acknowledges leaving these paths unchanged.

Permanent delete is more serious: after awaiting A's deleteInboxThreadIds, each panel derives next from the captured A render and calls persistInboxAwait. If B is current by then, the whole-snapshot writer can infer deletion of B's rows. Confirmed delete-all and bulk actions also resume across an awaited confirmation without verifying the initiating owner. This is the original destructive snapshot authority problem reachable through a delayed explicit action.

P2: manager AI persistence rollback can discard a newer draft queue

pro-inbox.tsx:1910-1922.

The rollback checks only current aiDraft.text and status, then restores both draft and the entire captured aiDraftQueue. While the upsert is pending, a cache event can append another queued draft without changing the active draft text/status. On failure the new queue entry is lost. The same comparison can overwrite newer metadata on a same-text draft. Reconcile only this operation's contribution against the latest cache; do not restore an entire prior queue based on active text equality.
