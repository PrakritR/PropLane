Approved execution correction A: owner-neutral platform replies

November 4 execution evidence: two controlled fake-timer tests pass and demonstrate the current route waiting 16 seconds in shared routing and post-claim continuation. The production architecture has no existing durable, owner-neutral outbound dispatcher suitable for every direct TwiML reply. one-number/lead-send.server.ts:sendPlatformLeadText is the correct existing policy for a platform response without a client workspace, but currently submits directly through sendSms. Owner-funded sendSharedLineMessage and signup-line sending are not substitutes: inventing an owner would charge or disclose to the wrong client.

Decision: extend the existing platform send policy with a narrow durable platform-reply transport, alongside the owner-neutral inbound envelope. This is approved within the repair scope and supersedes the earlier assumption that every deferred TwiML reply can reuse the existing owner outbox. Do not invent platform client ownership or weaken client billing gates.

  1. Use service-role-only durable reply rows with a unique inbound-envelope/SID plus bubble-index key. Store the exact prepared body/media, pinned wire sender and recipient, environment, timestamps, immutable digest, attempt/lease state, provider SID and opaque callback token. Validate that the reply is generated from a signature-verified accepted envelope, not arbitrary caller fields. No client owner or workspace is required or fabricated. Classify any new table in the purge manifest/retained policy with appropriate payload retention.
  2. Persist all prepared bubbles before dispatch. Replays reuse exact bytes and bubble order. Atomic compare-and-swap transitions prepared to submitting before any network submission; only one worker can submit a bubble. SID acceptance is recorded durably. A definite provider-not-attempted outcome can become retryable; any attempted request with unknown acceptance, or a crash after submitting, becomes delivery_unknown. Never automatically resend uncertain submission. Do not label accepted or unknown as handset-delivered.
  3. Extend the existing transport with a server-controlled opaque status-callback correlation token where needed. Validate the Twilio signature against the exact callback URL and require the stored token/row, exact pinned From/To, account and SID consistency. A callback may establish acceptance and delivery monotonically; it cannot overwrite an already bound different SID or create a new send. No body/phone secrets in callback URLs. Reconciliation is read-only provider evidence or authenticated callback; absence of evidence never authorizes resend.
  4. Continue the platform_lead configured-shared-number gate, test capture, protected-recipient shield and existing transactional response semantics. Add an explicit fail-closed suppression read before provider submission: the existing raw sendSms suppression helper catches infrastructure errors and therefore does not suffice. STOP that arrived after preparation must block submission. Verify shared-line identity still matches the pinned sender; configuration change cannot silently move a reply to a new number. Carrier controls retain their dedicated behavior.
  5. Whole-seam recovery must audit every direct handled/TwiML branch and every side effect reached before prepared reply persistence. Existing onboarding claimTurn unavailable behavior must not fall through into unclaimed execution under durable recovery. Inflight means pending, not successful empty completion. Reuse SID-keyed branch replay and existing write idempotency; add missing narrow guards when necessary. Do not rerun a model or side-effecting branch whose outcome is uncertain merely because the final seam result was not cached. Freeze ambiguous execution for reconciliation if it cannot safely replay. An envelope plus cached final result alone is not an exactly-once guarantee for arbitrary earlier effects.

Approved execution correction B: shared receipt recovery

recoverInboundReceipts currently resolves the physical owner of the received number and drops a receipt when that owner differs from the routed receipt manager. That is incorrect for Ambika/Vinod shared-line receipts whose client owners legitimately differ from the platform number owner.

When the persisted signature-verified payload identifies shared-line routing, revalidate the current shared configuration and exact wire number, the persisted routed workspace's existence/nonarchived state and unchanged owner, and the applicable shared-line eligibility/role contract. Preserve the stored owner and subject; never route a recovery to a newly selected client. Unreadable configuration or ownership is retryable, not proof of reassignment. A proven changed owner, removed grant or retired line is terminal/refused with an honest reason. Ordinary dedicated receipts keep the existing physical-owner rule. Explicitly test the special admin-assistant continuation, whose owner/default workspace may follow a different eligibility path from resident/client routing; do not blindly apply a dedicated-workspace filter that the original admin route deliberately bypassed. Every resumed private action still re-derives live authorization through the existing typed tool context.
