Completed receipt SMS integration: changes required

Independent Astra review, 26 September 2026. Baseline b27fca80acb129fe4de7e347e87f5b0f5702ce73; runtime comparison is against the staged SMS files, backfill comparison against the prior copy in /Users/akhilvemuri/coding/AXIS-2/scripts/backfill-sms-projection.mjs, and importer comparison against migration 180. Revision 3 of the integration plan and the frozen execution report were read.

Disposition: do not approve this revision for apply or release. The new resolver has an incomplete receipt-holder authorization proof, the log feed rejects legitimate co-manager originals, and its payload validation is not NULL-safe. Correct these and the regression/scale issues below, then obtain real PostgreSQL evidence. This reviewer performed static inspection and local hash/diff checks only. No code, migration, backfill, database, provider, git state, graph, server or test execution was changed. Root retains the heavy-validation and rollback-only DEV probe slots.

Findings and concrete corrections

R1 · P1 · Receipt holder is not bound to the receiving line

supabase/migrations/20260926150000_sms_completed_receipt_originals.sql:91 and supabase/migrations/20260926150000_sms_completed_receipt_originals.sql:104. For receipt/log owner A and ingress/burst owner B, both line queries can succeed solely because a line for the wire receiver belongs to B's workspace. Neither query requires that A held that line. The later “workspace_line_unproven” check repeats B's workspace proof, without referencing v_receipt.manager_user_id. Thus unrelated A plus a self-consistent B ingress/burst can return ok:true for B. Service-only execution limits callers, but does not establish the source authorization the RPC promises.

Correction: prove the exact selected historic line epoch, its holder, and its workspace owner together. Where receipt holder and projected owner differ, require the line's manager to equal the receipt holder (or the repository's equally explicit authoritative historic holder relation), its workspace owner to equal the projected owner, and its epoch to cover the receipt instant. Do not infer A's authority from B's ownership alone. Return or consistently reuse the proven line identity. Preserve ambiguity refusal.

Tests: same-owner success; real co-manager holder A/workspace owner B success; unrelated A with otherwise exact B evidence fails; wrong holder, workspace, phone, epoch and multiple eligible epochs each fail. Assert zero projection rows and no provider/model calls for failures.

R2 · P1 · Co-manager log inventory passes the wrong expected owner

scripts/backfill-sms-projection.mjs:660 and supabase/migrations/20260926150000_sms_completed_receipt_originals.sql:200. The resolver intentionally changes owner from receipt/log holder A to ingress workspace owner B. The receipt and ingress feeds pass B, but the inbound-log feed passes row.manager_user_id (A). The RPC then returns owner_mismatch, aborting the page even if the same original was correctly projected by the earlier ingress feed. The new importer guard makes the same call before its existing preferred-ingress skip, so a direct import also fails.

Correction: distinguish source holder from canonical projected owner in both callers. Derive the expected workspace owner from the exact bound ingress and validate it through the strengthened R1 authority. Retain exact source-row identity and source accounting; reconcile/acknowledge the earlier exact ingress original under B rather than projecting under A or skipping validation. Do not substitute a different row or SID to make the call pass.

Tests: a complete multi-feed backfill with receipt/log A, owned line A in B's workspace, ingress/burst B, and retained full original must finish both clean passes. Repeat as direct historical log import. Conflicting or unrelated-owner variants must fail without cursor advancement or readiness. Re-run ordinary same-owner cases.

R3 · P2 · Missing JSON keys bypass SQL validation

supabase/migrations/20260926150000_sms_completed_receipt_originals.sql:43 and supabase/migrations/20260926150000_sms_completed_receipt_originals.sql:61. For a processing/retryable receipt with a present object containing valid fromPhone/toPhone but no body, no log and no ingress, jsonb_typeof(payload->'body') <> 'string' evaluates to SQL NULL. NULL OR FALSE OR FALSE is NULL and PL/pgSQL does not enter the IF. The function returns ok:true, body:null. The TypeScript/backfill adapters currently reject that body, so this is a broken authority contract, not evidence of a successfully inserted null-body turn. SQL importer also has a later null-body guard. It still violates the required malformed-payload refusal and leaves direct consumers exposed to a false success.

The sender comparison v_sender_key <> recipient_phone_key similarly fails to reject NULL. However, the committed receipt DDL declares this column NOT NULL; no reviewed migration removes that constraint. A nullable sender-key reproduction requires target drift or altered test constraints. Do not describe it as reachable on the repository schema without catalog evidence. The real completion trigger also clears any completed non-null payload; malformed-present fixtures should use processing/retryable rows, with exceptional legacy-state cases labeled explicitly.

Correction: require a JSON object and use IS DISTINCT FROM 'string' for every required field; explicitly validate the resulting body/wire and use NULL-safe sender equality. Keep SQL NULL separate from JSON null and never fall back for any malformed present value. Audit other nullable comparisons without weakening existing schema guarantees.

Tests: real SQL cases for omitted body/from/to, JSON null payload, scalar/array payload, JSON-null fields, numeric fields, valid empty-string body policy, and conflicting present payload plus valid log. Add a catalog assertion for sender-key NOT NULL and a deliberately nullable defensive fixture if needed. Each malformed case returns a stable failure, never success or fallback. Exercise adapter failure handling too.

R4 · P2 · New identity conflict check rejects allowed queued enrichment

src/lib/sms/inbound-pipeline.server.ts:149. A classified pending retry with prior.counterpartyUserId=U and a valid retained receipt envelope can now fail whenever the log is absent or has no matched user: the resolver returns userId:null, and the new check treats absence as a conflicting identity. The staged implementation could retain that queued classification. This blocks the plan's bounded classified-pending path even though original.userId || prior.counterpartyUserId below still purports to support it.

Correction: distinguish unknown identity from a contradictory non-null identity. Preserve only the established authorized producer-enrichment path, with exact original owner/SID/body/wire/time binding; do not broadly trust arbitrary queued identities. If current queued evidence is insufficient, retain an explicit pending disposition until independently classified rather than treating “unknown” as an identity mismatch. Never downgrade a known resident/vendor/manager to prospect.

Tests: pending retained payload plus authorized queued user classification; completed log with the same user; log with a different user; unknown source with untrusted queued user; role mismatch; user deletion/null identity policy. Verify successful bounded enrichment and fail-closed contradictory identities without side effects.

R5 · P2 · New read workload lacks suitable historic-line and full-receipt scan indexes

supabase/migrations/20260926150000_sms_completed_receipt_originals.sql:91, scripts/backfill-sms-projection.mjs:607, scripts/backfill-sms-projection.mjs:660. Receipt, ingress and log exact-SID lookups are indexed by receipt/ingress primary keys and the non-null unique log SID index. Their counts are bounded by those constraints. The line lookup includes released, so the existing phone unique index (predicate provision_state <> 'released') cannot cover the whole lookup. No full historic-phone index was found. The now-expanded receipt feed orders all rows by (first_received_at,message_sid), while the existing recovery time index only covers unfinished rows with payload. That index cannot serve the full completed-null inventory. The log feed additionally starts up to the whole 500-row configured page of RPCs concurrently.

Correction: add narrowly appropriate indexes in new unapplied SQL for the full receipt cursor and historic phone/epoch lookup, or supply representative query-plan evidence of an equivalent existing target index. Bound RPC concurrency independently of page size; keep burst work bounded as well. No provider fetches belong here.

Tests: root-owned EXPLAIN evidence at representative cardinality for first and subsequent receipt pages and active/released line probes; a focused mock test proving maximum concurrent RPCs. Ensure the new indexes preserve duplicate/epoch ambiguity checks rather than selecting an arbitrary first match.

Retained integration hazard, not introduced by this delta

P1 acceptance gap: src/lib/sms/inbound-pipeline.server.ts:159 queries a provider SID globally, checks only body/time/wire, and returns success for an unclassified/source-intent retry at line 170 before checking the projected owner at line 171. It also does not load conversation role/user/work-line identity. This code exists in the staged SMS version; it is not charged as a new regression. Nevertheless, the explicitly requested wrong-owner/line and conflicting-existing-projection acceptance cases cannot pass with this shortcut. Before declaring the completed-receipt integration safe, validate owner, direction, line and grounded classification before acknowledging the turn. Add wrong-owner exact-envelope, wrong-line, wrong-direction and incompatible-role/user existing-turn cases. Every such retry must remain failed, not be marked complete. A correct existing turn may still be acknowledged idempotently.
