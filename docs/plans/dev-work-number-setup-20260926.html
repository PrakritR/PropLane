How the existing product provisions a number

In Manager Settings → Communication → Channels, “Set up a work number” calls POST /api/manager/messaging-number for the selected owned workspace. It is a billable Twilio number purchase. The route requires an eligible communication plan, a non-paused sms_runtime_config mode that includes Akhil's manager ID, and SMS_PROVISIONING_ENABLED=1. Signup alone only parks a record. Each workspace can hold one work number, and the purchased number is persisted in manager_sms_numbers and attached to the configured Twilio Messaging Service. The code sets the number's own SMS webhook at purchase to <TWILIO_WEBHOOK_URL>#rp=ct,5xx&rc=2; inbound signature validation uses the same URL without the fragment. Sending additionally requires carrier registration, Messaging Service attachment, communication credit, runtime enablement and an outbox scheduler.

The current local environment has Twilio account/auth credentials, a Messaging Service and campaign ID, but no local restricted API key pair. Development can use the Auth Token REST fallback; production requires the restricted key pair. SMS_COMM_UI_ENABLED is on locally, which reveals the UI but does not enable transport. QStash URL, token and signing keys are present, while PROSPECT_SMS_BURSTS_ENABLED and its public callback URL/secret are absent. That means the durable prospect AI burst path is not ready merely because an inbound webhook works.

Recommended laptop-only test path

  1. Confirm scope in Twilio before purchase. Use an SMS-capable US local number dedicated to this dev/test workspace. Confirm the configured Messaging Service and A2P campaign can attach another number without changing existing production senders. Inspect its inbound Integration setting. Twilio's default “Defer to sender's webhook” lets the new number use its own callback; a service-level common webhook would override it. If the existing service does not defer, stop and use a separate reviewed dev Messaging Service/campaign path rather than changing shared routing. Twilio documents this behavior in its Messaging Services guide and Service API reference.
  2. Start only for the test window. Run the app against the dev/test project on a pinned local port, then expose that port with a temporary HTTPS tunnel. Set TWILIO_WEBHOOK_URL=https://<dev-tunnel-host>/api/twilio/inbound in the local test process and verify it is exactly the URL Twilio will sign. Set the status callback and any Event Streams sink to dev endpoints only if those paths are part of the chosen test. Keep the tunnel and server running while waiting for a real incoming text; stop task-owned processes after the test. A laptop-only setup cannot receive while the laptop or tunnel is offline.
  3. Establish the app gates. Confirm the dev database runtime mode and Akhil's allowlist entry; confirm his owned default workspace and plan eligibility. Enable number provisioning only for the controlled request window. In Settings → Communication → Channels, request one number for that workspace. The request is idempotent after a completed purchase, but an uncertain provider response must be reconciled before retrying. Check that the new number's own webhook targets the dev tunnel and its Twilio Phone SID, Messaging Service attachment and registration state appear on the dev row.
  4. Test receive, then send. Text the new number from a phone Akhil controls. Confirm the signed inbound webhook reaches dev/test, stores the inbound receipt and places the conversation in the correct manager workspace. For a real reply, first confirm the number is carrier registered and the app's communication credit, runtime and five-minute scheduler gates are satisfied. The checked-in daily Hobby cron is only a safety net. Do not turn on broad automatic sends just to prove inbound receipt. US local-number outbound traffic requires A2P 10DLC brand, campaign and number registration, per Twilio's A2P guide.
  5. Close the test window. Disable local purchasing and sending flags, stop the verified task-owned app and tunnel processes, and retain the dedicated dev number's ownership and callback record. Do not repoint any production sender or global Messaging Service inbound setting. A later test needs a fresh tunnel URL and a reviewed update to this dev number's callback before incoming SMS can reach the laptop.
