## R1 - High / P1: old acknowledgements clear unread for newer merged sources

Location: `src/lib/portal-inbox-storage.ts:981-986`; latest-cache caller at `src/components/portal/pro-unified-inbox.tsx:1003-1004`.

Reconciliation selects only observations matching the old request and derives the entire merged row's unread flag from that subset. A newer source or revised member remains in the current row but is excluded from that calculation. The older response therefore suppresses its unread badge even though the database CAS correctly preserved it.

Confirmed using the actual helper body:

```text
current row: unread=true, observations=[A:old-A, B:new-B]
request: [A:old-A]
result: A unread=false
actual current row after reconciliation: unread=false
required: retain unread=true for unacknowledged B
```

The same defect occurs when B was in the original request but its observation has changed. An absent result also becomes false implicitly. The existing singleton newer-observation test does not exercise either aggregate case.

Correction: only change an aggregate when every contributing current source is accounted for by matching observations and valid results, or maintain enough per-source unread state to safely recompute it. Mixed legacy/no-observation and conflicting sources must fail closed. Never restore old body/history/folder/draft/attachment values.

## R3 - Medium / P2: pending email deduplication loses new SMS reads and returning-viewer requests

Location: `src/components/portal/pro-unified-inbox.tsx:998-999`; accepted-signature latch at `src/components/portal/pro-resident-detail-inbox.tsx:278-279`.

The pending signature contains viewer ID and email observations, while the pane's viewed signature also contains inbound SMS IDs. Start an email acknowledgement, hold its response, and render a new inbound native SMS. `onViewed` returns true at the pending-signature check before opening the new SMS. The pane records the new combined signature as handled, so settlement does not trigger another acknowledgement. The displayed SMS can stay unread until a fresh open.

The same set survives A -> B -> A. A current epoch-3 A request with the same observations joins the epoch-1 signature, yet the old response is correctly discarded by the epoch guard. The current viewer consequently gets neither an applicable result nor a new request. Deleting signatures in an old `finally` must also not remove a newer request's entry after correction.

Both early-return behaviors were reproduced by invoking the actual extracted callback with controlled promises. Correction: separate local SMS observation from email network deduplication, scope pending ownership to the viewer authority/epoch, and report a view handled only when its represented sources were handled. Keep retained old callbacks fail-closed before side effects and preserve bounded retries.

## R4 - Medium / P2: failure handling invents unread state and loses partial success

Locations: `src/components/portal/pro-unified-inbox.tsx:1022,1031`; `src/app/api/portal-inbox-threads/route.ts:165-166,172`; local storage call before POST at `pro-unified-inbox.tsx:1012`.

Three reachable failure paths need one coherent correction:

1. The selected source set includes already-read email sources. Any HTTP failure assigns `unread=true` to every source, so opening an already-read email+SMS conversation during a failure manufactures an unread email badge. Confirmed with the actual reconciliation helper and the failure map used by the callback.
2. The route commits sources sequentially. If A succeeds and B's RPC fails, the thrown error discards A's successful result. The client receives a generic 500 and treats A as failed too. This is the security review's P2 finding; no authorization bypass or rollback of the actual database write was found.
3. `markManagerSmsOpenedIds` can throw from `localStorage.setItem`. It runs after optimistic email staging and pending insertion, before the POST and its promise handlers. Injecting that error into the actual callback left the email locally read, made zero POSTs, and retained the pending signature. This can strand both read state and retry.

Correction: preserve exact prior unread metadata for failed/unknown observations, retain/report committed per-source outcomes on later failures, and reconcile only compatible current snapshots. Handle synchronous receipt-storage failure without leaving an optimistic patch or pending lock. A bounded revalidation may resolve an unknown transport outcome; never report success or restart an unbounded render/fetch loop. Malformed/partial result arrays must not count missing IDs as successful acknowledgements.
