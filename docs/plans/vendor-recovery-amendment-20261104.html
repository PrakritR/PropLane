Vendor release: account recovery classification

Decision for implementation review, 4 November 2026. This is a bounded extension of the existing account recovery framework, not a new archive system. No database, provider, or code changes were performed for this plan.

Decision and user-visible consequence

Explicitly exclude the twelve new operational tables below from replay. Preserve the existing canonical business records through their current recovery rules: manager_vendor_records, portal_work_order_records, work_order_bids, and portal_inbox_thread_records. Existing independently owned invoice/payout preservation remains intact. Recovery must not re-enable a sender assignment, consent, phone verification, capability, queued delivery, approval, or sourcing run.

This is not lossless coordination recovery. Unapproved structured quotes, discovered-but-unmaterialized candidates, proposed windows, coordination revision history, and operational reservation rows reset. Already recorded inbox messages remain readable; approved repair prices, scope, exclusions and schedule survive in the service and accepted bid; approved consultation fee and time survive in the service. Do not claim that every unapproved quote exists in inbox history. A later request to resume coordination requires fresh verification and explicit action. Stale proposal/capability IDs in historical service/inbox JSON are references only and must fail closed.

Privacy and existing framework behavior

The generic snapshot already creates temporary holds for nonrecoverable rows. The capture-delete trigger only marks an existing hold archived; it does not independently create snapshots. Completing archival erases nonrecoverable payloads and keys, recursively including their children. These hooks are necessary to finish archival and fence stale writers, even for never-restore tables. They must not introduce another history copy, plaintext export, or long-lived secret retention. Test that nonrecoverable payloads are erased after finish_archival, including token/challenge material and quote-response content. Interrupted archiving follows the existing private retry lifecycle; no claim of zero transient retention is made.

Required implementation amendment after lifecycle inspection

Vendor-only reference recovery: the never-restore rule applies to deleted operational rows. If the current framework lacks the directory agreement check, add a narrow check for those two reference targets; do not redesign generic reference recovery. Final bounded amendment: accepted bid restoration with a surviving manager proposal

Actual vendor-only deletion removes the vendor-owned accepted bid and the proposal FK becomes NULL; manager recovery has no surviving proposal, but vendor-only recovery does. Keep current ownership/purge rules for this release. Do not introduce a new financial ownership classifier. Permit the exact archived accepted bid to return through existing recovery under a narrow extension to the legacy approval fence.

The exception applies only to INSERT, never a new acceptance UPDATE. Require the internal recovery flag AND an exact archived, non-erased, recoverable work_order_bids record whose primary key and full persisted JSON payload equal NEW; the stored status must already be accepted. Require a matching delete hold with decision recover, a request in recovering state with decision recover, non-null claim ID, portal vendor, and user ID equal to NEW.vendor_user_id; require account_recovery_publishable(record.id). The internal flag alone is insufficient. Preserve the service advisory lock, accepted-winner unique constraint, and accepted-price immutability.

A surviving active proposal must be the approved proposal named by the canonical service coordinationProposalId, with identical manager/service/vendor-directory identities and approved prices, scope and scheduled time consistent with the canonical service and exact archived bid. Its accepted_bid_id may be NULL or already that bid, never a different ID. Reject any competing active proposal, different accepted winner, changed approved terms, reassignment or missing canonical proof. Restore-reference processing overwrites the retained proposal payload before bid insertion, so its original accepted_bid_id is not reliable evidence; use the canonical service link and exact financial terms. After successful insertion, conditionally reattach only the proven proposal's NULL accepted_bid_id. Do not change proposal status, approvals, confirmations, price, schedule, notifications, or payment state.

Tests must reproduce actual vendor-only deletion and recovery against the legacy fence migration, then reject fake internal flag alone, no held archived record, wrong portal/user/claim/decision, altered bid ID/amount/materials/status/scope/time/owner, changed canonical proposal/service, competing approval, and changed non-NULL pointer. Ordinary legacy acceptance remains fenced with 40001. Genuine recovery preserves the original bid identity and amount, restores the FK only, and emits no action event, delivery, invoice or payout. If canonical evidence no longer matches, fail closed without overwriting manager changes.

Privacy correction: supersedes all earlier service-phone instructions

Do not add consultationVendorPhoneE164 or any raw phone or low-entropy phone hash to portal_work_order_records.row_data. Residents can read that row through PostgREST and vendor readers spread its JSON. API redaction alone cannot make that storage safe. The canonical service may store consultationVendorDirectoryId; historical phone collision evidence belongs in the existing private manager_vendor_records.row_data.

Use one server-owned appointment-evidence map keyed by service ID and visit type on the exact manager-owned directory row. Its values contain the actual approved proposal ID, start/duration (or exact interval), and verified phone snapshot. Backfill only exact previously specified approved proposal/reservation/canonical-service matches. SQL conflict checks join that private evidence and require the canonical service's directory/proposal/time/kind to agree; cross-directory collisions can compare historical phone privately. Current mutable directory phone alone is insufficient after a contact change. No new table, new archive system, public phone, or public hash is needed. Existing directory recovery restores this historical business evidence without restoring a phone verification binding.

Protect the map with a narrow server-owned field guard. Ordinary INSERT cannot supply it. Ordinary UPDATE that omits it carries the OLD map forward so normal full-row directory edits remain usable; an explicitly supplied changed map is rejected. Only the existing trusted coordination-write and account-recovery paths may change it. All public/shared/vendor/resident projections must exclude the map. It is collision evidence only, never consent, authentication, payment approval, or message authorization. Cancellation clears active service time; retained private evidence cannot block an appointment unless the current canonical service still matches. Test raw resident PostgREST service JSON, vendor/shared projections, ordinary directory edits, attempted tampering, recovery and cross-directory conflict.
