P2: a successful first read can revive invalidated work

src/lib/supabase/portal-session-refresh.ts:109-114 accepts a successful read after the generation has changed whenever its session identity matches the current identity. The first-read continuation at lines 139-145 then adopts the current generation. This does not distinguish another concurrent read establishing the initial session from a genuine auth lifecycle transition or explicit component disposal.

Deterministic counterexample: establish session A, begin another refresh with its first getSession pending, observe B and then A with the original identity, and resolve the pending read with A near expiry. The old invocation passes the identity exception, acquires the new generation, and can start its second read and explicit refresh. A permanent error at that point can invoke application cleanup under the newly adopted generation. The same revival occurs when invalidate() runs during a pending first read while the active identity remains A: the component has unmounted, yet the old invocation can mark signed-in state and initiate new auth work.

There is also no lifecycle check in the outer continuation immediately after await readSession(...). A lifecycle event between the inner helper returning and the outer continuation resuming can therefore bypass even the helper's last generation check. Guard the continuation before observing a session or producing side effects.

Existing A-to-B-to-A, same-user re-login, and component-unmount tests defer the explicit refresh result. They correctly cover already-established work, but not a successful pending first read that rebinds itself after invalidation. The error-only pending-read tests reject correctly and do not cover this exception.

Bounded correction and acceptance

  • Separate lifecycle/disposal invalidation from harmless initial-session observation by concurrent reads, or use another explicit ownership scheme. A stale invocation must not adopt a lifecycle epoch that began after it started. Preserve same-session coalescing without treating identity equality as permission to cross a lifecycle boundary.
  • Check lifecycle ownership after asynchronous read continuations and before marking signed-in state, starting further SDK calls, or initiating application cleanup. A SDK read may itself rotate a token; its valid renewal must not cause a redundant explicit refresh. It is safe for a detached invocation to return without additional side effects after the SDK has already renewed successfully.
  • Add deterministic successful-first-read cases for A-to-B-to-A using the same A token, sign-out/re-login, and invalidate/unmount. Assert no additional second read, explicit refresh, signed-in marker mutation, or application cleanup from detached work. Include the boundary between helper completion and outer continuation.
  • Retain fresh-session no-refresh and concurrent coalescing coverage. Add an SDK-shaped renewal test that changes refresh_token and emits TOKEN_REFRESHED before getSession or refreshSession resolves; current renewal fixtures either retain the original token or omit the auth callback.

What is sound in this correction

The component subscribes synchronously to auth lifecycle changes and unsubscribes on disposal. Observed identity changes advance generation, so late permanent errors from an already-started explicit refresh cannot clear a later account, including A-to-B-to-A and same-user re-login. The component now calls raw getSession through an adapter that adds no cleanup itself. Returned and thrown permanent first/second-read errors pass through coordinator checks; transient failures do not intentionally invoke the additional application cleanup.

The disposed native callback does no work. A listener handle received after unmount is removed immediately, and a handle received before unmount is removed during cleanup. Its focused test covers delayed registration completion. No auth restoration, guard relaxation, vendored SDK patch, database change, or global recovery redesign is introduced.

The expiry test skips fresh sessions before explicit refresh, and coalescing works for stable identities. A rotated second-read session exits without another explicit refresh. A real TOKEN_REFRESHED event normally changes generation before explicit refresh resolves, causing the coordinator to return owner-changed even on successful SDK renewal; the component ignores the result, so this conservative classification is not itself a functional blocker.

SDK limitation and validation boundary

The handoff accurately limits the 429 guarantee to application-triggered cleanup. Installed node_modules/@supabase/auth-js/src/lib/fetch.ts:39-50 does not classify normal JSON 429 responses as retryable infrastructure failures, and GoTrueClient.ts:4621-4625 removes the session for non-retryable auth errors. The raw getSession adapter is non-destructive only at the application layer; SDK reads can auto-rotate and can internally remove a session. The unit test title “keeps local auth after rate limiting” overstates its mocked assertion and should say it avoids additional application cleanup. Never restore tokens to counter this SDK behavior.
