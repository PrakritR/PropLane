Concrete findings

R9 - P1: normal manager SMS histories are erased from the returned list

src/lib/manager-sms-messages.server.ts:1047-1049 saves the helper result, clears conversations.length, then spreads the result back. At :698-700 the helper returns the original array when no directory was absorbed. Both variables therefore alias the cleared array. Any mailbox without a successful prospect identity upgrade loses its existing SMS rows, including ambiguous shared-phone histories. This also makes downstream lifecycle lookup report no conversation or create a replacement thread. Keep the original input intact or return an independently allocated result before replacing it.

The coordinator reported five failures in sms-conversation-identity.test.ts: missing rows in shared-phone, existing residents, role separation and owner attribution match this defect; the lifecycle test separately reaches a missing .neq mock method. These must be fixed independently, without weakening expected isolation.

R10 - P1: an explicit binding accepts completely contradictory stored identity

src/components/portal/resident-communication.tsx:184-192 reports conflict only if at least one identity field overlaps. The explicit-bound path at :431-452 reuses that predicate. A stored email row with manager A/property A/email A and an explicit key for manager B/property B/email B has no overlap, so it is declared nonconflicting, renamed B and merged into B's SMS. For a selected explicit binding, reject every nonempty contradictory field without requiring overlap. Keep the overlap check only for finding relevant unbound candidates.

R11 - P1: collapse discards negative identity evidence while retaining the binding

src/lib/portal-inbox-storage.ts:1188-1191,1217-1221 clears a conflicting property or manager value to undefined but preserves a singleton SMS binding. Example: two same-email sources carry properties A and B; only source A declares key A. Collapse emits no property id plus key A. The resident bound resolver then treats the erased property as absent and folds both histories into A. This is not fail-closed conflict handling. Preserve an explicit conflict state or keep incompatible sources isolated, and ensure subsequent client collapse/propagation cannot erase that state. Test the actual storage-to-component path, not hand-built already-resolved list items.

R12 - P1: delivery overwrites existing relationship and binding provenance

src/lib/portal-inbox-delivery.ts:483 spreads incoming threadIdentity over an existing person thread selected by email/folder only. A property-A history receiving a property-B lease/payment/service message becomes entirely property B; a new application binding similarly replaces the old smsConversationKey. The prior contradiction is permanently lost before the read-time checks can see it. Reuse the compatible identity policy or accumulate conflict provenance instead of last-write-wins identity. Preserve message delivery and source ids; do not silently drop the new message.

R13 - P1: applicant enrichment can reassign a prospect to the wrong shared-phone person

src/lib/manager-sms-messages.server.ts:650-675,680-695 links by owner + phone and counts only directory rows with zero messages. It does not prove the submission's exact owner/work-number/conversation association and ignores competing directory identities once they have any messages. With applicant A already having native messages, applicant B having an empty directory row, and one prospect history on their shared phone, the function attaches the prospect to B, even though the owner has two known people on that number. An older approved resident on a recycled number can likewise be assigned an unrelated prospect. Require a server-proven submission association and evaluate all conflicting identities, not just empty candidates. Keep saved contact labels unchanged.

R14 - P2: unread/search selection removes the other channel's history

src/components/portal/resident-communication.tsx:406-416,504-515 filters email and SMS separately before identity merging. If the email is unread and its SMS is read, Unread opens only the email; the reverse opens an SMS-only pane and loses the existing email reply surface. Searching text that occurs on only one channel has the same effect. Build complete, authorized membership for the chosen active/archive partition, then filter conversation rows. Opening a matching row and archiving it must retain all proven members in that partition.

R15 - P2: rejected applications lose the newly recovered applicant identity

src/lib/manager-sms-messages.server.ts:458-459 excludes rejected applications from the directory, while the new name/email upgrade at :685-690 exists only in the returned object. After rejection the next loader has no directory identity and reverts the retained prospect to phone/null email (after R9 is repaired). The new lifecycle test only transitions submitted to approved. Preserve the proven identity after rejection without treating rejected applicants as active residents or broadening communication authority.
