R1 · P1 A client can plant or erase the imported-template review receipt

src/app/api/portal-lease-pipeline/route.ts:620, src/app/api/portal-lease-pipeline/route.ts:631, src/app/api/portal-lease-pipeline/route.ts:805, src/lib/lease-pipeline-storage.ts:1065

Finding. The generic upsert restores templatePlacementReview only when a stored row exists. A new Manager Review row can therefore carry a client-created receipt, with computable source/final-HTML hashes, any reviewer and timestamp. A subsequent send trusts that stored receipt without the dedicated confirmation action having run. There is also a two-write omission bypass: replace an unsigned HTML body in Manager Review with the required version increment while clearing templateImportReview, templateDocumentUrl and changing the mode to proplane-generated, then send. The first write drops stored provenance at line 631; the later send sees no imported template to gate. Simply omitting metadata on a same-body send is protected, but these other paths are not.

Correction. Make the receipt server-owned on create and update: generic writes must strip/reject it on insert and only retain a server-stored receipt on update. Preserve imported provenance across ordinary document edits and refuse a client-authored downgrade. A legitimate change to a different source or PropLane template needs an explicit authorized transition with fresh provenance, invalidation and version checks.

Acceptance tests. Route tests: create an imported Manager Review row with a forged valid-looking receipt, then send without confirmation (reject); edit + remove provenance + send (reject); same-body omission (still reject); legitimate source replacement and explicit PropLane regeneration (work); dedicated confirmation with owner/source/CAS checks (works). Include an invalid confirmedByUserId even when hashes match.

R2 · P1 Omitting the uploaded parse skips the server send gate

src/app/api/portal-lease-pipeline/route.ts:762, src/app/api/portal-lease-pipeline/route.ts:776

Finding. The new send guard requires nextRow.uploadedLeaseParse to be truthy before checking it. The generic client-controlled row can omit/null the parse while retaining the uploaded PDF and imported-converted HTML. Omitted-document restoration preserves bytes, not this parse. This skips source-review, coverage and exact-converted-hash checks. A manager can send the unreviewed converted body by POST even though the normal UI refuses it.

Correction. Infer the required import gate from trusted stored provenance and effective document mode, not the presence of optional request metadata. Require/restore the stored parse for imported rows; reject missing provenance for imported-converted uploads. Bind review of a direct upload to a server-confirmed source and body, and preserve intentional legacy original-PDF behavior explicitly.

Acceptance tests. Route tests with existing uploaded rows: omit/null uploadedLeaseParse, omit source coverage, alter the source, change the converted HTML, forge review fields and change mode. Every imported send must fail until exact-source/exact-body review is valid. Cover legacy original-PDF rows without a historical parse separately.

R3 · P1 Required identity can be disabled through the question override

src/lib/rental-application/application-field-catalog.ts:492, src/lib/rental-application/application-field-catalog.ts:425, src/lib/property-application-templates.ts:133, src/lib/rental-application/validate.ts:138

Finding. Identity removal is partly guarded, but an override with required:false for full legal name, phone or email is accepted. The publish gate checks only disabled keys. The changed validator uses the override as its validation switch. A Node 22 probe published this config and validateRentalWizardStep(2, blank identities, published property) returned {}. Published configs also bypass the legacy asStringArray identity filtering, so identity enforcement must happen on the resolved configuration itself.

Correction. Enforce enabled=true and required=true for the three canonical identity fields in one normalization/policy function used by editor, publish, preview and server submission. Disable/refuse the editor required toggle for these fields. Reject forged published config and forged submit attempts without relying on the UI.

Acceptance tests. Test both legacy and published configs with disabled identity keys and required:false overrides; test the actual submission route and blank/invalid name, phone and email. Verify one editable identity question each remains visible and mandatory.

R4 · P1 PDF JavaScript in annotation actions is accepted

src/lib/pdf-import/pdf-source.server.ts:104, src/lib/pdf-import/pdf-source.server.ts:178, src/lib/pdf-import/pdf-source.server.ts:196

Finding. The scan checks document and page getJSActions, then processes Widget fields. Those calls do not cover all annotation action dictionaries. A generated PDF with a Link annotation whose /A is /S /JavaScript imported successfully with coverage.complete=true and no issues in a Node 22 probe. Its original bytes are retained and served to viewers. No browser execution was attempted; the confirmed defect is that forbidden active content is accepted.

Correction. Inspect actual PDF action dictionaries for catalog, page, annotation and widget actions, including chained actions and compressed objects, using a parser that preserves those structures. Fail closed for unsupported executable actions/embedded payloads. Do not convert a security rejection into an ordinary parse failure that the original-PDF review can approve.

Acceptance tests. Fixtures: JavaScript Link /A, Widget /AA, document/page JS, chained /Next actions, Launch and embedded files, including compressed objects. All forbidden files must be rejected before a usable source is stored/served. Ordinary links, form fields and text PDFs must follow the chosen documented policy without silent false acceptance.

R5 · P1 Application mapping silently loses or misidentifies source questions

src/lib/rental-application/application-pdf-import.ts:32, src/lib/rental-application/application-pdf-import.ts:76, src/lib/rental-application/application-pdf-import.ts:117, src/lib/rental-application/application-pdf-import.ts:133, src/lib/rental-application/application-pdf-import.ts:141

Finding. Identity matching uses substring phone/email, so Emergency contact phone and Landlord email become applicant phone/email. If they appear first, the later actual applicant prompts are discarded by mappedStandard. The same probe showed Explain how you will pay rent disappearing because it lacks punctuation, and Parking required becoming optional, all with issues:[]. Thus an apparently clean import can lose questions and required state without a review blocker. The mapper also sets required from the canonical definition rather than recognizing text-required markers or flagging uncertainty.

Correction. Use conservative applicant-only identity aliases with subject/context boundaries; retain third-party contact questions as distinct custom questions. Account for every nonempty source block as mapped, intentionally classified non-question, or an unresolved issue, with provenance. Preserve/resolve required markers and ambiguous types/options explicitly. Deduplicate only proven identical questions, not any shared field class.

Acceptance tests. Fixtures with applicant/landlord/employer/emergency contact names, phones and emails in different orders; first/last names; required markers; punctuation-free prompts; multi-line prompts; repeated household-member prompts and long blocks. Assert no silent omissions, correct subject mapping, exact source wording, required state, and unresolved coverage gating publication.

R9 · P2 Optional fields now skip validation even when populated

src/lib/rental-application/validate.ts:138, src/lib/rental-application/validate.ts:335, src/lib/rental-application/validate.ts:390

Finding. The old fieldEnabled predicate has been replaced with fieldRequired for the entire standard validator. This disables all validation for optional fields, including checks previously written to allow blank but reject malformed populated values (for example currentLandlordPhone and monetary amounts). Making a field optional should waive presence, not validate arbitrary input.

Correction. Separate enabled, required and present-value validation. Validate populated optional values according to the typed field, while only reporting missing-value errors when required. Preserve dependency and authorization checks independently of the required toggle.

Acceptance tests. Test blank optional values pass, malformed populated phones/dates/money fail, valid optional values pass, disabled fields are not accepted, and required toggles affect only the intended absence constraints. Cover both legacy standard forms and published imported templates.
