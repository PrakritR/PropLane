E2E auth session isolation plan

Scope: source-only investigation for the full-browser CI auth failures. No source or test implementation was changed for this plan, and no runtime, browser, database, Node, install, or Git operation was run. Root's private artifact evidence reports repeated Supabase refresh-token reuse failures after initially successful authenticated requests; token values are intentionally omitted.

Finding

tests/e2e/auth.setup.ts signs in each seeded role once and writes manager.json, resident.json, and admin.json. Playwright then gives many independent test contexts the same serialized Supabase session. Supabase refresh-token rotation makes that state single-use once a context refreshes it; another context reusing the old refresh token receives refresh_token_already_used. This explains the CI pattern of successful initial dashboard/API requests followed by token refresh failures. A one-time storage state is not a safe shared credential for independent tests.

Recommended narrow architecture

  1. Add role fixtures in an E2E helper module, each overriding the Playwright page fixture to run signInAsManager, signInAsResident, or signInAsAdmin on the already-fresh test context. Keep the existing storageState: { cookies: [], origins: [] } default, or make it explicit in the fixture.
  2. Migrate manager-only, resident-only, and admin-only specs above to the matching role fixture and remove their test.use({ storageState: ../.auth/*.json }). Their beforeEach hooks should retain Stripe mocks, viewport setup, and route setup, then use the authenticated page. Do not add reauthentication to gotoAppPath or navigation helpers, because that would hide real session-expiry behavior.
  3. For portal-interconnect.spec.ts, keep three describes but sign in the role in each describe's beforeEach on an empty context. This avoids trying to change a role fixture dynamically inside one imported Playwright test object.
  4. For conversation-identity.spec.ts, replace the manager manual context's serialized state with an empty context followed by signInAsManager(page), then install the fixture workspace cookie. The resident half already performs a fresh password sign-in and should remain that way.
  5. After all consumers are migrated, remove the setup dependency and the three serialized role artifacts from the project configuration if no remaining spec references them. Keep tests/global-setup.ts's fresh per-role preflight contexts; it is an independent credential smoke check and does not serialize a session.

Validation plan for root

  • Static check that no E2E spec except the auth setup producer references ../.auth/*.json.
  • Run the focused conversation spec and the manager portal subset separately, then the full suite, confirming each test starts with a password sign-in in its own context.
  • Retain the existing zero retries and one worker. A refresh-token error must remain visible if it occurs during a test; the fixture only establishes initial authentication.
  • Keep sign-out and wrong-password cases outside any authenticated role fixture so they continue to exercise unauthenticated transitions.

This architecture removes the shared rotating refresh-token dependency while preserving real auth, role routing, portal-cookie establishment, session-expiry assertions, and sign-out coverage.

Root implementation decision

Approved for implementation after the current unit/workflow corrections are handed off. Use one test-scoped Playwright fixture with an optional role option (default null). A selected role starts from an explicitly empty browser context and invokes the existing real sign-in helper once before the page is yielded. Mixed-role and public describes can use the same fixture with scoped role options. This avoids maintaining separate imported test objects and preserves public tests. Do not catch and retry navigation/auth failures. Test timeout and full-suite limits remain unchanged.

Retain the setup project as the existing credential/role smoke check for this change; remove its serialization once no consumers remain. Do not broaden global config or production auth behavior. The manually created conversation manager context must sign in freshly with its existing external-write fence installed, then set the exact owned workspace cookie and continue the existing assertions and cleanup. Keep dev target guards and all send fences.

Validation: add a focused test of fixture role dispatch and fresh-context policy where behavioral testing is practical; static inventory must show zero saved-role session consumers. Independent source review precedes remote validation. Run the full suite after earlier focused conversation validation to identify genuine UI defects remaining after auth isolation.
