Conclusion: multiple issues contribute. The most concrete avoidable delay is the native sign-in session gate. Manager rendering also waits for billing-provider reconciliation; client startup triggers unrelated prefetches and redundant refreshes. Static CDN caching works. Current analytics cannot allocate total delay between server response, data loading and rendering, and the existing route breakdown misattributes some metrics.

Measurement defects

  • The whole project captured 2,393 web-vitals events in seven days; only 498 were on the two canonical production hosts. A host-unfiltered dashboard mixes development activity into production.
  • Of 172 production LCP samples, 52 (30%) have a different original navigation path from the event pathname after stripping query strings; another 8 lack navigation URLs. Eight Communication-attributed samples originated on the dashboard. The metrics themselves may be valid, but the current page grouping is misleading.
  • Captured web-vitals fields expose LCP, FCP, INP and CLS, but no TTFB or LCP subpart attribution. Sampled LCP entries contain empty objects. No native-runtime dimension appeared in the captured vitals property keys. There is also no reliable portal data-ready or SPA navigation-ready timing in the existing signals.
  • Taxonomy discovery via read-data-schema failed because the key lacks action:read. SQL schema discovery and bounded event inspection succeeded. No settings, dashboards or permissions were changed.

Findings and recommended fixes

1. Native sign-in waits roughly eight seconds before showing its form

src/components/auth/native-auth-hub.tsx:94,156–183,288 initializes checkingSession to true, calls waitForOAuthUser in native runtime, and shows a loading card until it finishes. src/lib/auth/wait-for-oauth-user.ts:5–31 uses an 8,000 ms wall-clock deadline; its attempts option is accepted but never read. The caller's four-attempt request does not bound the loop to four attempts. A signed-out user can therefore wait through a full polling window. The 2,500 ms per-attempt timeout is not clamped to the remaining deadline, so a final slow call can extend the wait beyond eight seconds. Ordinary web visitors skip this wait.

Fix direction: separate passive existing-session detection from active OAuth recovery. Show the signed-out form promptly after a bounded local session check; retain polling only while a genuine OAuth flow is in progress. Honor or remove the misleading attempts option. Preserve implicit-link recovery, returning authenticated users, native OAuth visibility recovery, and fail-closed authorization. Validate on actual iOS/Android shells as well as ordinary browsers.

2. Manager layout performs external billing work before returning its shell

src/app/portal/layout.tsx:39–47 waits for buildProPortalDefinition. src/lib/portals/pro-nav.ts:48–49 and src/lib/manager-access-server.ts:162–167 reach syncManagerPurchaseTierState. src/lib/manager-tier-sync.ts:83–105 serially reconciles Stripe, Apple, revocation, expiry and co-manager state. Eligible Stripe customers await a subscriptions.retrieve request (manager-stripe-subscription-sync.ts:173); Apple customers may await RevenueCat (manager-apple-subscription-sync.ts:308). These wrapper paths have no explicit cross-request reconciliation TTL or bounded provider wait. React cache deduplicates within rendering, not across visits.

Fix direction: first time these spans on representative non-production billing cohorts. Classified test workspaces bypass Stripe reconciliation at manager-stripe-subscription-sync.ts:151–157, so seeded test profiles alone cannot measure provider latency. Use sandbox-provider fixtures or instrumented mocks that exercise the real reconciliation path, alongside production read-only server telemetry. Make ordinary navigation read a safely maintained entitlement snapshot, with provider reconciliation in the existing webhook/background path or a bounded freshness policy. Preserve immediate expiry/revocation rules and server write/quota checks. Do not simply cache personalized HTML publicly or skip entitlement validation. These calls are proven to be layout-critical; their actual share of production response time is unmeasured.

3. Production portal warming downloads unrelated panels

src/components/portal/portal-sidebar.tsx:305–308 starts src/lib/portal-panel-prefetch.ts:23–65, which warms ten panels without a portal-role argument. Resident/vendor sessions can warm manager finances, documents and inbox modules. Imports are launched without awaiting prior completion. portal-nav-prefetch.ts:2–8 enables this in production only. Sidebar links additionally prefetch routes, and public-home-prefetch.tsx:10–14 requests the marketing homepage immediately and again at idle.

Fix direction: warm only relevant routes by role and intent after the active page is ready; limit concurrency and respect slow connections/data-saver. Remove unrelated homepage warming from portal startup. Validate with a production-mode build because development omits this behavior. Dynamic import initiation is proven; exact bytes and CPU contribution require a waterfall.

4. Cache bypasses and refresh triggers add client data work

Browser TTL and in-flight coalescing already exist. Properties use a 15-second guard (demo-property-pipeline.ts:499–529); charges use the shared coalescer (household-charges.ts:500–518). However, global AccountLinksSync and dashboard onboarding both force portfolio refresh (account-links-sync.tsx:46–71, pro-dashboard.tsx:658–674). Dashboard initialization launches nine syncs (pro-dashboard.tsx:767–776). Forced calls during an in-flight request intentionally queue a follow-up (coalesced-refresh.ts:84–111).

Resident dashboard initializes application sync twice (resident-dashboard.tsx:557,629). Its tour fetch depends on tick (:540–551); unrelated charge, lease, service and inbox events bump that tick (:564–573), triggering more tour requests without a tour-specific TTL/in-flight guard.

Fix direction: use shared cached refresh on read-only mounts; preserve forced refresh after actual writes. Give tours a scoped coalesced refresher and relevant invalidation triggers. Gate background warming on active-page readiness. Verify request counts, workspace/viewer isolation, empty/error states and post-write freshness.

5. Resident access resolution contains serial database reads

src/app/resident/layout.tsx:45–68 waits for authorization, navigation, effective session, manager entitlement, residency access, preferences and workspace classification. resident-portal-access.ts:250–358 then conditionally chains applications, signed lease, attested tenancy, tours, draft lease and pipeline reads; a fetched profile at :343 is discarded at :353. Request-scoped caching already exists at :229.

Fix direction: remove verified unused reads and parallelize independent work after authorization. Preserve residency-stage routing and scope. Benchmark signed, pre-application and lease-first residents separately.

6. Global client bundle includes substantial optional functionality

src/app/layout.tsx:4,90 mounts GeneralAssistant globally; its static imports include composer and Markdown rendering. Portal layouts also import assistant surfaces. A fresh desktop browser visit to live sign-in fetched numerous Next scripts, including a roughly 332 KB transferred chunk with a 975 KB decoded body. Inspection of that downloaded asset found PDFDocument and pdf-lib symbols, despite no PDF interaction. Its precise source import chain is not established, so do not attribute it to the assistant without bundle analysis.

Fix direction: use bundle analysis to identify the PDF dependency importer, defer optional document tooling until needed, and keep a lightweight assistant trigger while loading chat UI on open. Verify that native bridges, Markdown and attachment behavior still work.

What the cache evidence says

A read-only fresh desktop live sign-in visit recorded about 206 ms TTFB and 640 ms FCP; a subsequent browser-cache-enabled visit recorded 29 ms TTFB and 324 ms FCP with 28 Next script resource entries and zero network transfer for those scripts. These are local desktop spot checks, not production user percentiles or proof of native performance.

Live sign-in HTML returned Cache-Control: private, no-cache, no-store and x-vercel-cache: MISS. A static JS asset returned public,max-age=31536000,immutable and x-vercel-cache: HIT. Root metadata reads request headers (src/app/layout.tsx:61–63), making broad public-page static caching worth examining separately. Personalized portal responses must remain private. The evidence does not show a broken static CDN cache.

Implementation order and acceptance criteria

  1. Correct production analytics attribution and add sanitized navigation/data-ready timings, server span timing and a native-runtime dimension. Reuse web-vitals rather than introducing duplicate metric capture. Strip bearer queries/path tokens; never collect emails, phones, secrets or raw sensitive URLs. Keep localhost excluded in every baseline query.
  2. Fix passive native sign-in gating and its ignored attempt limit. Signed-out native form must appear without an intentional eight-second wait; active OAuth success/failure/recovery still routes correctly. Compare like-for-like native cohorts after deployment.
  3. Reduce redundant refresh and unrelated prefetch work. Assert request counts behaviorally; preserve scope, error handling and post-write freshness. Measure first visible data and first useful interaction.
  4. Move billing reconciliation off the ordinary render path only after entitlement safety review. Measure before/after server spans for Stripe, Apple, free, waived and co-manager accounts.
  5. Optimize bundle and resident waterfalls using recorded evidence. Targets: p75 LCP below 2.5 seconds, p75 INP below 200 ms, and clear data-ready improvement. These are targets, not achieved results.

Risk-based validation: focused behavioral auth/polling, cache concurrency and tour-invalidation tests; entitlement boundary and expiry integration checks; pinned Node 22; one owner for broader lint/typecheck/build. Seeded dev/test portal QA, production-mode slow-network checks, native auth exercise and staging QA before any release. No no-mistakes pipeline. No production changes or release were requested.
