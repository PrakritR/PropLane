Leave the seven applied migrations and their canonical resolver/importer function definitions unchanged. Historical code explains possibilities, not this event's true owner

At historical commit d6e25e3fe on September 2, src/app/api/twilio/inbound/route.ts claimed a receipt under the owner of the texted work number, without the current workspace-owner collapse. The leasing handler then selected a landlord independently. Its resolvePropertyByLabelHint searched scoped managers first but could fall through to the public listing catalog even for a scoped work number; landlordId preferred the hinted property's manager. It persisted inbound logs, created leasing sessions and sent the reply under that selected landlord. Therefore an A-receipt/B-log/session/outbox pattern is consistent with historical cross-catalog routing as well as other ownership history. It is not evidence by itself of a co-manager grant.

The prepared-reply and outbox-attachment RPCs pin session/outbox references onto the claimed receipt while the worker owns its lease, which strengthens the relationship between these artifacts. They do not prove the original inbound body, identify a missing receiving-line epoch, or repair a historical authorization defect. If the release owner wants to pursue a canonical routing proof later, it must also check the exact reply dedupe key, receipt/outbox linkage, outbox recipient and submitted sender against the original wire and all available epoch evidence. Even a successful check does not create the missing line record.

Why the archival path is safe and narrower

The existing manager reader authorizes the retained inbound row using its stored owner B and Communication scope. Preserving that same retained record under B is not a claim that B owned A's work number. No source owner changes, no grant is added, and no message is copied to A. Conversely, calling the row a canonical receipt-derived original under B would make exactly that unsupported claim. The representation must keep this distinction in machine-readable provenance and in its inability to send or merge with resolved identities.

No human ownership decision is required to preserve the existing stored record under its existing access boundary. A human decision or stronger independent evidence would be required to move it to A, call B the canonical transport owner, grant another viewer access, restore a missing production transcript, or make it sendable. None is proposed.

Concrete additive implementation

  1. Keep the canonical resolver and live adapter strict. Do not change resolve_sms_completed_receipt_original to accept this owner disagreement, and do not let resolveInboundOriginal, receipt replay or queued live events consume an archival result as normal success. A receipt source-intent with missing canonical authority remains an explicit repair failure. A separate historical reconciliation result must never authorize provider/model work. Existing migration-7 importer and function-definition postflight checks stay valid and untouched; the new operation gets its own exact definition/ACL postflight.
  2. Resolve by a retained row, not by a phone or session. Add a dedicated service-only resolve_sms_retained_historical_source(source_table,source_id) read-only helper and import_sms_retained_historical_source(source_table,source_id) write RPC accepting only allowlisted retained source tables and exact row UUIDs. Names are proposed, but these must be distinct from the applied canonical resolver/importer. Both share the same source classification. The write RPC independently rereads/revalidates the helper evidence under its lock; it never accepts a caller-supplied event payload. It rereads the row and re-derives the owner; caller-supplied owner/role/body/time are not authority. Eligibility is the reviewed historical inventory, completed receipt with cleared payload, exact SID binding, owner mismatch, no prospect ingress, no proven receiving epoch, valid retained body/wire/role, normalized sender key agreeing with the receipt, and no conflicting duplicate source. For the initial supported case, require the already-observed direct receipt session/outbox linkage to the same retained owner B (leasing_sms session and delivered manager_conversation/prospect outbox), without promoting that relationship to a grant or line proof. The exact manager mirror must agree in role/user as well as owner/body/wire before accounting it. Do not catch every log_conflict or arbitrary RPC failure and convert it to archival success. Pending/new messages, malformed envelopes, changed bytes, unreadable queries and unrelated conflicts still fail.
  3. Bound the first run. Record an explicit historical inventory cutoff and source fingerprint for the supported structural case, with the exact observed row privately reviewed. Do not embed a global permission for future owner conflicts. The structural code can be reusable for historical retained sources, but a new class of discrepancy cannot enter through a generic catch/fallback. Recompute the source proof inside the import transaction.
  4. Use source-owned, isolated identity. Preserve B, the exact inbound-log body/from/to, stored role, source UUID and created_at at PostgreSQL precision. The receipt's differing first_received_at is evidence metadata, not this archival display timestamp. Use identity_kind=unresolved with a stable key such as unresolved:inbound_sms_log:<row-uuid>, no inferred user identity, a collision-checked synthetic line scoped to the retained source, and historical=true, sendDisabled=true, archiveReason=receipt_owner_conflict. Keep provider SID as evidence/deduplication identity, not as proof of an active line. Do not mint a line record.
  5. Preserve scope without identity aliases. Do not add a phone/user/legacy-key alias that can merge this singleton into a resolved conversation or make a selected-line send possible. Record any original legacy conversation key solely as source provenance. If original house/archive metadata must be consulted to preserve existing access or archival state, use an explicit read-only source-scope field with the existing conversationVisible policy, not an alias for identity resolution. Test B's owner view, A's denied view, co-manager house grants and active workspace narrowing. Do not broaden access or silently move an archived original into Active. If no source-scope preservation is necessary for this row, keep the owner-only default-workspace behavior and document that verified fact.
  6. Retain deletion and collision fences. The dedicated write RPC is one transaction: derive the source owner, acquire the existing owner advisory lock before any source/projection row lock, reread and lock the primary and mirror source rows and receipt evidence, revalidate the complete fingerprint, then check exact source and provider-SID tombstones before the provider-SID lock and existing projections. Use the existing same-owner provider-lock key so ordinary projection/deletion and archive insertion serialize; explicitly refuse any observed cross-owner canonical collision rather than treating it as a mirror. Do not claim a global cross-owner lock unless every relevant writer actually participates. An identical archival record is idempotent. A canonical/provider turn or another owner/source with incompatible evidence is a visible integrity conflict; do not overwrite, re-home or silently prefer it. Use a distinct retained:inbound_sms_log namespace plus row UUID as the primary source identity, with provider_sid populated. Do not use historical:*: the existing projector automatically promotes unresolved historical provider turns when later live evidence matches. The distinct namespace keeps that promotion branch inapplicable, while the existing unique owner/provider-SID index causes a later incompatible canonical insertion to fail atomically instead of creating a duplicate or enriching the archive. This must be proved in a real SQL test, including rollback of any conversation insert preceding the unique conflict. Do not automatically enrich or promote this archival singleton later merely because a directory phone/user match appears.
  7. Handle the manager mirror explicitly. The matching manager-log timestamp is different from both the inbound log and receipt. Keep inbound-log precedence and its exact source timestamp; do not use a one-second tolerance or rewrite either row. Whether the caller requests the inbound row or its manager mirror, the dedicated resolver selects the same exact inbound row as primary. It may classify the manager row as an accounted mirror only after exact provider SID, same stored owner, inbound direction, body, from/to and role/user agreement, plus the primary source relation, are proven. Preserve the manager row UUID and its own timestamp/hash in archival provenance. The new import RPC and JavaScript backfill must consume the same classification so the later manager feed neither creates a second turn nor fails merely because its independent insert time differs. An altered body/wire/owner/role is still a blocker.
  8. Use explicit accounting. Backfill represents this as a successfully preserved historical source plus its proven mirror, not skipped corruption, a fabricated receipt, an ignored owner conflict or a canonical original. Counts such as historicalSourcePreserved and historicalSourceMirrorAccounted are separate from projectedCanonical. Dry run must report the same proposed classification; both complete inventory passes must revalidate all retained-source evidence, confirm the same one turn and mirror mapping, and retain zero unexplained mismatches/errors. Cutover cannot be forced from a null candidate or a silent continue.
  9. Apply additively. Create an eighth chronological migration containing the dedicated historical resolver/import RPCs and retain all seven applied file hashes and function definitions. Prefer no replacement of the existing importer: JavaScript routes an explicitly proven archival candidate to the dedicated RPC; normal candidates keep the existing importer. The archive write RPC can reuse well-scoped read helpers but must retain its own isolated identity and no-alias insertion contract. Modify the backfill classifier and exact reviewed wrapper hash/prerequisites; isolate code changes to historical ingestion and any strictly necessary source-scope rendering. Add explicit read-only helper result types so only an eligible retained-source result selects this path; an exception, null result or unrelated canonical error cannot select it. Do not edit source rows, receipt owner, logs, sessions, outbox or grants. Follow existing exact-target backup/apply/postflight and staging QA gates. A changed backfill hash requires correctly bound fresh/restarted inventory state, not hand-edited clean-pass counters. The eight-migration postflight must explicitly preserve and recheck the first seven definitions/hashes while checking the dedicated new functions separately.
