Corrected behavior

  • The singleton Supabase auth client now has a component-owned onAuthStateChange subscription. Its synchronous callback invalidates coordinator work when the observed session changes. The session identity includes the refresh token, so a new login by the same user is a new generation.
  • Every observed A to B to A transition advances the generation, even if A returns with the same token. A stale completion must match both its original generation and session identity before application cleanup is allowed.
  • Keepalive reads use a non-destructive auth.getSession() adapter. Returned and thrown permanent errors from the first or second read pass through the coordinator's generation guard before clearStaleBrowserAuth runs.
  • Returned or thrown 429 and network read failures remain transient at the application layer. The implementation does not restore tokens, weaken portal guards, disable SDK auto-refresh, or change the shared recovery helper.
  • Unmount synchronously invalidates pending coordinator work before the auth subscription is removed. Native resume registration tracks disposal; a handle that resolves after unmount is removed immediately, and a disposed callback cannot run keepalive.
  • Concurrent reads can share the current session only when the exact process-local session identity matches. Near-expiry refresh work remains coalesced across mount, visibility, and native resume signals.

SDK 429 limitation

The installed @supabase/auth-js implementation treats ordinary JSON 429 responses as non-retryable auth errors and may remove its stored session before returning to this coordinator. These tests can establish only that PropLane does not invoke its additional cleanup dependency for a 429. They cannot guarantee SDK session retention. This correction deliberately leaves that SDK security behavior unchanged and never restores a revoked token.
