Findings

P1 - Checkout proof did not authorize ownership of the matched application. Corrected during review.

The initial implementation issued a handoff nonce to any caller who started checkout with an email and public listing identifiers. A caller could pay a new session using another applicant's email, reach the existing application's already_submitted branch, and receive that application's newly rotated account-claim token because their own checkout cookie matched. A checkout proves payment initiation, not ownership of the application selected by email/property.

References: src/app/api/stripe/application-fee-checkout/route.ts, src/app/api/stripe/application-fee-verify/route.ts, and src/lib/promote-incomplete-application-after-fee.server.ts. Root removed the token from every verification response and removed the nonce mechanism. The checkout route and checkout helper have no diff against HEAD, and the nonce helper file is absent. Re-read verification lines 158-176: the response now contains payment/application status and email-delivery status, with no claim token. The link is sent to the saved application's email. Verify this for both new promotion and already-submitted paths, including callers with matching cookies.

P1 - HTTP failure recovery could overwrite saved answers with identity-only state. Corrected.

src/components/marketing/rental-application-wizard.tsx:2183 and the other new recovery branches clear submitInitiatedAxisIds and remove checkout return parameters. The same flow explicitly restores only email/property/name at lines 2094-2125. When a transient verification error leaves the server row incomplete, the next form or step change permits the autosave at lines 956-979 to replace its full saved answers with that incomplete form. The public resume path also skips a full reload when a local axis ID is already present.

Correction verified: the fee-return URL immediately suppresses both local and server autosave before effects can rehydrate identity. Failures retain the return parameters and show a recovery-only panel with Retry verification. Only server-confirmed promotion reaches the finish panel. Paid-but-unpromoted and ACH-processing returns never finalize the partial client form. The new HTTP-failure/remount test asserts no application POST and no local draft write.

P2 - Network rejection left checkout recovery stuck. Corrected.

src/components/marketing/rental-application-wizard.tsx:2142 starts an async recovery operation without a catch/finally boundary. A rejected verification fetch leaves processedApplicationFeeSessions set and the newly added submit marker active. Subsequent effects skip verification, draft saves remain suppressed, and the user receives no recoverable error. Correction verified: a try/catch/finally boundary reports thrown failures and releases the processed-session marker on unsuccessful attempts. A per-attempt ref and retry counter prevent accidental repeated requests while allowing explicit retry and remount. Behavioral tests reject verification and preview requests, then successfully retry without application writes or duplicate submitted-email delivery.
