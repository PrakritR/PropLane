Import a manager's lease or rental application PDF

Managers can choose a PropLane form or import their own PDF. An imported document becomes a reviewable, editable draft. The original remains available for comparison. Only a manager-approved version becomes available to residents or applicants.

Repository: /Users/akhilvemuri/coding/AXIS-2 · Branch: agent/assistant-chrome-polish · Planning HEAD: f814a9e8a825132f4a62108c1bc771c8b8343ff1 · Plan only; no product code changed or tests run.

Recommended product decision

An imported, manager-approved converted lease is the version offered for new signatures. The unchanged original PDF stays private and visible beside it as source evidence. A separate “Use original PDF” path remains for managers who intentionally want to sign their exact upload, and existing signed or sent PDF leases keep their current behavior. This makes “edit the converted lease before using it” meaningful without changing historical agreements.

Manager experience

Lease

Choose PropLane or upload PDF→Read and convert→Compare and edit→Save reviewed version→Send for signature
  1. Offer “Use a PropLane lease” and “Import my lease” in the existing lease workspace. Import works for a reusable property template and a particular resident lease.
  2. Store the original PDF privately and show reading progress. A failed or partial read stays a draft with a page-specific issue list and a retry action. Never label it converted when content was missed.
  3. Open one compare workspace: original PDF on the left and the PropLane formatted, editable document on the right. On phones, use an Original / Converted switch that keeps the current page and section. Provide page references and a list of unresolved passages, tables, form fields, and images.
  4. Allow direct edits to the converted document before save. Preserve source text in original order on initial conversion. New words from the manager are identified as edits; the source is never silently rewritten. Saving remains a draft until explicit confirmation of the whole document.
  5. Show the exact final document before sending. Send and assistant tool paths read the same server-side gate. A converted lease sent for signature is immutable after either party signs; revisions require a new version and a new signing request.

Application

Choose PropLane or upload PDF→Extract questions→Edit draft→Preview full form→Publish
  1. Add PDF import to the existing application workspace. Let the manager choose the property and long-term, short-term, or co-signer form. Keep the original PDF in a private manager-owned store and offer Original / Form comparison during editing.
  2. Map each source question to a standard field when the meaning is clear; retain its original wording as the visible label. Put unmatched questions into custom fields in source order. Preserve choice options and identify uncertain field type, grouping, or required status for the manager to resolve.
  3. Always include full legal name, phone, and email once. Treat these as required identity fields in the editor and in server validation. Avoid duplicate imported copies when the PDF asks for them under different labels.
  4. Let the manager add, remove, edit, move, and set required status for other questions, including imported questions mapped onto built-in fields. Use one saved display order across built-in and custom questions. Save as a draft. Show the whole applicant wizard, including branching and validation, in a write-disabled preview using the unpublished draft.
  5. Publish only after import issues and required-field validation pass. The public applicant flow reads the published version; a manager edit creates a new draft version and never changes a form already in progress.
  6. For signed-in applicants, fill missing identity values from the authenticated account and reusable prior answers. Let the applicant verify and edit the values. Do not copy answers between accounts or overwrite answers the applicant already typed.

Implementation decisions

1. One source-preserving import core

Use server-side, bounded PDF processing for both document types: page text, AcroForm fields and options, annotations, tables where detectable, and OCR for scanned pages. Record source page and span for every imported block. Conversion may use a classifier for structure, but the final draft is assembled from source spans, never from generated paraphrases. A coverage check accounts for all extracted text; non-text content must be represented in the converted draft or explicitly marked unresolved. Limit file size, pages, OCR time, and output size. Retry from the stored source, not a browser-held data URL.

Run this as an asynchronous, resumable import job if OCR exceeds the route's bounded execution time. Keep the source and result private, scoped to the authenticated manager and property. Reject disguised PDFs and executable content. Do not send document text to an external model as an implicit side effect of upload. If a later model-assisted classifier is selected, make data handling an explicit product and security decision first.

2. Explicit lease artifact and version

Add an explicit document mode for PropLane generated, imported converted, and original PDF. Store the immutable source PDF separately from the editable converted HTML and its review record, with source hash, converted version, reviewer, and time. Route preview, export, send, hash, certificate, and resident rendering through one “effective signable document” resolver. Preserve legacy rows as original-PDF mode. The converted HTML must use the existing sanitizer and signed-document immutability rules.

3. Per-template application configuration

Give each named application template its own draft and published question configuration, explicit question order, version, and import provenance. Keep existing listing variant configuration as the fallback for legacy templates. The applicant route resolves one published template for the listing and stay type, and pins its version to each in-progress application. Publish makes one immutable snapshot active; changes to a draft do not leak through the public listing projection. Store the source PDF reference in manager-only metadata, not the public listing payload. Make the applicant renderer and validator read the same enabled, required, type, and order settings.

4. Required fields and autofill

Make identity requirements part of one shared field policy used by the builder, normalization, preview, and server-side submission validation. Match imported identity prompts into those fields while retaining source wording. Extend current account autofill to include authenticated name and phone when present; email comes from the authenticated identity. Merge only into blank answers and keep prior-application reuse account-scoped.

Key limitation to resolve during implementation

PDF extraction cannot prove that handwriting, a poor scan, or a flattened graphic was transcribed correctly. The product must show those pages in the comparison, mark uncertain content, and block the converted version from publication or signing until a manager resolves it. The original remains available throughout. This is the practical meaning of “preserve all content” without making a false completeness claim.
