Auth findings and bounded correction plan

P2 - Account changes are observed only during keepalive reads

src/lib/supabase/portal-session-refresh.ts:47-76, 103-108 advances its owner generation only when another invocation resolves getSession. The component has no auth-state subscription. Start a near-expiry refresh for A, change the singleton client's session to B without another visibility/mount/resume call, then complete A's refresh with a recognized permanent error: the current-owner check still considers A current and calls unscoped clearStaleAuth against B. An A to B to A transition is likewise invisible unless keepalive observes B. The existing account-change test manually calls run for B, so it excludes the missing integration.

Correction: expose a synchronous auth-state/session-lifecycle observation or invalidation entry point and wire it to the singleton client's auth changes with safe subscription ownership. Invalidate stale work across sign-out/sign-in transitions, including the same user signing in again; do not equate user id alone with session continuity. Do not await auth calls inside the Supabase auth callback. Before app-triggered destructive cleanup, require the still-current session generation. Add deterministic tests for A to B without another run, A to B to A, sign-out/new sign-in as A, and late completions.

P2 - Session reads bypass the new cleanup guard

src/components/portal/portal-session-keepalive.tsx:15-20 supplies safeBrowserGetSession to both coordinator reads. That helper calls clearStaleBrowserAuth internally on permanent read errors (src/lib/supabase/safe-browser-session.ts:36-46), before the coordinator can reject a stale owner/generation. The second getSession read can therefore clear auth even when the later check at coordinator line 96 rejects its result. Current helper tests mock a side-effect-free session read and cannot establish the actual integration's cleanup safety.

Correction: use a non-destructive read/error adapter for this keepalive path and route its recognized permanent errors through the same scoped cleanup decision as explicit refresh failures. Keep other callers' shared recovery behavior unchanged unless independently justified. Add component/adapter tests covering returned and thrown permanent errors during first and second reads, account changes while reads are pending, and 429/network read errors. Separate application-triggered cleanup guarantees from SDK-internal behavior.

P2 - Late native listener registration survives unmount

src/components/portal/portal-session-keepalive.tsx:43-55 sets removeResume after asynchronous import/addListener completion. If the effect unmounts before completion, cleanup runs while removeResume is undefined; the later handle is never removed. A stale native resume callback remains attached and repeated mounts can accumulate callbacks. This is pre-existing code retained in the touched component, not introduced by the new coordinator, but it violates the native lifecycle edge under review.

Correction: track effect disposal and immediately remove a handle received after disposal; remove normally if registration finishes first. A callback from a disposed effect must not initiate keepalive. Add component tests that defer import/listener resolution until after unmount, verify exactly one handle removal, and verify active visibility/native callbacks coalesce while disposed callbacks do no work.
