P1 - Replay-safe control failures are permanently frozen after acknowledgement

Primary location: src/lib/sms/inbound-envelope.server.ts:49-51. Related: src/lib/sms/process-accepted-inbound.server.ts:35-39,96-110; recovery selection at inbound-envelope.server.ts:65.

A valid STOP is durably accepted and the webhook returns 200. If the subsequent provider timestamp lookup fails once, processing returns 503, the wrapper throws, and the envelope becomes needs_review. The recovery cron selects only accepted/prepared envelopes. A duplicate webhook also cannot claim this envelope again. The application's suppression event is never applied automatically even after the provider recovers. A failed or response-lost apply_sms_control_keyword call has the same result despite that RPC being atomic and keyed by MessageSid. The old comment that 503 asks Twilio to retry no longer describes the asynchronous path.

The same blanket handling freezes known pre-effect failures such as an unavailable rate-limit read. Conversely, an existing downstream owner receipt may recover successfully through its established sweeper while its enclosing envelope remains permanently in review, producing a continuing unhealthy cron response.

Correction

Introduce explicit durable processing outcomes/checkpoints that distinguish proven safe-to-retry work, responsibility transferred to an existing owner receipt, completed work, and uncertain effects. Retry only known safe stages with bounded attempts, backoff, expiry, and lease CAS. Keep unknown side effects frozen. Control processing should have a durable branch/keyword decision and replay its MessageSid-idempotent RPC, so a START/YES retry after suppression changes cannot fall into agent confirmation. Do not solve this by rerunning every exception. Persist a non-PII reason/stage for review outcomes.

Acceptance tests

  • Full fast-ACK-to-worker-to-cron path: STOP timestamp lookup fails once, then succeeds; suppression applies once, no model/tool runs, envelope completes.
  • STOP/START control RPC commits but its response is lost; retry is idempotent. A suppressed YES remains a control on retry and never confirms an action.
  • A proven pre-effect dependency failure recovers; an injected crash after an unknown effect remains frozen and does not rerun the effect.
  • A delegated owner receipt fails then recovers through the existing receipt sweeper; envelope state/health eventually reflects that durable outcome without re-entering the shared seam.

P1 - A valid late acceptance callback cannot resume untouched reply bubbles

Primary location: supabase/migrations/20261104120000_sms_durable_ingress.sql:58-59. Related: src/lib/sms/platform-reply-dispatch.server.ts:26,37,63; inbound-envelope.server.ts:65.

Prepare bubbles A and B. Twilio accepts A, but the submission response is lost. The dispatcher marks A delivery_unknown and the envelope needs_review. A subsequent correctly signed, token/account/wire/SID-bound callback proves A was accepted and changes its reply row to accepted. It never changes or reconciles the envelope. Cron skips the envelope forever, and even an explicit dispatcher call returns at line 26. B is never submitted. With one bubble, the resolved envelope still stays in review indefinitely. This is a functional gap in the intended provider reconciliation, not a reason to resend A.

Correction

Record why an envelope is suspended and atomically reconcile only delivery-uncertainty suspensions after authoritative callback evidence. Reopen an unexpired envelope only when the blocking submission has been resolved, prior bubbles have safe terminal submission states, and there is no independent blocked/uncertain execution reason. Resume exact persisted remaining bubbles through the existing per-bubble claim. A callback must never rerun the processor, overwrite a conflicting SID, resurrect expired work, or clear an unrelated refusal. Cron-based reconciliation is acceptable and avoids doing sends inside the callback request.

Acceptance tests

  • Two bubbles: first request accepted but response lost; signed callback arrives after needs_review; cron sends only B once, in order, using the original bytes, then completes.
  • One bubble: same failure/callback sequence reaches completed with no additional provider call.
  • Callback races the unknown-state transition and multiple cron workers; at most one submission per bubble. Conflicting SID, wrong token/runtime/wire/account, expired envelope and independently blocked later bubble cannot be reopened.

P1 - Transient shared-configuration reads terminally block prepared replies

Primary location: src/lib/one-number/lead-send.server.ts:25-27. Related: src/lib/sms/platform-reply-dispatch.server.ts:51-63; fallback semantics in src/lib/one-number/config.server.ts:32,66,82.

The durable dispatcher has the exact reply stored and has made no provider request. If the shared configuration, number table, or one owner's entitlement read temporarily fails, loadSharedLineConfig folds that failure to per_workspace. The sender returns not_shared_mode, which the new dispatcher treats as a terminal blocked reply and needs_review envelope. Restoring the database does not recover the reply. This is distinguishable from a proven mode or sender change and therefore should not require manual reconciliation.

Correction

Use the strict configuration result for durable platform replies. An unreadable configuration is a definite pre-provider retryable outcome; a successfully read changed mode or pinned sender remains refused. Preserve exact prepared body, media, order, and sender. Also use a strict/retryable configuration boundary before the asynchronous processor enters shared routing, so unreadability cannot silently select physical-owner/per-workspace handling. Do not reinterpret a configuration outage as permission to use a different line.

Acceptance tests

  • Prepared reply encounters transient config and dedicated-entitlement read failures: zero provider calls while unavailable; later recovery sends original bytes once without rerunning routing/model work.
  • A successfully read changed shared number/mode remains blocked, and suppression read errors continue to prevent sending until a safe retry.
  • Before routing, unreadable shared configuration cannot route a Seattle shared text as the physical platform number owner or complete it as an unrelated no-owner message.
