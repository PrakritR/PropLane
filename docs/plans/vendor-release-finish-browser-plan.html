1. Admin recipient loading and authorize-before-append

Confirmed in source: AdminCommunication sets recipientsLoaded=true before awaiting its fetch. Because that value is an effect dependency, the next render runs cleanup and marks the response cancelled. A successful 99-manager/71-resident response therefore never reaches the picker. Separately, submitSendNow appends Sent before launching a fire-and-forget POST. An empty broadcast also gets a false Sent row and success toast.

  1. Keep request-in-progress separate from successfully loaded. Set loaded only after a successful, structurally valid response has populated both arrays. Closing/unmounting invalidates the outstanding response; reopening after failure starts one fresh request. Do not create an automatic failure/refetch loop or reset typed subject/body/audience when recipients arrive.
  2. Expose loading/failed/ready to compose so Send/Schedule cannot submit while recipient identity is unresolved. A concise status/control is sufficient; no explanatory subtext. Provide an explicit retry or reopen path on failure. Empty ready arrays remain valid loaded state but cannot send.
  3. Resolve every audience through one nonempty recipient set. Deduplicate by user id, and validate selected ids against the current fetched pool. Reject empty broadcasts, stale selections and malformed recipients before local writes or fetch.
  4. Build the prospective local message in memory. Await adminOversightUrl('/api/portal/send-inbox-message') with the existing oversight query, cookie credentials, deliverViaEmail:false and current payload. Require HTTP success and parsed ok:true. Only then call appendInboxMessage, success toast, onSent and onClose. Network errors, non-2xx, invalid JSON and ok:false preserve draft and produce no local Sent row. Prevent duplicate submits while pending. Keep scheduling's existing separate request path and failure behavior.
  5. Fix the E2E safety interceptor before exercising Send: match new URL(url).pathname === '/api/portal/send-inbox-message', which includes oversight requests. Assert exactly one intercepted POST, nonempty recipient ids, unchanged draft through delayed recipient response, no real provider request, then the existing archive flow.

Acceptance: delayed success populates without discarding edits; close-before-response/reopen works; response failure/retry works; empty All managers cannot send; explicit picked recipients work; duplicate ids deduplicate; pending double-click sends once; 403/500/network/invalid JSON/ok:false cause no append/toast/close; accepted send appends exactly once after response. Add schedule regression with loading and empty pool. Existing admin shared-inbox/workspace unit suites remain meaningful regressions.

Bulk-delete safety: this spec currently clicks Delete all archived on a shared admin mailbox. Use an exclusively task-owned admin fixture mailbox or a scoped UI-only mailbox adapter for the destructive chrome proof, with actual backend authorization covered separately. Never delete other archived records merely to make the count zero. If retaining a real mailbox, preflight and recheck that the complete archived inventory contains only this test's owned row before the bulk action.
