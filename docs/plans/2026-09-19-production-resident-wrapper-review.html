This source-only review does not approve application code, a production database mutation, or shipping. It did not execute Node, tests, CLI, network, database operations or Git commands. Safety findings

  • The production apply wrapper explicitly requires target production and project qahnczmilgptcedaqype. It calls only the resident-read runner, followed by a production read-only capture and verification. It does not call the obsolete six-step reconciliation workflow. Its additional label check rejects path separators and malformed labels.
  • The resource gate matches staging except for its sole allowed wrapper filename. It requires normal pressure and at least 35 percent available memory, selects Node 22.23.0 and bounds the Node heap to 64 MiB. This is a start-time check, not a guarantee that memory remains available throughout execution.
  • The manifest binds the fixed resident migration identity, source digest, runner and helper bytes, complete generated inventory, target, capture and matching backup. Private artifacts require restrictive modes and reject symlinks. Exact dry run is followed by a process-local, one-use token with a 60-second lifetime; approval and capture freshness are rechecked immediately before apply. Evidence older than ten minutes is rejected.
  • The migration changes only the allowed manager/resident scopes of the exact prior function. Its independent scope = p_scope predicate remains in the pinned source. Function guards preserve owner, invoker security, language, volatility, empty search path and restricted EXECUTE ACL. The generated SQL guards every prior ledger row, ordered statement bytes and SQL array dimensions under a ledger lock.
  • Authored outer BEGIN/COMMIT are removed. Nested DO transaction settings and locks remain through the CLI's automatic history insertion. Existing reports provide PostgreSQL 16/17 direct-connection transaction rehearsal and actual staging linked-transport post-state evidence. Those reports do not constitute a new production execution.

Precise remaining requirements

  1. Fresh concrete artifacts: after application work stabilizes and resources permit, take a new production capture and matching backup, generate a new resident-only workspace, independently review its manifest and SQL, and issue a new expiring receipt. The reported resumed capture has 261 rows, the old manager-only function and no resident feature migration; this reviewer did not independently compare that private capture. It must not be treated as fresh enough for a future apply. Preserve the already-applied prerequisites and test-workspace migrations. Never use the old six-step wrapper.
  2. Recovery is a template: residentRecoverySql deliberately emits no full post-apply ledger guard and no new migration identity. It must never be executed directly. If recovery becomes necessary, capture the actual complete post-state, add its full ledger guard after the transaction guard and before any DDL, use a NEW reviewed migration identity, restore the exact backed-up function with pre/postconditions, and preserve successful history. The approval field recoveryRehearsalPassed is an attestation, not an automatic rehearsal. Its supporting evidence and template must be reviewed for the concrete manifest.
  3. Independent post-state inspection: automated verification proves old ledger preservation, target/function equality and exactly one correctly named new row, but only requires that row's statements to be nonempty strings. It does not compare their complete payload to the sealed migration. Independent review must account for every actual CLI-recorded statement against the reviewed generated SQL, as the staging runtime review did, and verify full prior-ledger equality plus exact function metadata. A verified: true receipt still explicitly requires independent review.
  4. Ambiguous completion: apply can commit before post-capture, verification or receipt writing fails. Do not rerun apply or assume rollback from a wrapper error. Perform a fresh read-only target inspection first. A present feature row or changed function invalidates the pre-apply workspace; inspect and independently verify the committed state or prepare the new guarded recovery path. Use a unique post-capture label to avoid an exclusive-create collision after application.

No blocking defect was found in the mechanical production-wrapper adaptation. These boundaries remain required parts of the release procedure, and this document cannot substitute for the forthcoming concrete manifest or independent post-apply review.
