Build the grant and projected conversation

  1. Create one accepted account_link_invites manager row for the exact owner, co-manager, and workspace, with house_scope: "selected", assigned_property_ids: [fixturePropertyId], and property_co_manager_permissions: { [fixturePropertyId]: { inbox: { read: true, edit: true } } }. Set its required inviter/invitee axis IDs from the existing profiles. Use a unique row ID and leave delete absent. The visibility resolver reads this accepted row and its per-house permission map; a team role or workspace membership alone is not the grant.
  2. Use the existing owner work line and project_sms_conversation_event RPC to create one clearly labeled, run-unique inbound test event with a generated source event ID, test-only namespace, non-routable test phone, and a unique legacy conversation key. Do not call Twilio or create an outbox row. This RPC establishes the real projection conversation, turn, and alias under the validated owner line.
  3. Tag that exact legacy key in manager_sms_conversation_houses with the fixture property ID, source: "manual", and the owner as tagged_by_user_id. The reader resolves projection aliases to this house tag before applying the co-manager grant.

Browser checks

  1. Sign in as the co-manager using the known test login and select the same owner workspace. Confirm the fixture conversation appears in Communication and its detail loads. The read path is GET /api/manager/sms-conversations and GET /api/manager/sms-conversations/:id.
  2. Exercise the edit gate without sending: post the selected projection ID, its matching phone, and an empty message to POST /api/manager/sms-conversations. With the grant present, detail authorization succeeds and the send handler returns its expected 400 Enter a message. validation before any outbox or provider work.
  3. Revoke only the fixture house's inbox grant on that exact link row, retaining its workspace and house assignment. Confirm the list omits the conversation, detail returns 404, and the same empty-message POST returns 404 before the send handler. Then restore the exact saved grant and confirm the row returns.

Exact schema and cleanup boundary

Fixture rows: portal_workspaces is reused unchanged; one manager_property_records row uses id, manager_user_id, workspace_id, status, row_data, property_data; one account_link_invites row uses id, inviter_user_id, invitee_user_id, tab_kind, inviter_axis_id, invitee_axis_id, assigned_property_ids, status, workspace_id, house_scope, property_co_manager_permissions; the work line is read-only from manager_sms_numbers; the canonical event RPC creates sms_projection_conversations, sms_projection_turns, and sms_projection_aliases; one house tag uses manager_sms_conversation_houses(manager_user_id, conversation_key, property_id, source, tagged_by_user_id).

Before setup, record whether the invite row is newly created or pre-existing. Prefer a new exact pair/workspace row; if one already exists, do not overwrite its broader permission map. Record the full original grant before temporarily changing any pre-existing row, and restore it immediately after the check. Cleanup only rows created by this run: verify owner, workspace, generated property ID, and the fixture marker before deleting the property; delete the exact house tag and invite row by generated IDs; delete the projection conversation by its generated ID only after confirming its owner and fixture source event, allowing its turns, aliases, and view state to cascade.
