P2 - Reconcile changed projections beyond the first list page

src/components/portal/pro-unified-inbox.tsx:1065 refreshes only the head page after archive/restore; :1074 does the same after deletion. :517 retains every previously loaded row absent from that page unchanged. The bulk hook ignores the successful PATCH response version and does not update the parent row.

Reproduction: load a second SMS page; archive a conversation on that page that has no newer event. The PATCH succeeds, but its summary remains active with the previous stateVersion. A second archive attempt receives 409. Restore has the same failure in reverse. A successful delete can similarly leave an unselected old-page row visible. Polling the head again cannot repair any of these rows. The selected-row reauthorization at :1524 ignores successful response bodies, so it does not reconcile archive/version changes either.

Correction: propagate each successful projection mutation result back to the owning list, updating exactly that row's archive flag and returned version. Remove exactly successfully deleted IDs. For conflicts and read-state changes, fetch and merge authorized summaries for affected IDs, including older pages, rather than relying on head-page refresh. Keep failed rows present and preserve honest partial-failure counts. Retain existing viewer/workspace generation guards and do not erase unrelated loaded pages.

Required focused coverage: page-one plus page-two fixture; archive and restore a page-two row, verify membership/counts and next expected version; delete a page-two row and verify it disappears while its neighbor stays; mixed success/409 batch reconciles each affected ID; viewer/workspace switch during reconciliation cannot publish old results.

P2 - Notice reopening can permanently disagree with legacy controls after a partial write

src/lib/sms-inbox-notice.server.ts:113 ignores the Supabase control-update error after the notice CAS at :89 already committed. The function returns success. On retry, the message-ID deduplication at :79 returns before any repair; even a different inbound message will see an already-active notice and skip the reopens branch. A transient database failure therefore leaves the notice active while the applicable legacy control remains archived. Projection summaries without explicit viewer state still read that control fallback.

Provenance: this behavior is unchanged from upstream 0ecb464b9; the merge correctly retained it. The review's concern is failure handling, not the intended inbound-only reopen policy.

Correction: make the successful notice CAS append/reopen and matching legacy-control update one atomic database operation, or use a durable, version-bound repair intent that can safely finish only that reopening. Preserve returned thread/message identifiers and original-event metadata. A transaction-backed helper should make control-update failure roll back the notice append so an ordinary retry remains valid. Merely throwing after the second write fails is insufficient because the first write already committed.

Do not blindly clear controls on duplicate delivery: a manager may archive after the original inbound message. Its duplicate must not undo that later decision. Keep duplicate delivery a no-op once the original atomic operation succeeded, and leave outbound appends archived.

Required focused coverage: inject control-write failure and verify no split committed state; retry succeeds exactly once; archive after successful delivery then replay the same message and verify both stores stay archived; concurrent appends retain all message IDs and metadata. No transport rewrite or confirmation flow is needed.
