Source cause and limits

src/components/portal/resident-inbox-panel.tsx:337-367 still owns an unscoped mount loader through the legacy array-only syncPersistedInboxFromServer. It blindly applies the returned array, sets persistReady, and flips a mutable persistence ref. Its passive effect then calls persistInbox(scope, local) whenever local or readiness changes. The parent renders this panel even while its own initial-readiness gate is pending.

src/lib/portal-inbox-storage.ts:613-617 discards the status returned by the real loader; stale or failed results can appear to this consumer as an empty array. Its array completion has no unmount, viewer epoch, or cache-identity protection. The independent parent hydration recovery now correctly obtains fresh rows, but does not control this child's stale state or passive writer.

persistInbox at lines 774-808 compares the panel snapshot against the current shared viewer cache. Missing ids become deleteInboxThreadIds; it updates the cache and emits its change event before the server mutation. An empty or obsolete local snapshot therefore clears newly loaded rows and deletes their database records. A passive effect can also see an older React-render snapshot while a ref was already re-enabled by an asynchronous completion. Merely ignoring stale=false results or adding another readiness boolean does not remove this class of destructive feedback.

The trace conclusively proves the unauthorized-by-user automatic deletion and source identifies the passive destructive writer. It does not record React state/ref scheduling, so the exact callback interleaving (stale array versus stale passive-render snapshot) is an inference, not measured instrumentation. Both must be removed as possible delete authority.

Bounded correction for the fresh implementation manager

  1. Remove passive full-snapshot persistence from ResidentInboxPanel. Reading a server response, handling a shared cache event, mounting, switching viewers, and resetting state must never call replace/delete or infer user deletions. Audit every setLocal call in this file. Existing explicit read/unread, trash/restore, delete and authorized-send paths already use write helpers; preserve those. If an intentional mutation truly relied on the generic effect, move only that mutation to an explicit authorized handler. Retain demo behavior using existing local-only helpers where required.
  2. Make panel hydration status-aware and viewer scoped. Use the status loader, with the existing initial-viewer observer and bounded stale retry only if recovery is needed. Capture component generation, intended viewer and cache identity; reject old completions after unmount, identity change or A-B-A. Failed/stale loads do not replace a usable local snapshot with []. A successful empty response may set local empty but must remain read-only. Never set the shared global viewer from the panel.
  3. Prevent late hydration from rolling back newer cache events. A completion should consume the current authorized cache after successful loading, or use an explicit revision/generation guard when applying its snapshot. Cache-change subscriptions need matching scope and current viewer ownership. Do not perform stale-viewer reset writes or queue a reset that can run after the next viewer has loaded. Clear local presentation synchronously through generation-bound state updates as needed, with no shared-store persistence.
  4. Keep parent source readiness intact. Resident/manager all-enabled-source gates, stale retry bound, fail-closed account changes and error Retry behavior remain. Do not suppress inbox rows, bypass read-source proofs, increase test timeouts, add force-fetch loops, or change identity folding.
  5. Audit assistant placeholder staging. ResidentCommunication currently schedules a whole captured local array through queueMicrotask. Ensure delayed placeholder work cannot overwrite current loaded rows or cross viewer generations. Prefer the existing pure pinned presentation helper if it supplies the needed placeholder; otherwise merge against current authorized cache at execution with generation guards. Avoid replacing the whole store using an earlier render snapshot.
