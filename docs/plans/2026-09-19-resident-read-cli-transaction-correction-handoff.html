Goal and evidence

The starting source audit is docs/plans/2026-09-19-resident-read-cli-transaction-source-audit.html. Supabase CLI 2.117.0 uses one extended-protocol batch for all migration statements and its parameterized history INSERT. That batch is atomic, but PostgreSQL does not treat it as an explicit transaction block. The observed dev failure was PostgreSQL 25P01 at the first top-level LOCK TABLE, before guarded DDL. Root separately confirmed that dev, staging and production all report PostgreSQL 17.6 (server_version_num=170006).

Implementation

  • scripts/release-conversation-schema-reconciliation.mjs exports cliTransactionGuardSql. It validates controlled timeout, relation and lock-mode inputs, then emits transaction-local settings and table locks inside a collision-safe DO body.
  • Conversation reconciliation, history-name recovery and function recovery use that guard. They retain headerless outer SQL, all existing ledger, catalog, function and invite guards, and no authored BEGIN/COMMIT.
  • scripts/release-resident-inbox-read.mjs uses the same guard for its apply and NEW-migration recovery SQL. Ledger and inbox-table locks therefore remain owned by the CLI batch through the automatic history INSERT.
  • Existing private CLI diagnostic capture and fail-closed runner behavior were preserved.

Exact disposable CLI proof

scripts/test-release-cli-transaction.mjs is a CI-only harness. It accepts only a loopback PostgreSQL admin URL, uses bounded subprocesses, creates disposable databases and invokes db push --db-url ... --skip-vault --include-all --yes. It imports the production cliTransactionGuardSql and ledgerGuardSql generators rather than copying their SQL.

The release-cli-transaction job in .github/workflows/test.yml runs a PostgreSQL 16.10 and 17.6 matrix. It downloads the official Supabase CLI 2.117.0 Linux amd64 release archive, verifies the official checksums.txt asset SHA-256 afcec54b3b19d8c73957cafb4956bb10cb7493207c29df60cdcd9afe6317cdb0, verifies the archive SHA-256 69c05f85b9e47ee706d30f1a6ca8a526b4e337bfd12c7ef1ef522d24e7280d24, and checks the extracted CLI reports exactly 2.117.0. It uses no Supabase project, API access or secrets.

The matrix must prove:

  • successful DDL and function replacement plus a nonempty automatic CLI history row whose statements contain the real DDL;
  • the exact ledger ExclusiveLock, payload ShareRowExclusiveLock, and transaction-local settings still exist inside the history INSERT trigger;
  • a forced error after DDL rolls back the table change, function replacement and history;
  • a forced automatic history-insertion error rolls back the table change and function replacement;
  • a second guarded recovery through the same CLI transport restores the function, records truthful recovery history and preserves the first automatic history row exactly.

The hermetic matrix job is included in the required check aggregator. Workflow contract tests pin the versions, official digests, command, lack of secrets and gate membership.
