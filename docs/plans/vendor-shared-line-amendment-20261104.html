Shared-line vendor quote consent

November 4, 2026. Bounded planning amendment for the isolated vendor release. Shared-line consent is required release scope. This document authorizes no production mutation. Root owns release sequencing; the implementation manager remains the sole heavy-validation owner.

Decision

Use the current TypeScript sender authority for shared, paid dedicated, linked and PropLane-managed workspaces. Keep atomic consent consumption in the existing SQL transaction. Bridge these authorities with a fail-closed revision handshake, not a second SQL implementation of personal-number entitlement. A proof that only says “TypeScript checked recently” is insufficient: the SQL transaction must reject a sender-policy change after that check.

The smallest safe bridge found is one service-only sender-authority revision row, transactional invalidation triggers on its actual source data, and a fresh, uncached resolver mode. This adds one bounded consistency mechanism, not a replacement number model. It deliberately trades occasional retriable refusals when unrelated sender policy changes for a complete fence. Do not silently omit shared consent or treat an unpaid active number row as a dedicated entitlement.

Verified integration seams

  • vendor-outreach-identity.server.ts currently requires a matching manager_sms_numbers row even after resolving the sending number. This excludes ordinary shared senders and managed senders whose PropLane line belongs to another owner.
  • evaluateWorkspaceSendReadiness already resolves managed-service overrides first, then shared/dedicated selection, provider identity, runtime and wallet gates. Its shared numberRow is explicitly a transport description, not an owned database row. Do not insert or represent it as ownership evidence.
  • loadSharedLineConfigStrict plus workspaceOnSharedLine use paid-plan, paid-number add-on, grandfathered-number and managed-workspace decisions. A config flag alone cannot reproduce this authority.
  • getEffectiveManagerSkuTier reads React-cached purchase facts; those include confirmed Auth email ownership. Promo policy has a separate 30-second TTL. An immediate second ordinary resolve can reuse stale facts.
  • vendor_quote_sender_is_current and consume_vendor_quote_sms_challenge each hardcode a dedicated row. Both must change together. The current newest-challenge lookup also fails when the same phone has multiple workspace challenges.
  • The inbound route handles compliance before shared routing, but shared routing can consume unknown senders. Proof classification belongs after compliance and before shared routing or old-number rewriting.

Implementation protocol

  1. Resolve the service's workspace from persisted ownership. Continue deriving service → property → workspace under the existing owner checks. Obtain an explicit transport identity from canonical sender selection: workspace, actual From, consent messaging-service SID, provider service SID, transport kind and any real selected line ID. Keep legal sender mode separate from transport kind: vendor outreach managed is not the same flag as workspace is_service. Preserve the assigned legal identity checks.
  2. Expose fresh policy reads without copying policy. Extract the existing purchase-loader implementation from its React cache wrapper and add an optional fresh/strict read context through the canonical resolver chain. Existing callers retain their current behavior. The quote proof path bypasses both React purchase caching and promo-policy TTL, and refuses unreadable authority inputs. Reuse the existing pure tier/waiver/number rules unchanged. Pass the same evaluation time through time-dependent helpers. A strict initial config read must not be followed by a non-strict failed fallback in readiness; pass the strict result through or use the same strict context inside readiness.
  3. Fence the read. Add a singleton vendor_quote_sender_authority_revision, service-role read only, no anon/authenticated grants. Mutation triggers increment it in the SAME transaction as changes to authority inputs. Read revision R and DB time, evaluate the fresh sender, then call the consuming RPC with R, the exact derived sender/key, and a short validity deadline. The consumer locks the revision row first and requires equality to R. It keeps that lock until consent commit. A policy mutation before the read is included; one during evaluation causes a mismatch; one after the lock waits until consent commit. Bounded retry starts a new fresh evaluation, never reuses the old proof.
  4. Cover actual dependency closure. Fence sender-selection writes to sms_runtime_config, manager_sms_numbers, workspace_work_numbers, portal_workspaces, platform_service_settings, manager_purchases, number_subscriptions, manager_promo_code_policies, and relevant auth.users confirmed-email identity changes. Include sender identity sources vendor_outreach_workspace_profiles, manager_assistant_emails, relevant profile-name changes and service/property workspace ownership, unless existing row locks are proven to cover every insert/delete/absence case. Use relevant UPDATE columns and changed-value predicates; do not invalidate on sign-in timestamps. INSERT/DELETE and absence-to-present transitions must invalidate. Validate all relation/column names against current schema before authoring migration. A missing dependency is a release blocker, not permission to weaken the fence.
  5. Fence time as well as writes. A revision cannot notice a trial or waiver expiring without a write. The fresh evaluation must expose the next relevant policy transition and cap proof validity at that instant as well as a short processing TTL. Derive transition times using current policy helpers/constants, including waiver policy/account expiry and signup-trial boundaries where relevant. SQL compares clock_timestamp() immediately before the consent effects. If the strict reader cannot establish its validity horizon, refuse that proof and retry/reissue; do not assert that a 5-second TTL alone proves freshness.
  6. Keep the existing atomic grant. Add a reviewed compatibility migration rather than changing applied predecessor bytes. Replace the dedicated-only sender predicate with identity checks plus the service-only revision-bound sender proof for both shared and dedicated modes. Bind proof to capability ID, workspace, owner, exact sender snapshot/key and channel; never accept a browser-provided decision. Remove/revoke an obsolete executable overload that could bypass the new proof. Preserve capability expiry/revocation, proposal version, job/candidate/offer/service activity, suppression lock, directory ownership, consent-event uniqueness, phone binding and all existing lifecycle checks. Any other RPC calling the sender predicate, including quote submission, must get a valid proof too; do not make email-only capability paths accidentally require an SMS-capable wallet.
  7. Separate identity from delivery readiness. Do not let a zero wallet erase an existing legal sender snapshot. Use the shared canonical selection logic for identity; use complete evaluateWorkspaceSendReadiness at SMS challenge availability and the actual dispatch boundary. Extract a small reusable transport-selection helper if needed, preserving the current readiness policy. Consent does not reserve credit or authorize future delivery. Outbound still rechecks current sender equality, suppression, purpose scope, runtime, provider identity and billing before calling Twilio.

Inbound proof routing

Capture immutable normalized signed From and rawTo before any moved-number rewrite. After STOP/START/HELP handling and an ordinary proof rate limit, recognize only the exact QUOTE <12 digits> grammar. Search active challenges by that signed wire pair, not a guessed manager. Compute the existing capability/phone/code HMAC for each bounded candidate and compare safely. Exactly one matching active capability identifies the owner/workspace. Zero matches do not grant; multiple matches fail closed. If the candidate limit is exceeded, refuse rather than choosing the newest row. Never log the code.

Resolve the capability's current sender through the fresh revision protocol, require its actual From to equal rawTo and match both consent and provider scope as appropriate, then consume once under the existing MessageSid uniqueness and consent locks. A valid proof must reach this path even when the phone is unknown to shared routing. A recognized proof must not run a prospect agent or produce an unrelated automated reply. Return 503 for transient database/control-plane failures so Twilio can retry; stale/invalid proof receives a harmless acknowledgement without consent. Old-number rewrite never makes a code sent to the wrong number valid. Keep durable receipt/projection evidence using existing pipeline conventions; do not fabricate ownedNumber to bypass routing.
