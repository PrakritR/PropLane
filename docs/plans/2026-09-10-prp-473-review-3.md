## Findings

### P2 / Medium - The final reply CAS loses the original legacy snapshot guard

`src/lib/tour-reschedule-sms-reply.server.ts:413` checks the repaired legacy snapshot on the guarded reread, but the final planned mutation at `:573` / `:578` does not carry that guard. The equivalent pending mutation at `:357` / `:361` also has no repair-guard argument.

After legacy A is upgraded and passes that reread, a competing write can change its SMS origin, source inquiry, conversation identity, request timestamp, or stored consent before the final CAS. The final CAS reloads that changed row, then confirms it because it only compares the narrower generation/version/owner/phone/window/status subset. Its database CAS token does not prevent this: it uses the competing write's new timestamp as its expected token.

The security delegate executed the actual current module with in-memory dependencies and storage, changing each omitted field separately at read 6, after successful upgrade and guarded reread. All five cases returned `confirmed`, with six reads and two writes. I independently reran the retained exact probe under Node 22.23.0 and reproduced every result, exit 0. The planned case is dynamically established; the equivalent pending omission is source-reviewed. Owner and exact phone checks still hold, so this is not a demonstrated cross-owner authorization bypass.

The correction-2 requirement was to preserve the original snapshot through reply consumption, including every retry. Apply the upgraded snapshot predicate inside both final CAS callbacks when a repair guard exists. Regression coverage must change one original field at a time after the guarded reread; the current new tests change B before that reread or change many discriminators together before repair.

### P2 / Medium - Mixed legacy/current proposals bypass ambiguity handling

`src/lib/tour-reschedule-sms-reply.server.ts:397` excludes proposals without `smsEligibility` from current matches. `:440` repairs a legacy proposal only when exactly one legacy candidate exists. The ambiguity check at `:522` then counts only the already-current proposals.

For one current eligible proposal and two actionable legacy proposals belonging to the same manager and exact phone pair, legacy repair is skipped and the match count becomes one. A generic YES confirms the current proposal even though the guest could be answering either outstanding legacy message. Shared valid conversation consent cannot solve which tour they meant, and those legacy candidates are never revalidated or counted.

The security delegate's actual-module probe returned `confirmed`, one write, and proposal statuses `[confirmed, awaiting_reply, awaiting_reply]`. I independently replayed it with the same result, exit 0. Fresh bugbot then corroborated both findings using the actual transpiled active-tour helper, valid tour rows, three distinct future windows and distinct properties, exit 0. This rules out an artifact of overlapping tour fixtures; it is not based on a static string assertion or a provider send.

Establish uniqueness across all actionable, authorized legacy and current candidates before consuming YES; when that cannot be established, fail closed or use the existing manager follow-up path. Cover mixed inventories, including two legacy plus one current and pending/planned combinations. Existing all-current ambiguity tests do not cover this deployment-compatibility case.
