## Cache, rendering, and performance

- New routes are server-side machine endpoints: signed `POST /api/internal/prospect-sms-burst` and authenticated `GET /api/cron/prospect-sms-bursts`. They add no page, RSC/client boundary, font, image, list, layout, or browser polling. The installed Next guide `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` confirms POST is uncached and request-header/database access keeps GET execution at request time. Neither route opts into shared caching. No private SMS response was found entering a public cache.
- QStash is used in server API code; the new model/provider path remains in the existing server agent call graph. No changed client import of these new runtime modules was found in the task diff. This is source-boundary review, not a measured before/after bundle-size benchmark.
- Burst publication uses a five-second HTTP timeout, with a 15-second recovery publication loop and at most 20 selected bursts. Quiet-window aggregation and database generation leases avoid one simultaneous model call per fragment. Both machine routes declare 60-second maximum duration; claims use a 120-second lease. Actual provider/database latency under load remains staging evidence to collect.
- Durable history loads inbound and confirmed outbound records concurrently, each capped at 24, then merges to 24. Recent confirmed replies are capped at four and retained tool-context groups at eight (`leasing-sms-agent.server.ts`). No new broad client sync/refetch or public tour response cache change was found; `tour-availability.server.ts` adds internal resolved/unavailable metadata while preserving the public slot projection.
- Recovery runs at most two shadow jobs together, and the runner bounds provider time/output. With `AXIS_PROSPECT_GPT_SHADOW_ENABLED` absent or false, the worker returns before querying/claiming shadow jobs or calling GPT. However, enabled durable primary turns still prepare snapshots and the submission RPC still inserts pending shadow jobs. Keeping GPT disabled prevents calls, not storage growth. Do not later enable the worker without accounting for that accumulated backlog and fixing FINAL-1/P2. No live volume benchmark or retention guarantee is claimed.

Final reviewed migration SHA-256 is `f2e77728990800838696e6fff60df17c723861dd9555a217f0650dc7ee96be70`; isolated clean/repeat apply and 78 SQL assertions are root's evidence, not proof of staging/production application. The new burst flag cannot bypass them. Prepared/deferred replies still rely on the existing outbox dispatcher and monitored outbox scheduler. A healthy burst cron alone is not delivery evidence. It does not verify this new migration, QStash variables, the burst callback, or GPT shadow disablement. Even a green old cutover check cannot close these prerequisites.
6. **Keep GPT shadow disabled.** `AXIS_PROSPECT_GPT_SHADOW_ENABLED` only enables for the string `true` (case-insensitive). Preserve absent/false across Preview and Production; do not use an inherited paid key. The known FINAL-1/P2 scorer can falsely ground swapped property-field values. Transport review acceptance does not resolve that defect or authorize GPT activation.

Rollback remains setting `PROSPECT_SMS_BURSTS_ENABLED=0`: old callbacks fail closed and prepared prospect rows defer; newly received supported Twilio traffic returns to the prior synchronous path. This disables the durable fix itself. A release with the feature off must not be described as an active production single-reply solution. Claw remains retired throughout.

## Follow-up: code deployment with the new migration absent and bursts disabled

Root requested a source check for unconditional new-column reads/writes that could break existing Twilio traffic before manual production migration. **None was established in the original reviewed tree**, for these concrete reasons:

- `owner-sms-dispatcher.server.ts:255` ordinary enqueue inserts only pre-existing outbox fields. New preparation RPC/parameters occur only within `if (input.prospectBurst)` at line 215.
- Dispatcher line 403 uses the existing `claim_sms_outbox` RPC without a projection of new columns. Its baseline SQL at `20260825120000_sms_control_plane.sql:421` returns `SETOF public.sms_outbox`. A database without the new columns returns objects with those properties absent; the TypeScript row type does not add a runtime query.
- Missing `row.prospect_burst_id` is falsy at lines 437 and 510, and missing `row.transport` does not match `claw` at line 446. The ordinary submission path at line 541 continues updating only pre-existing fields and uses the existing segment-budget RPC. The new submission RPC is called only for a correlated burst row.
- The legacy ingress only enters durable enqueue behind `durableProspectSmsEnabled()` in `claw-leasing-bot.server.ts:1044`. The leasing runtime reads `prospect_sms_bursts` history only with `args.prospectBurst` at line 370. Recent-confirmed-outbox reads use pre-existing fields.
- The new callback fails its health check before database access when disabled. Recovery also fails health before any burst table query, although its cron route first constructs the existing service client. Therefore the newly scheduled cron will return 503 while disabled; it must not be treated as a healthy activated scheduler.
- Added account-purge table entries do not establish a missing-table deletion regression: `account-deletion-errors.ts:5` and `purge-portal-account-data.ts:25` explicitly recognize missing-table codes `42P01`/`PGRST205`.

It does not establish full migration-free deployment compatibility or override the normal schema/release gate.
