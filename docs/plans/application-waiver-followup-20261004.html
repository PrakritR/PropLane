Waiver save and display follow-up

Dedicated follow-up to production commit 4796d559d. The manager account/property was requested but has not been identified; this report distinguishes reproduced defects from verification of that specific account.

Reproduced defects

The automation dialog retained “Saved” after a new focused edit that had not been sent. Regression tests also reproduced an older settings read replacing a confirmed new code, no normalization of the displayed saved value, and successful HTTP responses being accepted without checking persistence. The application form editor silently discarded an enabled promo code when its separate fee override was off.

Fix

Waiver edits clear the previous success mark and autosave after a 600 ms pause, while blur/close still flush and await the same request. Success requires the PATCH returned code and a fresh property-scoped GET to match the requested normalized code. The displayed field uses the confirmed stored value. Failed confirmation retains the draft, reports failure and blocks close. Scoped load IDs and per-property edit revisions prevent stale responses replacing newer edits or another property's code. Form promo codes persist independently of the fee toggle. No authorization, schema, dependency or environment changes.

Validation

78 focused tests across seven files passed with one worker. The new property-switch regression covers a save on A completing while B's current read is pending. Security and Bugbot reviews are clear after resolving that race. Changed settings component and tests lint passed; the application editor retains exactly its two pre-existing lint errors and three warnings, with no new errors. Whole-project CI/build and final browser checks are pending.

Dev/test browser reproduced stale “Saved” and verified paused input saving without blur: fresh server read and field both showed the normalized code before success. Temporary codes are cleared. Native uses the same shared settings implementation; no routing or shell changes.
