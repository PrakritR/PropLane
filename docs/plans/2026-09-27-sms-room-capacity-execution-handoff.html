Outcome

  • The shared listing tool used by prospect and verified resident SMS now returns residentCapacity and physicalBeds as separate room facts.
  • get_listing_details returns maximumResidents only when every normalized stored room is represented in the prospect-safe summary. The prompts describe it as summed published room capacity, not a legal occupancy limit.
  • Reply suppression now requires an exact delivered outbox row that predates the inbound and a trusted inbound text matching a narrow standalone acknowledgment. Repeated questions, clarifications, corrections, availability questions, and affirmative replies such as “sounds good” cannot silence the turn.
  • The model-callable regression path is covered: an attempted suppression for the observed capacity clarification returns a tool error, then the model produces an answer.
  • The Twilio prospect path records durable ingress before acknowledgment, then publishes to QStash in after(). A failed deferred publish uses the existing inline revision-fenced worker, and the recovery cron remains the final recovery path. This removes a blocking QStash call of up to five seconds from Twilio's 15 second webhook budget without bypassing QStash as the normal worker path.

Key decisions

  • Capacity comes from the normalized listing submission. It is never inferred from bedrooms, physical beds, or model arithmetic.
  • If the room summary filters any stored room, the listing total is null rather than an understated number.
  • Only unambiguous acknowledgments such as “thanks”, “thank you”, “got it”, “understood”, and “noted” may be quiet. “Yes”, “okay”, “sounds good”, “great”, “perfect”, and “awesome” remain reply-bearing because they may accept an offer.
  • Suppression candidates require sms_outbox.status = delivered, fall inside the existing two-minute window, and have a delivery timestamp no later than the inbound snapshot.
  • No production data, live listing, Twilio message, protected account, deployment, or branch promotion was changed.
