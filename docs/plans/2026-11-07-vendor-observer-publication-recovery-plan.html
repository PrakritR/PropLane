Failure, timeout and retry semantics

Listen for restricted-client error/end events before requesting termination so an expected asynchronous event cannot crash the process. PostgreSQL administrative shutdown (57P01) or a transport close caused by that exact requested self-termination may be expected cleanup outcomes. Neither an error nor EOF proves success; require prior successful proof, verified held identity, an issued bounded termination attempt and independent fresh all-state zero. Unexpected proof errors must never be reclassified as expected termination. Test denial, unexpected errors and events arriving before, during and after query rejection. No unhandled promise or error event.

All DB connections and queries need finite bounds. Keep the existing 10-second connection/statement limits and add bounded client waits where necessary; do not implement a Promise.race that leaves a query or termination running in the background. Track and close the owned sockets on failure. Renewal belongs to root's separate process because synchronous GitHub subprocess calls block the helper event loop. Do not extend 60-second receipts or waive the 35-second final budget.

On any failure, retain the same password and all original files; suppress raw driver/provider diagnostics. No automatic rollback password, reapply, deletion, privilege change or publication from a finally block. Cleanup may close only the proven task-owned connection; it must not terminate a discovered unrelated row. If its identity is unknown, close its local socket and report unresolved backend state. Root keeps consumers excluded and diagnoses privately.

Use uniquely named exclusive durable recovery-attempt records (nonsecret timestamps and source/operation bindings), allowing a later full re-proof without overwriting the original markers. A GitHub timeout or lost response is ambiguous: leave publication pending and preserve the operation. A retry may publish the exact same retained bytes only after repeating all fresh safety gates. A success followed by failed published-marker IO is likewise ambiguous and permits only same-value replay. Updated GitHub metadata is corroboration, not proof of the secret's value. No source edit or timestamp rewrite may revive a stale reviewed pin.
