Remaining source defects

R16 - P1: conflicting delivery still places another property's content behind the first property's permissions and binding

src/lib/portal-inbox-delivery.ts:87 preserves the old scalar identity when incoming identity conflicts, but :460 still selects the existing thread by the person/folder lookup and :506-511 appends the new body to that same row. Preserving a contradiction in identityProvenance does not isolate the actual message.

Concrete case: a manager's resident conversation is stamped property A and SMS key A. A newly submitted application or payment/service message about property B for that resident appends into that record. The resulting record contains B's content but still says propertyId: A. src/lib/communication/conversation-visibility.server.ts:337-340 treats that scalar property as the entire house scope, and :381-393 can return the whole record to a co-manager authorized only for A or in A's workspace. It does not inspect provenance. The manager renderer independently reads only scalar binding fields at src/components/portal/pro-unified-inbox.tsx:607-631, so the combined record can also remain folded with SMS A despite the stored conflicting claim.

This is a source-derived authorization and identity defect, not a claimed reproduced disclosure. The added test at tests/unit/collapse-person-inbox-threads.test.ts:23 explicitly expects B's message to append while A's scalar property/key remain; it does not exercise house authorization or the manager renderer. The next implementation must choose a compatible relationship record before appending, or enforce equivalent message-level isolation through every reader and action. Keeping provenance alone is insufficient.

R17 - P2: the resident list undoes property isolation when SMS is absent

src/components/portal/resident-communication.tsx:458-470 only detects conflicting unbound identity by comparison with smsConversations. With SMS UI disabled, or with no matching SMS history, two email rows for the same manager email but different properties both receive unifiedInboxPersonKey(storedEmail). :601 merges them again, undoing the new storage partition at src/lib/portal-inbox-storage.ts:1250.

A resident with property-A and property-B threads therefore gets one combined timeline and action membership even though the server retained separate, contradictory relationship identities. This is especially relevant to the default SMS-off surface. Derive the fallback grouping from compatible email provenance itself; its safety must not depend on native SMS being present. Existing tests cover contradictory email versus SMS, not this server-partition-to-client fallback.

R18 - P2: a transient read failure cannot retry for the same observation

src/components/portal/resident-communication.tsx:708-714 stores the attempted signature before sending and leaves it set when the response is null or contains a failed result. A network rejection also has no catch. The inner panel's former acknowledgement is disabled by the new parent integration.

After one temporary failed mark-read request, reopening the same unchanged unread conversation or refreshing its unchanged list does not issue another acknowledgement: the signature still matches. A viewer change, remount, another attempted signature or changed source observation is needed to escape it. Release the failed attempt and provide a bounded retry path; catch transport rejection. Test failure followed by successful retry without changing the message.

R19 - P2: reconfirming the same tour window and copy is suppressed as an old retry

src/lib/tour-notification-delivery.server.ts:1084-1089 derives a confirmation id only from inquiry id, the constant confirmed, the window and a content hash. Confirm, cancel and genuinely confirm again for the same window using the unchanged default subject/body yields the first confirmation's id. src/lib/property-manager-inbox-thread.server.ts:286 returns early for that already-recorded id, so the timeline can end at cancellation despite a real reconfirmation.

The lifecycle regression at tests/unit/property-manager-inbox-thread.test.ts:142 changes both the window and reconfirmation wording. It proves that changed content produces a different turn, but not that repeated lifecycle transitions are recorded. Use a durable lifecycle operation/generation identity to distinguish a new transition from a delivery retry, and test a same-window, same-copy confirmation after cancellation. This collision is established from deterministic source behavior; actual booking/browser orchestration was not exercised.
