Portal auth refresh storm

Release-blocking product defect: ordinary portal page loading forcibly refreshes a fresh one-hour session. Repeated navigations exhaust refresh capacity and the browser is redirected to sign-in. This was observed in the full browser run 35456966267 at commit 63d4d6d87. This plan is a source and trace review, not an implemented fix.

The mobile-portal-layout spec already uses the fresh-session authenticated fixture. Stale saved storage is not the cause. The trace proves excessive refresh requests and subsequent session failure. It does not establish which internal library branch clears or fails to retain session state after the 429; investigate that detail without inventing a server error code.

Source cause and bounded change

src/components/portal/portal-session-keepalive.tsx calls refreshSession() unconditionally after safeBrowserGetSession(). Its effect runs on mount, document visibility, and native resume. Full page navigations remount the portal layout and reset any module-only throttle. No expiry check or in-flight guard exists. The component is mounted by both manager and resident layouts. src/lib/supabase/browser.ts already returns a singleton browser client and enables the SDK's automatic refresh; it is not necessary to replace the client factory.

Change keepalive to preserve a valid, sufficiently fresh session without explicit refresh. Use the session expiry timestamp, allowing a small documented safety margin. If safeBrowserGetSession already renewed an expired session, do not immediately refresh the resulting fresh session again. Coalesce concurrent mount/visibility/native-resume work, keyed to the actual session owner, and reset stale work correctly when the account changes. An in-memory cooldown alone is insufficient because full navigation recreates the module.

Preserve native resume recovery for sessions near expiry. Keep revoked/invalid-token cleanup limited to recognized permanent failures. Rate limiting and transient network errors must not trigger a local sign-out or destructive cache clearing. Inspect the actual 429 path before changing shared recovery logic. Do not disable SDK auto-refresh, globally increase auth rate limits, add E2E sleeps, or loosen portal guards.

src/app/auth/continue/page.tsx also explicitly refreshes to flush SSR cookies. Review its necessity and avoid redundant refresh when the session is already synchronized, but preserve OAuth and cookie-flush behavior. That one call does not by itself explain the observed per-navigation storm.

Acceptance and validation

  1. Focused tests exercise fresh mount (no explicit refresh), near-expiry resume (one renewal), simultaneous visibility/native resume (one renewal), already-renewed session (no second renewal), permanent revoked token (existing safe cleanup), transient 429/network failure (no deliberate logout), and owner change while a refresh is in flight.
  2. Run the existing mobile manager route sweep using a fresh real dev/test session on GitHub. Capture only grant type, response status, and aggregate refresh counts. The sweep must retain its authenticated identity and reach /portal/app without 429 or sign-in redirects.
  3. Exercise resident navigation and native-background resume. Verify a real near-expiry session can recover; a fix that merely eliminates all refreshes is insufficient.
  4. Rerun Calendar filter and Promotion flows after this correction. Their detached controls may share this failure, but that link is not proven by the inspected mobile trace.
  5. One validation owner coordinates focused checks and then the full browser run. Keep zero retries and do not alter the release ladder or production database.
