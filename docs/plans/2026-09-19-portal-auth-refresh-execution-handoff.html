Implementation

  • src/components/portal/portal-session-keepalive.tsx now delegates keepalive decisions to one module-level coordinator shared by manager and resident layout mounts, visibility changes, and native resume events.
  • src/lib/supabase/portal-session-refresh.ts adds an expiry-aware coordinator. A session more than two minutes from expiry is preserved without an explicit refresh. The two-minute margin is slightly wider than the installed Supabase client's 90-second expiry margin.
  • The coordinator reads the session again before explicit renewal. If getSession() already renewed the token, it skips the redundant refresh.
  • Concurrent keepalive signals share one promise per authenticated user. Account changes advance an owner generation and detach stale in-flight work, preventing a permanent failure for the previous user from clearing the new user's local auth.
  • Recognized invalid or missing refresh tokens still use the existing fail-closed cleanup. HTTP 429 responses, network failures, and other transient errors do not deliberately sign the user out or clear browser auth.

Focused tests added

tests/unit/portal-session-refresh.test.ts covers:

  • fresh mount with no explicit refresh;
  • near-expiry renewal;
  • simultaneous visibility and native resume coalesced to one renewal;
  • a session already renewed by getSession() with no second renewal;
  • permanently revoked refresh-token cleanup;
  • HTTP 429 and rejected network requests without local sign-out;
  • an account change while the previous owner's refresh is in flight.

Scope decisions

  • The singleton Supabase browser client and SDK auto-refresh remain unchanged.
  • src/app/auth/continue/page.tsx remains unchanged. Its one explicit refresh serves the separate OAuth and SSR cookie-flush path and does not explain the per-navigation storm.
  • No database, migration, route, portal-guard, rate-limit, or production changes were made.
