## Description

Found in a portal audit, 2026-09-04. **The evidence layer's core promise is enforced in the browser.**

## Where the guard lives

The "already signed / not yet sent" check is in `src/lib/lease-pipeline-storage.ts:2741`:

```ts
if (row.status !== "Resident Signature Pending" || row.bucket !== "resident" || row.residentSignature) return false;
```

That is a **browser-side store function**. The server route `src/app/api/portal-lease-pipeline/route.ts` guards the *document* (`replacesSignedLeaseDocument`, 455-461) and the resident's *scope* (581-590) — but **nothing refuses a resident PUT that**:

* writes a **new** `residentSignature` **over an existing one**, or
* signs a row still in `bucket: "manager"` (i.e. never sent to them)

## The stale-amendment path is worse

If the resident's tab holds a stale `generatedHtml` and the manager amends the lease meanwhile, the resident's sign-and-save **writes the stale body back**. The immutability check at line 455 only fires once a signature already exists, so on the first signature there is nothing stopping it.

Result: **the manager's amendment is silently reverted, and a signature is attached to the superseded text.** Both parties believe the signed lease says what they last saw, and they are looking at different documents.

## Why this is the most serious kind of bug here

AGENTS.md is explicit that every signature must record the SHA-256 of the document *that party was shown*, per-signature, at signature time — the whole point being that a substitution is detectable. A client-only guard means the invariant holds **only for well-behaved browsers**. A lease is the legal artifact of the tenancy; "we trust the client" is not a defensible position for it.

## Fix

* **Move the guard server-side.** Refuse a `residentSignature` write when one already exists, or when `bucket !== "resident"` / status is not awaiting that signature. The client check stays as UX.
* **Reject a stale body.** The resident's PUT should carry the document hash they were shown; if it does not match the current row, refuse and tell them the lease was updated — do not silently accept either version.
* Regression tests for: double-sign, sign-before-send, and sign-with-stale-body.

## Related

`docs/agents/lease-generation.md` — `preserveSignedLeaseDocuments`, `leaseClaimsExecution`. Note the doc already warns the digest bindings are internal-consistency checks, **not** tamper-proofing, because `row_data` is writable by the row's own resident. This ticket is that warning becoming concrete.
